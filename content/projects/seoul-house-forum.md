## 프로젝트 개요

서울특별시가 여는 **2026 서울주거포럼** 공식 홈페이지입니다. '전월세시장 현황 진단 및 안정화 방안 모색'을 주제로 2026년 10월 7일 한국프레스센터에서 열리는 시민 참여형 주거정책 포럼입니다.

행사 정보와 연사 소개, 사전 참가 등록 안내에 더해, 시민이 자기 지역의 주거 문제에 대한 의견을 직접 남기는 **자유게시판**을 함께 만들었습니다. 공개 게시판인 만큼 기능 구현보다 "어떻게 하면 익명 창구를 열면서도 도배와 악성 게시물을 막을 수 있는가"에 집중했습니다.

### 기술 스택

- **FE**: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS 4, TipTap 3
- **BE / 인프라**: Route Handlers, Cloudflare Workers (`@opennextjs/cloudflare`), Cloudflare D1, Supabase Storage, Cloudflare Turnstile, GA4 Data API

### 협업 방식

기획 1인, 디자인 1인, 개발 1인이 붙은 프로젝트였고, 주어진 구축 일정이 1주라 세 역할이 순차가 아니라 거의 동시에 돌아갔습니다. 기획이 확정되기를 기다렸다가 디자인을 받고 그때 개발을 시작하면 일정이 맞지 않아, **화면 단위가 아니라 기획이 확정된 순서대로** 넘겨받는 방식을 택했습니다.

**Notion** — 요구사항 정리, 페이지별 진행 상태, 피드백을 한곳에 모았습니다. 특히 자유게시판은 "어디까지 자동으로 막고 어디부터 운영자가 판단할 것인가"를 개발 혼자 정할 수 없는 문제라, 차단 기준과 이용 수칙 문구, 개인정보 수집 안내 문구를 기획과 Notion에서 문서로 합의한 뒤 구현했습니다.

**Figma** — 디자인 소통 창구로 썼습니다. 시안을 받아 그대로 옮기기보다, 반복되는 요소(버튼, 카드, 모달, 배지, 폼 인풋)를 먼저 추려 컴포넌트와 Tailwind 요소로 정리하고 페이지를 조립하는 방식으로 진행했습니다. 디자인 쪽에서 아직 정리 중인 화면이 있어도 이미 확정된 공통 요소부터 구현할 수 있어, 시안 대기 시간을 줄이는 데 도움이 됐습니다.

관리자 페이지는 시안이 별도로 없어 공개 페이지에서 정리한 토큰과 컴포넌트를 재사용해 개발이 직접 구성했습니다.

## 기술 목표

- **익명 게시판을 안전하게 여는 것** — 로그인 없이 누구나 쓸 수 있게 하되, 자동 차단과 운영자 검수를 이중으로 두어 악성 게시물이 공개 화면에 노출되지 않도록 설계
- **개인정보를 최소로 수집하고 스스로 지우는 구조** — 도배 방지에 필요한 IP·User-Agent만 받고 30일 뒤 자동 파기, 작성자 이름은 공개용 마스킹 값과 암호화 원문을 분리 저장
- **행사 종료 후에도 고정비가 없는 운영** — Cloudflare Workers + D1 서버리스 구성으로 상시 가동 서버 없이 운영

## 고민했던 점들

### 익명 게시판
![의견 등록 전 안내 모달 — 수집 항목·목적·보유 기간 안내, 필수 동의 체크박스 두 개와 이용 수칙, Cloudflare Turnstile 검증](/assets/projects/seoul-house-forum/board-consent-modal.webp)

로그인이 없는 공개 게시판은 사실상 아무나 제한없이 쓸 수 있는 입력창입니다. 한 겹으로 막기보다 여러 방식의 방어 수단을 순서대로 쌓고, 애매한 표현은 운영자 검수로 넘기는 방향을 택했습니다.

의견 등록 요청은 다음 순서를 통과해야 저장됩니다.

1. **출처 확인** — Origin이 다르면 거부. 세션 쿠키는 `SameSite=Strict`로 두어 CSRF를 차단합니다.
2. **동의 확인** — 개인정보(IP, 브라우저 정보, 입력한 이름, 선택한 거주지 등) 수집과 이용 수칙 두 가지에 모두 동의해야 합니다.
3. **허니팟 / 최소 작성 시간** — 사람 눈에 보이지 않는 필드가 채워졌거나 폼을 연 지 3초 안에 제출되면 봇으로 판단합니다. 이때는 **실패가 아니라 성공처럼 응답**해 자동화 도구가 조건을 바꿔 재시도하지 않도록 했습니다.
4. **입력 검증** — 길이 제한과 함께 링크·도메인, 전화번호·이메일, 같은 문자 10회 이상 반복, 욕설·도박 관련 금칙어를 차단합니다. 금칙어는 공백과 특수문자를 제거한 뒤 비교해 `시 x`처럼 끊어 쓰는 우회를 막았습니다.
5. **Turnstile** — Cloudflare Turnstile 토큰을 서버에서 검증합니다.
6. **레이트리밋 / 중복 차단** — 같은 IP는 10초 쿨다운과 시간당 20건 제한을 받고, 24시간 안에 같은 내용을 다시 올릴 수 없습니다.
7. **검수 대기 저장** — 여기까지 통과해도 `pending` 상태로 저장되고, 운영자 승인 후에 공개됩니다.

1~6은 명백한 스팸만 거르고, 판단이 필요한 내용은 7의 운영자의 검수에 맡기는 구조입니다.

### 작성자명 보관 방식

의견에는 이름이 따라붙는데, 공개 화면에 실명이 그대로 노출되면 안 되고 운영자는 검수를 위해 원문을 볼 수 있어야 했습니다.

따라서 두 값을 분리하여 저장했습니다. 공개용으로는 `김철수`를 `김ㅇㅇ`로 바꾼 **마스킹 값만 평문**으로 두고, 원문은 **AES-256-GCM으로 암호화**해 따로 저장했습니다. 목록·모달·공개 API는 마스킹 값만 읽고, 복호화는 관리자 화면에서만 이루어집니다. 키가 교체되거나 값이 손상돼 복호화에 실패하면 예외를 던지는 대신 `null`을 돌려 관리자 화면이 마스킹 값으로 대신 표시하도록 했습니다.

수집한 IP와 User-Agent는 30일이 지나면 자동으로 지웁니다. 별도 예약 작업을 두지 않고, 의견이 등록되거나 관리자가 게시판을 열 때마다 기간이 지난 값을 비우는 쿼리를 함께 실행하도록 했습니다. 글은 남기고 IP와 User-Agent만 `NULL`로 바꾸며, 이미 비워진 행은 조건에서 빠지도록 했기 때문에 자주 실행해도 부담이 없도록 했습니다.

```ts
export const BOARD_PERSONAL_DATA_RETENTION_DAYS = 30;

export async function purgeExpiredPersonalData(): Promise<void> {
  await getDb()
    .prepare("UPDATE board_posts SET ip = NULL, user_agent = NULL WHERE ip IS NOT NULL AND created_at < ?")
    .bind(minutesAgo(BOARD_PERSONAL_DATA_RETENTION_DAYS * 24 * 60))
    .run();
}

await createPendingPost(validation.value, { ip, userAgent, contentHash });
await purgeExpiredPersonalData();
```

동의 안내 문구에는 버전을 매겨, 문구가 바뀌면 **어떤 버전의 안내에 동의했는지**가 기록에 남도록 했습니다.

### proxy.ts

Next.js 16에서 `middleware.ts`가 `proxy.ts`로 바뀌었습니다. `proxy.ts`는 요청 경로 앞단 쪽에서 도는 코드라 여기서만 막으면 우회 경로가 생길 여지가 있습니다.

그래서 `proxy.ts`에서는 **세션 쿠키가 아예 없는 요청만** 빠르게 걸러내는 1차 검사만 하고, 쿠키의 유효성(만료, 위조)은 페이지에서는 `verifyAdmin`, API에서는 `guardAdminApi`를 불러 DB에서 다시 확인합니다.

세션은 쿠키에 랜덤 토큰을 내리고 DB에는 그 **SHA-256 해시만** 저장해, DB가 유출돼도 토큰을 되돌려 쓸 수 없게 했습니다. 비밀번호는 PBKDF2(SHA-256, 100,000회)로 해싱했는데, 이 반복 횟수는 Workers의 WebCrypto가 허용하는 최대치입니다. 로그인 실패는 IP 기준으로 기록해 일정 횟수를 넘으면 잠기도록 했습니다.

### 공지 본문 필터링

공지 본문은 TipTap JSON 형식으로 저장하고 서버에서 HTML로 렌더링합니다.

HTML 문자열을 그대로 저장하지 않고 JSON을 고른 이유는 걸러내기가 쉽기 때문입니다. HTML은 태그와 속성이 문자열에 섞여 있어 안전하게 거르려면 HTML을 다시 해석해야 하는데, Cloudflare Workers에는 브라우저의 DOM이 없어 이런 sanitize 라이브러리를 쓰기 번거롭습니다. 반면 TipTap JSON은 `{ type: "paragraph", content: [...] }`처럼 블록마다 종류가 있기에 객체를 따라 내려가며 `type`만 확인하면 됩니다. 같은 JSON에서 문자열만 뽑아 공지 검색, 검색엔진용 설명문, 구조화 데이터에도 재사용할 수 있는 장점이 있습니다.

관리자만 쓰는 에디터라도 외부에서 복사해 온 내용에 스크립트가 섞여 들어오면 전체 방문자에게 실행되므로, 관리자가 쓴 글이라도 똑같이 걸러야 한다고 판단했습니다.

**저장 시점**에 미리 정해 둔 요소만 남기고 나머지는 버렸습니다. 문단·제목·목록·이미지 같은 블록 12종과 굵게·링크·색상 같은 글자 서식 8종만 허용하고, 링크는 `http`/`https`/`mailto`/`tel`과 내부 경로만, 이미지는 자체 업로드 경로와 https 원격 주소만 허용합니다. 색상과 글자 크기도 정규식으로 형식을 제한해 임의 style 값이 들어가지 못하게 했습니다.

에디터가 만든 JSON을 위에서부터 따라 내려가면서, 허용 목록에 없는 블록은 그 아래 내용까지 통째로 버리고 글자 서식은 값의 형식까지 확인한 뒤 남깁니다.

```ts
const ALLOWED_NODES = new Set([
  "doc", "paragraph", "text", "heading", "bulletList", "orderedList",
  "listItem", "blockquote", "horizontalRule", "hardBreak", "codeBlock", "image",
]);
const ALLOWED_MARKS = new Set(["bold", "italic", "underline", "strike", "code", "link", "textStyle", "highlight"]);
```

**렌더링 직전**에 같은 화이트리스트를 한 번 더 통과시킨 뒤 TipTap `static-renderer`로 출력합니다. 에디터에 등록된 블록만 HTML로 바뀌고, 글자나 속성 값에 섞인 `<script>` 같은 태그는 실행되지 않는 일반 문자열로 바뀝니다. 따라서 에디터를 거치지 않고 API로 직접 값을 저장하더라도 화면에는 나오지 않습니다.

`static-renderer`는 에디터를 띄우지 않고도 서버에서 HTML을 만들 수 있기에 선택했습니다. 공지 상세 페이지는 서버 컴포넌트라 브라우저 없이 HTML 문자열만 있으면 되고, 방문자에게 에디터 코드를 내려보낼 필요도 없습니다.

확장자나 `Content-Type`은 업로드하는 쪽에서 얼마든지 바꿀 수 있기 때문에, 이미지 파일마다 맨 앞에 정해져 있는 값을 직접 읽어 실제 형식을 확인합니다. SVG는 코드 내에 스크립트를 담을 위험이 있어 아예 받지 않습니다.


## 회고

1주라는 짧은 기간이었지만, 시간의 대부분은 화면이 아니라 **누구나 글을 쓸 수 있는 게시판을 어떻게 안전하게 열어둘지**를 정하는 데 들어갔습니다. 로그인 없는 게시판은 기능 자체는 단순한데, 열어두는 순간 스팸·개인정보·명예훼손의 위험이 큰 기능이었습니다. 자동 차단은 명백한 것만 거르고 판단은 사람에게 넘기는 선을 정하고 나니 나머지 구현은 자연스럽게 따라왔습니다.

짧은 일정 안에서 기획자, 디자이너와 지속적으로 소통하며 작업한 것도 큰 경험이었습니다. 시간이 넉넉하지 않다 보니 막히는 부분을 혼자 오래 붙잡기보다 빨리 공유하고, 같은 문제도 직군에 따라 다르게 설명하는 게 중요했습니다. 기획자와는 기능이 어디까지 되고 안 되는지를, 디자이너와는 화면에서 무엇이 달라지는지를 중심으로 이야기하니 결정이 훨씬 빨라졌습니다. 여러 직군이 함께 일할 때 어떻게 말해야 효율적으로 맞춰 갈 수 있는지 직접 겪어볼 수 있었습니다.
