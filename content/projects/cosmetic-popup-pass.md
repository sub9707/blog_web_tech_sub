## 프로젝트 개요

바이오던스가 서울 소재 대학 네 곳을 돌며 여는 제품 팝업 행사의 **사전 참여 플랫폼**입니다.

참여자는 사전에 대학 커뮤니티에 올라온 전용 링크로 들어와 스킨케어 설문 5문항에 답하고 이름과 연락처를 남기면, 카카오 알림톡으로 **팝업 행사장 입장용 디지털 패스(QR)**를 받습니다. 행사 당일에는 현장 스태프가 앱 내부의 스캔 페이지에서 QR을 찍어 바로 입장 처리하고, 운영 측은 대학별 발급 현황과 설문 응답 결과를 대시보드와 엑셀로 확인합니다.

참여자 화면, 스태프 스캐너, 관리자 대시보드를 모두 **Cloudflare Workers 하나**에 올려 화면과 API를 함께 띄웠습니다.

### 기술 스택

- **FE**: React 19, TypeScript, Vite 6, React Router 7, Tailwind CSS 4, shadcn/ui, React Hook Form, Zod
- **BE / 인프라**: Cloudflare Workers, Hono, Cloudflare D1 + Drizzle ORM, Workers Rate Limiting, Cloudflare Turnstile
- **인증 / 보안**: JWT(jose) + httpOnly 쿠키 세션, bcryptjs, Web Crypto(AES-256-GCM, HMAC-SHA256, SHA-256)
- **외부 연동 / QR**: Solapi 카카오 알림톡, qrcode(SVG 렌더), qr-scanner(카메라 스캔)

**선택 이유**

- **React + Vite** — 참여자는 대학 커뮤니티 링크로만 들어오고 검색에 노출될 필요가 없기에, 서버에서 화면을 그리는 Next.js 대신 가벼운 React 화면을 API와 함께 Worker 하나에 올렸습니다.
- **Hono** — Workers에서 바로 돌아가는 API 라우터였고, 같은 Worker 안에서 `/api/*` 요청만 따로 받아 처리하기 쉬웠습니다.
- **Cloudflare D1** — 쓰기 요청을 하나씩 차례로 처리하기 때문에, 따로 잠금을 걸지 않고도 선착순 정원을 지킬 수 있었습니다.
- **bcryptjs** — 흔히 쓰는 `bcrypt`는 Workers에서 돌아가지 않아, 순수 JavaScript로 만든 `bcryptjs`를 썼습니다.
- **Solapi** — 카카오 알림톡은 공식 대행사를 거쳐야 보낼 수 있어 대행사를 골라야 했습니다. Solapi는 월 기본료 없이 보낸 건수만큼만 비용을 내서, 한 달 남짓 쓰고 끝나는 행사에 부담이 없었습니다. 알림톡 템플릿 등록과 승인 요청을 관리 화면에서 바로 할 수 있고, 알림톡이 실패하면 문자로 대신 보내주며, 알림톡과 문자를 같은 API로 보낼 수 있어 선택했습니다.

## 직접 체험해보기

참여자가 대학 커뮤니티 링크로 들어왔을 때의 화면입니다. 설문 5문항에 답하고 정보를 입력하면 디지털 패스가 발급되는 흐름을 그대로 따라가 볼 수 있습니다. 서버 대신 브라우저 안의 예시 데이터로 동작하는 데모라 실제 알림톡은 발송되지 않습니다.

## 기술 목표

- **대학별 선착순 정원을 정확히 지키기** — 수백 명이 동시에 신청해도 정원보다 많이 발급되지 않도록 처리
- **개인정보를 그대로 저장하지 않기** — 이름과 연락처는 암호화해 저장하고, QR에는 개인정보 없이 무작위 값만 담기
- **알림톡이 실패해도 신청은 끝까지 되게 하기** — 알림톡 발송이 실패해도 신청과 패스 발급은 정상 완료하고, 실패한 건은 따로 표시
- **현장에서 막히지 않는 입장 처리** — QR 찍기 → 확인 → 결과 표시 → 다음 QR까지 멈춤 없이 이어지는 스캐너

- Cloudflare Worker 하나에서 프론트엔드와 API를 함께 띄웠습니다. `/api/*`로 들어온 요청은 Hono가 처리하고, 나머지 경로는 React 화면을 보여줍니다.
- 암호화, QR 토큰, 입력값 검사, 정원 계산처럼 브라우저와 서버 양쪽에서 필요한 코드는 `src/lib` 한곳에 모아 같이 썼습니다. 화면에 뜨는 '신청 가능 / 마감' 표시와 서버가 실제로 신청을 받아주는 기준이 어긋나지 않습니다.
- 참여자는 로그인 없이 링크(대학별 코드로 분기한 링크)로만 들어오고, 스태프와 관리자는 아이디와 비밀번호로 로그인합니다. 스태프는 QR 스캐너와 당일 참여자 관리에, 관리자는 스태프 기능을 포함한 통계, 인원 및 기간 설정에 접근 가능합니다.

**랜딩 페이지** — 대학 커뮤니티 전용 링크(`/event/:slug/u/:linkCode`)로만 들어올 수 있습니다. 링크 끝에는 어느 대학용인지 알 수 없는 무작위 코드가 붙고, 이 코드 없이 들어오면 참여를 막고 안내 화면만 보여줍니다. 그 대학의 모집 기간이 끝났거나 정원이 찼으면 여기서 종료, 마감 안내 UI로 바뀝니다.

**설문** — 4지선다 5문항을 한 화면에 하나씩 보여주고, 선택지를 누르면 0.3초 뒤 다음 문항으로 넘어갑니다. 문항 길이가 달라도 선택지 위치가 흔들리지 않게 문항 영역과 '이전' 버튼 자리의 높이를 미리 고정했습니다. 답변은 제출 전까지 `sessionStorage`에 저장해 두는데, 저장 키에 링크 코드를 넣어서 같은 탭에서 다른 대학 링크로 들어와도 이전 답변이 섞이지 않게 했습니다.

**정보 입력 및 제출** — 이름, 연락처, 개인정보 수집 및 이용 동의를 받고 Turnstile 봇 검사를 거쳐 제출합니다. 같은 행사에 같은 번호로 다시 신청하면 이미 신청했다는 안내를 띄웁니다.

**디지털 패스** — 알림톡의 '입장용 QR 확인하기' 버튼을 누르면 열리는 페이지로, QR 코드와 4자리 고객번호를 보여줍니다. 스태프가 QR을 찍으면 입장 확인 안내가 뜬 뒤 화면이 바로 **설문 결과(추천 루틴) 페이지**로 바뀝니다. 입장 후에 알림톡 버튼을 다시 눌러도 QR이 아니라 결과 페이지가 열려서, 방문객은 입장하자마자 자기 결과를 보고 다음 안내로 이동할 수 있습니다.

**카카오 알림톡** — 승인받은 템플릿으로 이름, 고객번호, 패스 페이지 링크를 보냅니다. QR 이미지를 직접 보내지 않고 링크만 보내며, QR은 패스 페이지를 열 때마다 그 자리에서 그립니다. 그래서 QR 이미지를 따로 저장해 둘 곳이 필요 없습니다.

### 현장 모바일 설문 (추가 요청)

에이전시 측 요청으로 추가한 기능입니다. 키오스크를 쓰려고 따로 줄을 서지 않고, 현장 대기줄에서 기다리는 동안 휴대폰으로 같은 설문을 진행해 대기하는 불편을 덜기 위해 만들었습니다. 현장에 놓인 QR을 찍으면 휴대폰에서 [설문 키오스크](/portfolio/바이오던스-팝업-설문-키오스크)와 같은 설문과 추천 결과 화면이 열립니다.

사전 설문과는 목적이 달라서 흐름도 다르게 만들었습니다.

| | 사전 설문 | 현장 모바일 설문 |
| --- | --- | --- |
| **언제, 어디서** | 행사 전, 대학 커뮤니티 링크 | 행사 당일, 현장 QR |
| **목적** | 입장용 디지털 패스 발급 | 대기줄에서 기다리는 동안 설문 참여, 추천 결과 확인 |
| **개인정보** | 이름, 연락처 입력 (암호화 저장) | 받지 않음, 답변만 익명으로 저장 |
| **결과** | 알림톡과 입장용 QR | 그 자리에서 스킨케어 루틴 추천 화면 |
| **언어** | 한국어 | 한국어, 중국어, 일본어 |

추천 결과는 화면에서 계산한 값을 그대로 저장하지 않고, 서버가 답변을 받아 다시 계산해서 저장합니다. 이미 있던 Worker와 D1에 경로와 테이블 하나만 더해 붙였기 때문에, 추가 요청이었는데도 새로 띄울 서버나 늘어나는 비용 없이 반영할 수 있었습니다.

**QR 스캐너** — 스태프 휴대폰 브라우저에서 카메라로 QR을 찍으면 서버가 확인하고 결과를 색으로 구분해 보여줍니다. 입장 완료는 초록, 이미 입장한 QR은 노랑, 다른 행사 QR이나 잘못된 QR은 빨강입니다. 스태프가 QR을 찍는 순간 참여자 쪽 디지털 패스 화면에도 입장 처리 표시가 바로 뜹니다.

결과 알림은 2.5초간 떠 있지만 스캐너는 1.2초 뒤 바로 다음 QR을 찍을 수 있게 돌아가고, 같은 QR을 5초 안에 다시 비추면 무시해서 같은 요청이 여러 번 가지 않게 했습니다. 스캐너에 들어가면 전체화면으로 바뀌고, 위쪽에 오늘 입장한 인원 수가 보입니다.

**참여자 관리와 현장 검색** — 알림톡을 못 받았거나 폰 배터리가 꺼진 참여자를 위해 이름이나 연락처 일부, 또는 고객번호 4자리로 찾을 수 있게 했습니다. 검색된 참여자는 QR 스캔없이 직접 입장 처리하거나, 입장 취소, 입장 시각 수정, 정보 수정을 할 수 있고, 어떤 스태프/관리자가 스캔했는지도 함께 기록됩니다.

**설정** — 대학마다 팝업 일정과 사은품 물량이 달랐기에 모집 마감일과 정원을 대학별로 두고, 관리자 화면에서 유연하게 바로 바꿀 수 있게 했습니다.

## 고민했던 점들

### 선착순 정원 동시성 문제

대학별 정원(`capacity`)과 지금까지 발급한 수(`issued_count`)를 같은 줄에 두고, 신청이 들어오면 **"발급 수가 정원보다 적을 때만 1 더하기"를 쿼리 한 번으로** 처리했습니다. D1은 쓰기 요청을 하나씩 차례로 처리하기 때문에, 따로 잠금을 걸지 않아도 여러 명이 동시에 신청해서 정원을 넘기는 일이 생기지 않습니다. 이 쿼리로 바뀐 줄이 없으면 정원이 찬 것으로 보고 마감 안내를 보냅니다.

자리를 먼저 잡은 뒤 참여자 저장이 실패하면(이미 신청한 번호, 일시적인 오류 등) 발급 수를 다시 1 줄여 자리를 돌려줍니다. 관리자가 참여자를 삭제할 때도 마찬가지입니다. 대시보드에서는 실제 참여자 수와 발급 수 기준 남은 정원을 따로 계산하는데, 자리를 돌려주는 처리가 어디선가 빠지면 두 숫자가 달라져 바로 눈에 띕니다.

참여자 정보와 설문 답변은 한 번에 같이 저장해서, 참여자만 저장되고 답변이 빠지는 일이 없게 했습니다.

### 개인정보 처리

이름과 연락처는 관리자 화면에서 다시 보여줘야 해서, 되돌릴 수 없는 해시가 아니라 되돌릴 수 있는 **AES-256-GCM**으로 암호화했습니다. 문제는 이 방식이 같은 번호라도 암호화할 때마다 결과가 달라진다는 점입니다. 그래서 DB에서 "같은 번호로 두 번 신청했는지"를 비교할 수 없었습니다.

따라서 연락처는 암호문과 별도로 **"같은 번호면 항상 같은 값이 나오는 해시(HMAC-SHA256)"**를 하나 더 저장하고, "한 행사에 이 값은 하나만"이라는 제약을 걸었습니다. 같은 번호로 동시에 두 번 제출해도 DB는 이를 한 건만 처리합니다.

처음에는 이름도 연락처처럼 해시로 저장해 검색했는데, 이름을 한 글자도 틀리지 않고 전부 입력해야만 검색할 수 있었습니다. 줄 선 참가자를 빨리 찾아야 하는 현장에서는 쓰기 어려워, 이름 해시를 없애고 서버에서 참가자 정보를 복호화하며 비교하도록 바꿨습니다. 이름 일부만 입력해도 찾을 수 있고, 8,000명 기준 약 0.5초면 충분했습니다. 숫자만 입력하면 이름은 건너뛰고 연락처만 비교하고, 고객번호 4자리는 참가자 ID 앞자리라 복호화 없이 바로 찾습니다.

QR에는 개인정보를 넣지 않고 무작위 값(`crypto.randomUUID()`)만 담았습니다. QR을 찍으면 이 값을 해시로 바꿔 참여자를 찾습니다.

### 스태프와 관리자 권한 분리

로그인하는 사람은 스태프와 관리자로 나눴습니다. 스태프는 행사 당일 입구에 서서 휴대폰 하나로 계속 QR을 찍는 현장 인력이고, 여러 명입니다. 관리자는 운영 측 몇 명이 행사 전후로 현황을 보고 설정을 바꾸는 역할입니다.

입구에서 쓰는 휴대폰은 잃어버리거나, 잠깐 내려놓은 사이 누가 보거나, 여러 사람이 계정을 돌려 쓰기 쉽습니다. 따라서 스태프에게는 **"지금 눈앞의 참여자를 입장시키는 데 필요한 것"만** 열어두고, 전체 인원 정보나 통계처럼 새어 나가면 피해가 큰 기능은 관리자만 접근 가능하도록 했습니다.

- **스태프 명단은 오늘 입장한 사람만** — 스태프 화면의 명단에는 오늘 이미 입장한 참여자만 나옵니다. 스태프 폰으로 볼 수 있는 개인정보는 오늘 입구를 지나간 사람까지이고, 수천 명의 사전 신청자 명단은 볼 수 없습니다.
- **QR 없는 입장 처리는 관리자만** — QR 없이 입장시키는 건 이름과 연락처만 보고 본인인지 판단해야 하는 일이라, 전체 검색 권한과 함께 관리자에게만 줬습니다. 이렇게 처리한 입장도 누가 했는지 기록에 남습니다.
- **배포 링크와 명단 파일은 관리자만** — 대학별 링크와 개인정보가 담긴 CSV는 한번 새어 나가면 되돌리기 어려워서, 관리자로 로그인해야만 받을 수 있게 했습니다.

로그인 기능과 계정 테이블은 하나로 두고, 계정마다 역할(`STAFF`/`ADMIN`)만 구분했습니다. 로그인하면 역할이 담긴 토큰(JWT)을 쿠키로 내려주고, 근무 교대 시간에 맞춰 12시간 뒤 만료되게 했습니다. 로그인 후에는 역할에 따라 스캐너나 대시보드로 이동하고, 관리자가 스태프 화면 주소로 들어오면 관리자 화면으로 보냅니다.

다만 이렇게 화면을 나눠 보여주는 건 편의를 위한 것이고, 권한 확인은 서버에서 합니다. 스태프 API는 로그인 여부와 그 행사 담당인지를 확인하고, 관리자 API는 여기에 더해 관리자 계정이 아니면 거절합니다. 화면에서 메뉴를 숨겨도 API는 직접 부를 수 있기 때문에, 요청이 올 때마다 서버에서 다시 확인하도록 했습니다.

### 봇 방지 — IP 제한을 걸지 않은 이유

신청 API에는 보통 "같은 IP에서 너무 많이 요청하면 막기"를 걸어두는데, 이번에는 참여자 신청 쪽에 **일부러 걸지 않았습니다.** 참여자 대부분이 같은 학교 와이파이나 같은 망을 쓸 가능성이 있기에, 수백 명이 하나의 IP를 가지는 최악의 상황을 가정했습니다.

대신 봇은 **Turnstile**로 막고, 같은 번호로 중복 신청은 연락처 제약으로 막도록 나눴습니다.

- **스태프, 관리자 로그인** — 사용하는 사람이 적고 Turnstile을 적용하지 않아, IP 기준 1분에 10번까지 제한
- **패스 페이지의 입장 여부 확인** — IP가 아니라 참여자 기준 1분에 60번까지. 입구에 줄 선 사람들이 같은 망을 써도 서로 영향이 없고, 비정상적으로 요청을 쏟아내는 경우만 막힙니다.

횟수 제한 기능 자체에 문제가 생기면 요청을 막지 않고 통과시키고 로그(Workers 메트릭)만 남깁니다.

### 알림톡 실패

알림톡 발송 코드는 어떤 경우에도 에러로 멈추지 않고 '성공' 또는 '실패' 결과만 돌려줍니다. 발송에 실패해도 신청과 패스 발급은 정상 완료되고, 실패한 건은 따로 표시되어 대시보드에서 볼 수 있습니다.

실패 건은 관리자 참여자 통계의 발송 상태와 Cloudflare Workers 메트릭 로그 두 곳에서 확인했습니다.

카카오 채널을 차단했거나 외국인 교환학생처럼 카카오톡을 쓰지 않아 알림톡이 아예 닿지 않는 참여자도 있었습니다. 이런 참여자에게는 Solapi 문자로 고객번호와 입장 안내를 따로 보냈습니다.

그래도 알림톡을 끝내 못 받는 참여자가 있을 수 있어서, 신청 완료 화면에 "이 화면이 보인다면 신청은 이미 끝났으니, 현장 스태프에게 이름과 연락처를 말하면 입장을 도와드린다"는 안내를 넣었습니다. 이후 관리자 페이지의 현장 검색과 직접 입장 처리 기능으로 해결합니다.

### 같은 QR을 두 명이 동시에 찍을 경우

입장 처리도 "아직 입장 기록이 없을 때만 입장 시각을 기록"하도록 쿼리 한 번으로 처리했습니다. 두 스태프가 같은 QR을 거의 동시에 찍어도 한 명만 성공하고, 다른 한 명에게는 '이미 입장한 고객'으로 나옵니다. 입장 기록은 따로 남겨서 누가 언제 입장시켰는지 확인할 수 있게 했습니다.

### 대학별 배포 링크 분기

배포 링크에는 대학 이름 대신 무작위 10자리 코드를 붙였습니다. 링크 코드로는 그 대학 정보만 조회할 수 있고, 전체 대학 목록을 알려주는 공개 API는 만들지 않았습니다. 잘못된 코드든 없는 행사든 똑같이 404로 응답해서 대학 코드를 추측하기 어렵게 했습니다.

통계와 CSV에는 사람이 알아볼 수 있는 대학 코드를 따로 씁니다. 링크가 엉뚱한 곳에 퍼지면 링크 코드만 바꿔서 기존 링크를 막을 수 있고, 이미 발급된 패스는 그대로 쓸 수 있습니다.

## 회고

1주라는 짧은 일정이라 기능 목록보다 **"행사 당일에 무엇이 잘못될 수 있을까"**를 먼저 적어두고 시작했습니다. 같은 와이파이의 수백 명, 알림톡 못 받은 사람, 동시에 찍은 QR, 배터리가 꺼진 폰처럼 현장에서 생길 만한 상황을 하나씩 떠올리고, 각각을 코드로 막을지 관리자 화면에서 해결하게 할지 고민을 많이 했습니다.

플로우를 짜는 데는 예전에 팝업 현장에서 입장 업무를 많이 봤던 경험이 큰 도움이 됐습니다. 참여자들이 네이버 폼 같은 곳으로 신청하고 현장에 왔을 때 입구에서 어떤 일들이 생기는지, 입장 처리가 실제로 어떤 순서로 흘러가는지를 직접 겪어봤기에, 화면을 설계할 때 현장 스태프와 참여자 입장에서 먼저 생각해볼 수 있었습니다.
