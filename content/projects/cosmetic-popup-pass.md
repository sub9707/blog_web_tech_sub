## 프로젝트 개요

코스메틱 B사가 서울 소재 대학 네 곳을 돌며 여는 제품 팝업 행사의 **사전 참여 플랫폼**입니다.

참가자는 대학 커뮤니티에 올라온 전용 링크로 들어와 스킨케어 설문 5문항에 답하고 이름과 연락처를 남기면, 카카오 알림톡으로 **팝업 행사장 입장용 디지털 패스(QR)**를 받습니다. 행사 당일에는 현장 스태프가 휴대폰 카메라로 QR을 찍어 바로 입장 처리하고, 운영 측은 대학별 발급 현황과 설문 응답 결과를 대시보드와 엑셀로 확인합니다.

참가자 화면, 스태프 스캐너, 관리자 대시보드를 모두 **Cloudflare Workers 하나**에 올려 화면과 API를 함께 띄웠습니다.

### 기술 스택

- **FE**: React 19, TypeScript, Vite 6, React Router 7, Tailwind CSS 4, shadcn/ui, React Hook Form, Zod
- **BE / 인프라**: Cloudflare Workers, Hono, Cloudflare D1 + Drizzle ORM, Workers Rate Limiting, Cloudflare Turnstile
- **인증 / 보안**: JWT(jose) + httpOnly 쿠키 세션, bcryptjs, Web Crypto(AES-256-GCM, HMAC-SHA256, SHA-256)
- **외부 연동 / QR**: Solapi 카카오 알림톡, qrcode(SVG 렌더), qr-scanner(카메라 스캔)

## 기술 목표

- **대학별 선착순 정원을 정확히 지키기** — 수백 명이 동시에 신청해도 정원보다 많이 발급되지 않도록 처리
- **개인정보를 그대로 저장하지 않기** — 이름과 연락처는 암호화해 저장하고, QR에는 개인정보 없이 무작위 값만 담기
- **알림톡이 실패해도 신청은 끝까지 되게 하기** — 알림톡 발송이 실패해도 신청과 패스 발급은 정상 완료하고, 실패한 건은 따로 표시
- **현장에서 막히지 않는 입장 처리** — QR 찍기 → 확인 → 결과 표시 → 다음 QR까지 멈춤 없이 이어지는 스캐너

## 고민했던 점들

### 선착순 정원 동시성 문제

대학별 정원(`capacity`)과 지금까지 발급한 수(`issued_count`)를 같은 줄에 두고, 신청이 들어오면 **"발급 수가 정원보다 적을 때만 1 더하기"를 쿼리 한 번으로** 처리했습니다. D1은 쓰기 요청을 하나씩 차례로 처리하기 때문에, 따로 잠금을 걸지 않아도 여러 명이 동시에 신청해서 정원을 넘기는 일이 생기지 않습니다. 이 쿼리로 바뀐 줄이 없으면 정원이 찬 것으로 보고 마감 안내를 보냅니다.

자리를 먼저 잡은 뒤 참가자 저장이 실패하면(이미 신청한 번호, 일시적인 오류 등) 발급 수를 다시 1 줄여 자리를 돌려줍니다. 관리자가 참가자를 삭제할 때도 마찬가지입니다. 대시보드에서는 실제 참가자 수와 발급 수 기준 남은 정원을 따로 계산하는데, 자리를 돌려주는 처리가 어디선가 빠지면 두 숫자가 달라져 바로 눈에 띕니다.

참가자 정보와 설문 답변은 한 번에 같이 저장해서, 참가자만 저장되고 답변이 빠지는 일이 없게 했습니다.

### 개인정보처리

이름과 연락처는 관리자 화면에서 다시 보여줘야 해서, 되돌릴 수 없는 해시가 아니라 되돌릴 수 있는 **AES-256-GCM**으로 암호화했습니다. 문제는 이 방식이 같은 번호라도 암호화할 때마다 결과가 달라진다는 점입니다. 그래서 DB에서 "같은 번호로 두 번 신청했는지"를 비교할 수 없었습니다.

그래서 연락처는 암호문과 별도로 **"같은 번호면 항상 같은 값이 나오는 해시(HMAC-SHA256)"**를 하나 더 저장하고, "한 행사에 이 값은 하나만"이라는 제약을 DB에 걸었습니다. 같은 번호로 거의 동시에 두 번 제출해도 DB가 한 건만 받아줍니다.

현장 검색 방식은 한 번 바꿨습니다. 처음에는 이름에도 같은 해시를 두었는데, 이름을 정확히 다 입력해야만 찾을 수 있어서 현장에서 쓰기 불편했습니다. 결국 이름 해시를 없애고, 행사 참가자 정보를 서버에서 풀어가며 일부만 입력해도 찾히게 바꿨습니다(8,000명 기준 약 0.5초). 숫자만 입력하면 이름은 풀지 않고 연락처만 확인하고, 고객번호 4자리는 참가자 ID 앞자리라서 암호를 풀 필요 없이 바로 찾습니다. 저장하는 개인정보 관련 값이 하나 줄어든 것도 장점이었습니다.

QR에는 개인정보를 넣지 않고 무작위 값(`crypto.randomUUID()`)만 담았습니다. QR을 찍으면 이 값을 해시로 바꿔 참가자를 찾습니다.

### 스태프와 관리자 권한 분리

로그인하는 사람은 스태프와 관리자로 나눴습니다. 둘은 일하는 환경부터 다릅니다. 스태프는 행사 당일 입구에 서서 휴대폰 하나로 계속 QR을 찍는 현장 인력이고, 여러 명입니다. 관리자는 운영 측 몇 명이 행사 전후로 현황을 보고 설정을 바꾸는 역할입니다.

입구에서 쓰는 휴대폰은 잃어버리거나, 잠깐 내려놓은 사이 누가 보거나, 여러 사람이 계정을 돌려 쓰기 쉽습니다. 그래서 스태프에게는 **"지금 눈앞의 참가자를 입장시키는 데 필요한 것"만** 열어두고, 전체 명단이나 통계처럼 새어 나가면 피해가 큰 기능은 관리자만 쓰게 했습니다.

| 기능 | 스태프 | 관리자 |
| --- | :---: | :---: |
| QR 스캔 입장 처리 | O | O |
| 오늘 입장 명단 조회,정보 수정,입장 취소,삭제 | O | O |
| 행사 전체 참가자 검색 | X | O |
| QR 없이 직접 입장 처리, 입장 시각 수정 | X | O |
| 통계, 설문 응답 결과 | X | O |
| CSV 내보내기 (참여자 명단 포함) | X | O |
| 대학별 배포 링크 확인 | X | O |
| 모집 마감일,정원,행사 기간 설정 | X | O |

- **스태프 명단은 오늘 입장한 사람만** — 스태프 화면의 명단에는 오늘 이미 입장한 참가자만 나옵니다. 스태프 폰으로 볼 수 있는 개인정보는 오늘 입구를 지나간 사람까지이고, 수천 명의 사전 신청자 명단은 볼 수 없습니다.
- **QR 없는 입장 처리는 관리자만** — QR 없이 입장시키는 건 이름과 연락처만 보고 본인인지 판단해야 하는 일이라, 전체 검색 권한과 함께 관리자에게만 줬습니다. 이렇게 처리한 입장도 누가 했는지 기록에 남습니다.
- **배포 링크와 명단 파일은 관리자만** — 대학별 링크와 개인정보가 담긴 CSV는 한번 새어 나가면 되돌리기 어려워서, 관리자로 로그인해야만 받을 수 있게 했습니다.

로그인 기능과 계정 테이블은 하나로 두고, 계정마다 역할(`STAFF`/`ADMIN`)만 구분했습니다. 로그인하면 역할이 담긴 토큰(JWT)을 쿠키로 내려주고, 근무 교대 시간에 맞춰 12시간 뒤 만료되게 했습니다. 로그인 후에는 역할에 따라 스캐너나 대시보드로 이동하고, 관리자가 스태프 화면 주소로 들어오면 관리자 화면으로 보냅니다.

다만 이렇게 화면을 나눠 보여주는 건 편의를 위한 것이고, 진짜 권한 확인은 서버에서 합니다. 스태프 API는 로그인 여부와 그 행사 담당인지를 확인하고, 관리자 API는 여기에 더해 관리자 계정이 아니면 거절합니다. 화면에서 메뉴를 숨겨도 API는 직접 부를 수 있기 때문에, 요청이 올 때마다 서버에서 다시 확인하도록 했습니다.

### 봇 방지 — IP 제한을 걸지 않은 이유

신청 API에는 보통 "같은 IP에서 너무 많이 요청하면 막기"를 걸어두는데, 이번에는 참가자 신청 쪽에 **일부러 걸지 않았습니다.** 참가자 대부분이 같은 학교 와이파이나 같은 통신사 망을 쓸 가능성이 있기에, 수백 명이 하나의 IP를 가지는 최악의 상황을 가정했습니다. IP 제한을 걸면 정상 참가자끼리 서로를 막게 됩니다.

대신 봇은 **Turnstile**로 막고, 같은 번호로 여러 번 신청하는 건 앞에서 말한 연락처 제약으로 막도록 나눴습니다. 요청 횟수 제한은 대상이 분명한 곳에만 걸었습니다.

- **스태프, 관리자 로그인** — 사용하는 사람이 적고 Turnstile이 없어서, IP 기준 1분에 10번까지
- **패스 페이지의 입장 여부 확인** — IP가 아니라 참가자 기준 1분에 60번까지. 입구에 줄 선 사람들이 같은 망을 써도 서로 영향이 없고, 비정상적으로 요청을 쏟아내는 경우만 막힙니다.

횟수 제한 기능 자체에 문제가 생기면 요청을 막지 않고 통과시키고 기록만 남깁니다. 막는 장치가 고장 났다고 서비스 전체가 멈추면 안 되기 때문입니다.

### 알림톡 실패

알림톡 발송 코드는 어떤 경우에도 에러로 멈추지 않고 '성공' 또는 '실패' 결과만 돌려줍니다. 발송에 실패해도 신청과 패스 발급은 정상 완료되고, 실패한 건은 따로 표시되어 대시보드에서 볼 수 있습니다.

알림톡 설정값이 하나라도 비어 있으면 테스트용 가짜 발송으로 넘기지 않고 '실패'로 기록하게 했습니다. 가짜 발송은 '성공'으로 기록되기 때문에, 실제로는 안 보낸 걸 보낸 것처럼 남겨서 다시 보내야 할 사람을 놓치게 됩니다. 발송 실패 기록에는 연락처를 가려서 남깁니다.

실패를 놓치지 않도록 확인할 곳은 두 군데로 정했습니다. 하나는 관리자 참여자 명단의 발송 상태이고, 다른 하나는 Cloudflare Workers의 관측 가능성(Observability) 로그입니다. 로그에서 error만 따로 걸러 보면서, 지난 시간 동안 발송 실패나 서버 오류가 있었는지 바로 확인할 수 있게 했습니다.

알림톡이 아예 닿지 않는 경우도 있었습니다. 카카오 채널을 차단했거나, 외국인 교환학생처럼 카카오톡을 쓰지 않는 참가자입니다. 이런 경우에는 Solapi 문자메시지 발송에서 알림톡을 받지 못한 참가자에게 고객번호와 입장 안내 문구를 문자로 보냈습니다.

그래도 알림톡을 끝내 못 받는 참가자가 있을 수 있어서, 신청 완료 화면에 "이 화면이 보인다면 신청은 이미 끝났으니, 현장 스태프에게 이름과 연락처를 말하면 입장을 도와드린다"는 안내를 넣었습니다. 이후 관리자 페이지의 현장 검색과 직접 입장 처리 기능으로 해결합니다.

### 같은 QR을 두 명이 동시에 찍을 경우

입장 처리도 "아직 입장 기록이 없을 때만 입장 시각을 기록"하도록 쿼리 한 번으로 처리했습니다. 두 스태프가 같은 QR을 거의 동시에 찍어도 한 명만 성공하고, 다른 한 명에게는 '이미 입장한 고객'으로 나옵니다. 입장 기록은 따로 남겨서 누가 언제 입장시켰는지 확인할 수 있게 했습니다.

### 배포 링크 분기

배포 링크에는 대학 이름 대신 무작위 10자리 코드를 붙였습니다. 링크 코드로는 그 대학 정보만 조회할 수 있고, 전체 대학 목록을 알려주는 공개 API는 만들지 않았습니다. 잘못된 코드든 없는 행사든 똑같이 404로 응답해서 코드를 찍어 맞추기 어렵게 했습니다.

통계와 CSV에는 사람이 알아볼 수 있는 대학 코드를 따로 씁니다. 링크가 엉뚱한 곳에 퍼지면 링크 코드만 바꿔서 기존 링크를 막을 수 있고, 이미 발급된 패스는 그대로 쓸 수 있습니다.

### Workers 배포에서 만난 문제

배포 후 관리자 화면에서 CSV 다운로드 링크를 누르면 404 페이지가 뜨는 문제가 있었습니다. 링크를 누르는 요청은 브라우저가 "페이지를 보여달라"는 요청으로 보내기 때문에, API보다 React 화면 쪽이 먼저 받아버리고 모르는 주소라며 404를 띄운 것이었습니다. 버튼으로 호출하는 다른 API는 정상이라 원인을 찾는 데 시간이 걸렸습니다. `run_worker_first: ["/api/*"]` 설정으로 `/api/`로 시작하는 주소는 항상 API가 먼저 받도록 해서 해결했습니다.

## 회고

1주라는 짧은 일정이라 기능 목록보다 **"행사 당일에 무엇이 잘못될 수 있을까"**를 먼저 적어두고 시작했습니다. 같은 와이파이의 수백 명, 알림톡 못 받은 사람, 동시에 찍은 QR, 배터리가 꺼진 폰처럼 현장에서 생길 만한 상황을 하나씩 떠올리고, 각각을 코드로 막을지 관리자 화면에서 해결하게 할지 고민을 많이 했습니다.

플로우를 짜는 데는 예전에 팝업 현장에서 입장 업무를 많이 봤던 경험이 큰 도움이 됐습니다. 참가자들이 네이버 폼 같은 곳으로 신청하고 현장에 왔을 때 입구에서 어떤 일들이 생기는지, 입장 처리가 실제로 어떤 순서로 흘러가는지를 직접 겪어봤기에, 화면을 설계할 때 현장 스태프와 참가자 입장에서 먼저 생각해볼 수 있었습니다.
