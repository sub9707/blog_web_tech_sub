## 프로젝트 개요

[바이오던스 팝업 디지털 패스](/portfolio/바이오던스-팝업-디지털-패스)와 같은 행사에서 쓴 **현장용 설문 키오스크**입니다.

디지털 패스는 참가자가 행사 전에 자기 휴대폰으로 설문에 답하고 입장용 QR을 받는 웹 서비스였다면, 키오스크는 팝업 현장에 세워둔 세로형 터치 모니터에서 방문객이 바로 설문에 답하고 그 자리에서 **나에게 맞는 스킨케어 루틴 추천**을 받는 Windows 앱입니다. 설문 문항은 같고, 쓰는 장소와 사람, 기기가 달라서 만드는 방식도 많이 달라졌습니다.

## 웹 설문(디지털 패스)과 달라진 점

| | 디지털 패스 (웹) | 설문 키오스크 (Electron) |
| --- | --- | --- |
| **사용 장소** | 행사 전, 참가자 본인 휴대폰 | 행사 당일, 현장에 세워둔 터치 모니터 |
| **사용하는 사람** | 한 사람이 한 번 | 하루 종일 여러 사람이 번갈아 가며 |
| **결과** | 입장용 QR 발급, 카카오 알림톡 | 그 자리에서 스킨케어 루틴 추천 화면 |
| **개인정보** | 이름, 연락처 (암호화 저장) | 수집하지 않음, 답변과 추천 결과만 저장 |
| **서버** | Cloudflare Workers + D1 | 없음, 기기 안 파일에 저장 |
| **언어** | 한국어 | 한국어, 중국어, 일본어, 영어 |
| **집계** | 관리자 대시보드, CSV | 설정 화면에서 참여자 수 확인, Excel 내보내기 |

가장 큰 차이는 **"한 대의 기기를 하루 종일, 수백 명이 돌아가며 쓴다"**는 점이었습니다. 웹은 각자 자기 폰에서 한 번 쓰고 끝나지만, 키오스크는 앱 하나가 아침부터 저녁까지 꺼지지 않고 같은 흐름을 계속 반복합니다. 그래서 기능보다는 **오래 켜둬도 느려지지 않는지, 중간에 꺼져도 기록이 남는지, 스태프가 없어도 혼자 잘 돌아가는지**에 더 많이 신경 썼습니다.

인터넷 없이 동작하게 만든 것도 같은 이유입니다. 야외 팝업은 와이파이가 불안정한 경우가 많고, 키오스크는 개인정보를 받지 않으니 서버에 바로 올릴 필요도 없었습니다. 참여 기록은 기기 안 파일에 쌓아두고, 필요할 때 Excel로 뽑아 전달하는 방식으로 정했습니다.


## 화면 흐름

메인 → 설문 5문항 → 추천 로딩 → 결과 → 처음으로

- **메인** — 화면 어디를 눌러도 시작합니다. 대형 터치 모니터 앞에서는 '시작하기' 배너만 정확히 누르는 사람보다 모델 사진이나 화면 아무 곳이나 누르는 사람이 많아서, 화면 전체를 하나의 시작 버튼으로 만들었습니다. 우측 상단에서 언어를 고를 수 있습니다.
- **설문** — 웹과 같은 4지선다 5문항입니다. 선택지를 누르면 0.3초 뒤 다음 문항으로 넘어가고, 문항 길이가 달라도 선택지 위치가 흔들리지 않게 문항 자리 높이를 미리 잡아뒀습니다.
- **추천 로딩, 결과** — 가장 많이 고른 보기(A~D)로 추천 루틴을 정하고, 2.2초 정도 로딩 연출 뒤에 결과 화면과 함께 컨페티를 터뜨립니다. 결과 화면이 뜨는 순간 참여 기록이 저장됩니다.
- **처음으로** — 메인으로 돌아가면서 언어도 한국어로 되돌려 다음 방문객이 이전 사람의 설정을 이어받지 않게 했습니다.

## 행사장 키오스크 기기

### 키오스크 모드와 꺼지지 않는 화면

설치된 앱은 창 테두리 없이 전체화면 키오스크 모드로 뜹니다. 방문객이 앱을 끄거나 다른 화면으로 나갈 수 없게, 페이지 이동이나 새 창 열기도 막았습니다.

- **화면 꺼짐 방지** — Windows 절전 설정 때문에 행사 중에 화면이 꺼지거나 잠금 화면으로 넘어가지 않게 `powerSaveBlocker`로 막았습니다.
- **앱은 하나만 실행** — 터치 모니터에서 바탕화면 아이콘을 두 번 누르면 앱이 두 개 뜰 수 있습니다. 두 앱이 같은 참여번호 파일을 동시에 쓰면 번호가 겹치기 때문에, 두 번째 실행은 막고 기존 창을 앞으로 가져오게 했습니다.
- **상단바 켜고 끄기** — 설치나 점검할 때는 창을 옮기고 줄여야 해서, 설정 화면에서 창 상단바를 다시 보이게 할 수 있습니다. Electron은 창을 만들 때만 테두리 여부를 정할 수 있어서, 켜고 끌 때마다 창을 새로 만들고 이전 창을 닫는 방식으로 처리했습니다.

### 어떤 모니터에서도 같은 화면

설치되는 모니터의 해상도와 상관없이 같은 화면이 나와야 했습니다. 그래서 **810 x 1440(9:16) 크기를 기준으로 화면을 그리고, 실제 창 크기에 맞춰 통째로 늘리거나 줄이는** 방식을 썼습니다. 해상도가 달라져도 글자 크기와 이미지 비율이 디자인 시안과 똑같이 나옵니다.

모니터 비율이 9:16과 딱 맞지 않을 때는 바깥에 여백을 칠하지 않고, 남는 방향으로 화면을 조금 늘려서 각 화면 배경으로 채웠습니다. 화면마다 배경색이 달라서 여백을 한 색으로 칠하면 경계가 드러나기 때문입니다. 비슷한 이유로, 소수 배율로 늘리면 띠 양 끝에 얇은 흰 선이 생기는 문제가 있어서 상하단 분홍 띠 아래 바탕까지 분홍으로 깔았습니다.

### 대형 터치 모니터에 맞춘 누름 처리

일반 모니터에서는 문제없던 버튼이 대형 터치 모니터에서는 잘 안 눌렸습니다. 원인은 두 가지였습니다.

- **꾹 누르면 우클릭** — Windows 터치는 길게 누르면 우클릭으로 처리해서 클릭이 생기지 않습니다.
- **손가락이 살짝 밀리면 취소** — 누르는 동안 손가락이 조금만 움직여도 브라우저가 스크롤로 판단해 클릭을 취소합니다.

그래서 버튼마다 `onClick` 대신 **"누른 시간이나 중간 움직임과 상관없이, 손을 뗀 위치가 그 버튼 위면 누른 것으로 친다"**는 공통 처리(`pressHandlers`)를 만들어 붙였습니다. 손가락이 버튼 밖으로 나갔다 들어와도 뗄 때 신호를 그 버튼이 받도록 했습니다. 여기에 더해 화면 전체에서 스크롤, 확대 제스처, 우클릭 메뉴, 글자 선택, 이미지 끌기를 모두 껐습니다. 스크롤이 필요한 설정 화면 목록만 다시 켰습니다.

버튼 배치도 기기에 맞췄습니다. 세로형 대형 모니터는 화면 위쪽이 손에 잘 닿지 않아서 '이전', '처음으로' 같은 이동 버튼을 모두 아래쪽에 모았습니다. 결과 화면의 '처음으로'는 눈에 띄지 않게 작게 두되, 누를 수 있는 영역만 사방 20px씩 넓혀 대충 눌러도 되게 했습니다.

### 연타와 화면 전환 사이 꼬임 방지

여러 사람이 지켜보는 앞에서 빠르게 누르는 경우가 많아서, 연타로 화면이 꼬이지 않게 막았습니다.

- 선택지를 누르고 다음 문항으로 넘어가는 0.3초 동안은 입력을 막아 문항이 두 칸씩 넘어가지 않게 했습니다.
- 마지막 문항을 고르자마자 '처음으로'를 누르면, 메인으로 돌아갔다가 기다리던 타이머 때문에 로딩 화면으로 넘어가고 결과까지 저장되는 문제가 있었습니다. 화면을 떠날 때 넘김 타이머를 반드시 취소하도록 고쳤습니다.

### 4개 국어

팝업 현장에는 외국인 관광객도 많이 옵니다. 디지털 패스 때 카카오톡을 쓰지 않는 외국인 참가자가 있었던 것처럼, 키오스크도 한국어만으로는 부족해서 **중국어, 일본어, 영어**를 추가했습니다.

- 언어 버튼은 각 언어 사용자가 바로 알아보도록 그 언어로 적었습니다 (한국어, 中文, 日本語, English).
- 화면 언어에 맞춰 `<html lang>`을 바꿔서 중국어, 일본어에서 한자 글꼴과 줄바꿈이 그 언어에 맞게 나오게 했습니다.
- 답변은 언어와 상관없이 **보기 라벨(A~D)로만 저장**하고, 추천 결과도 한국어 기준 이름으로 저장했습니다. 그래야 Excel 통계가 언어별로 쪼개지지 않습니다.
- 결과 설명 문구는 디자인대로 줄 구성을 유지해야 해서, 외국어 문장이 길어 칸을 넘으면 넘지 않을 때까지 글자 크기를 조금씩 줄이게 했습니다. 결과 화면 폰트는 처음 쓰일 때 불러오기 때문에, 폰트가 다 들어온 뒤에 한 번 더 맞춥니다.

### 효과음

버튼, 시작, 로딩, 결과에 효과음을 넣었습니다. `<audio>` 태그로 틀면 누를 때마다 살짝 늦게 나고 연타하면 소리가 씹혀서, **앱을 켤 때 모든 효과음을 미리 불러와 두고 Web Audio로 바로 재생**하게 했습니다. 로딩, 결과처럼 파일 두 개를 겹쳐 내는 효과음은 같은 시각에 시작하도록 예약해서 정확히 동시에 나옵니다.

행사장마다 주변 소음이 달라서 음량과 음소거는 설정 화면에서 바꿀 수 있고, 앱을 다시 켜도 유지됩니다.

## 참여 기록을 잃지 않기

서버 없이 기기 안 파일에 저장하다 보니, 가장 걱정한 건 **전원이 갑자기 꺼지거나 앱이 죽었을 때 기록이 날아가는 것**이었습니다.

### 저장 방식

- **날짜별 JSONL 파일에 한 줄씩 추가** — 참여 한 건이 끝날 때마다 그날 파일 끝에 한 줄을 붙이고, 바로 디스크에 확실히 쓰도록(`fsync`) 했습니다. 파일 전체를 다시 쓰지 않으니 쓰는 도중 꺼져도 이전 기록은 그대로 남습니다.
- **반쯤 쓰인 줄은 건너뛰기** — 그래도 마지막 줄이 반만 쓰인 채 꺼질 수 있어서, 읽을 때 깨진 줄은 건너뛰고 로그에만 남깁니다. 한 줄 때문에 전체 통계가 안 열리는 일은 없습니다.
- **참여번호 파일은 통째로 바꿔치기** — 참여번호는 임시 파일에 먼저 쓰고 디스크에 확실히 쓴 다음 이름을 바꿔 덮어씁니다. 쓰는 도중 꺼져도 번호 파일이 반쯤 쓰인 채로 남지 않습니다.
- **번호 파일이 없거나 깨졌을 때** — 번호가 1부터 다시 시작해 겹치지 않도록, 저장된 기록 중 가장 큰 번호를 찾아 거기서 이어갑니다. 평소에는 매번 전체 기록을 읽지 않고, 이런 경우에만 훑습니다.
- **저장은 한 건씩 차례로** — 저장 요청이 겹쳐 들어와도 번호 발급과 기록을 한 건씩 줄 세워 처리해서 번호가 겹치지 않게 했습니다.

### 저장이 실패했을 때

화면 쪽에서도 저장이 조용히 사라지지 않게 했습니다.

1. 저장에 실패하면 1초, 3초 뒤에 두 번 더 시도합니다.
2. 그래도 안 되면 기기 브라우저 저장소(`localStorage`)에 따로 보관해 둡니다. 다시 시도할 때 처음 참여한 시각이 바뀌지 않도록 완료 시각도 같이 보관합니다.
3. 보관해 둔 기록은 앱을 다시 켤 때, 그리고 다음 저장이 성공할 때 다시 저장합니다.
4. 설정 화면에 "저장 대기 중인 참여 기록 N건"과 '다시 저장' 버튼이 떠서 스태프가 바로 알 수 있습니다.

## 하루 종일 켜두는 앱 — 누적 성능 관리

### 결과가 쌓일수록 느려지는 문제

행사 현장에서 참여가 수십 건 쌓이자 **앱 반응이 점점 늦어지고 버튼이 가끔 안 먹히는** 증상이 나왔습니다. 개발하면서 한두 번 눌러볼 때는 전혀 드러나지 않았고, 같은 흐름을 계속 반복해야만 보이는 문제였습니다.

사람이 직접 수십 번씩 설문을 돌려보며 원인을 찾기는 어려워서, **AI(Claude Code)로 원인을 좁히고, 반복 테스트를 자동으로 돌려서 숫자로 확인**하는 방식으로 접근했습니다.

### AI로 원인 찾고 반복 누적 테스트하기

#### 1. 코드를 바로 고치지 않고 원인 후보부터 정리

AI에게 "수십 건 누적되면 느려지고 버튼이 안 먹힌다"는 현장 증상을 그대로 전달하고, **코드는 고치지 말고 원인 분석과 해결 계획만** 먼저 달라고 했습니다. 메인 프로세스(저장, 번호, 로그), React 상태와 타이머, 이벤트 리스너, 이미지와 애니메이션을 훑어서 원인 후보를 확신도 순으로 정리했습니다.

- **세션마다 쌓이는 것** — 결과 화면이 뜰 때마다 화면 크기만 한 컨페티 캔버스를 새로 만들어 백그라운드 작업(Worker)으로 넘기는 부분. 4K 세로 화면이면 한 장에 약 33MB입니다. 가장 유력했지만 아직 가설이었습니다.
- **쌓이지는 않지만 느리게 느껴지는 것** — 결과 화면의 계속 도는 장식 애니메이션, 큰 PNG 이미지 등
- **성능과 별개로 버튼이 안 먹히는 것** — 터치가 `click`에만 의존해서, 길게 누르거나 손가락이 밀리면 클릭이 생기지 않는 문제

마지막 항목은 현장에서 실제로 "길게 누르거나 밀릴 때 안 먹혔다"는 걸 확인해서, 성능 문제와 함께 고칠 항목으로 올렸습니다. 이 내용이 위의 [대형 터치 모니터에 맞춘 누름 처리](#대형-터치-모니터에-맞춘-누름-처리)입니다.

#### 2. 의심 가는 부분만 떼어내서 실측

가설을 확인하려고 앱 전체가 아니라 **컨페티 부분만 떼어낸 작은 Electron 테스트 앱**을 만들었습니다. 프로젝트와 같은 Electron, canvas-confetti 버전으로, 결과 화면처럼 캔버스를 만들고, 컨페티를 터뜨리고, 지우는 과정을 60번 반복하면서 10번마다 `app.getAppMetrics()`로 프로세스별 메모리를 찍었습니다. 지금 방식(매번 새 캔버스)과 고칠 방식(캔버스 하나 재사용)을 똑같은 조건으로 각각 돌렸습니다.

| 반복 횟수 | 지금 방식 (매번 새 캔버스) | 캔버스 하나 재사용 |
| --- | ---: | ---: |
| 시작 | 83MB | 83MB |
| 10회 | 568MB | 151MB |
| 30회 | 1,245MB | 151MB |
| 60회 | 2,335MB | 183MB |
| 이후 15초 대기 | 2,270MB | 183MB |

*GPU 프로세스 메모리 기준, 4K 세로 화면 가정, 개발 PC에서 측정*

지금 방식은 **한 번 돌 때마다 GPU 메모리가 약 37MB씩 늘고, 기다려도 줄어들지 않았습니다.** 하루 수백 명이 참여하는 행사라면 사양이 좋은 PC여도 느려지는 시점이 늦춰질 뿐, 결국 한계에 닿는 구조였습니다. 반면 화면 쪽(렌더러) 메모리는 두 방식 모두 40MB 안팎으로 차이가 없어서, 원인이 React 코드가 아니라 캔버스라는 것도 같이 확인됐습니다.

#### 3. 수정

**컨페티 캔버스와 인스턴스를 앱 전체에서 하나만 만들어 계속 다시 쓰도록** 바꿨습니다. 캔버스는 결과 화면이 아니라 앱 최상단에 항상 띄워 두고, 결과 화면은 그걸 빌려 쓰기만 합니다. 캔버스 해상도도 실제 모니터 크기가 아니라 기준 화면 크기(810 x 1440 안팎)로 고정해서, 큰 모니터에 연결해도 메모리가 더 들지 않고 컨페티가 퍼지는 모양도 시안과 같게 나옵니다.

#### 4. 실제 빌드된 앱을 자동으로 53번 돌리기

떼어낸 테스트만으로는 부족해서, 수정 후에는 **실제로 설치되는 빌드 결과물을 그대로 띄워 사람 대신 자동으로 설문을 반복**하게 했습니다. 방법은 이렇습니다.

1. 빌드된 앱을 `--remote-debugging-port` 옵션으로 실행하고, 테스트 스크립트(Node.js)가 Chrome DevTools Protocol(CDP)로 앱에 연결합니다.
2. 마우스 클릭이 아니라 CDP의 **터치 이벤트**(`Input.dispatchTouchEvent`)로 화면을 누릅니다. 메인 화면 시작부터 문항 5개 선택, 결과 화면, '처음으로'까지 한 바퀴를 한 세션으로 보고, 화면 위치는 실제 버튼 좌표를 읽어와 누릅니다.
3. 터치 방식도 섞었습니다. 짧게 누르기 외에 **1.5초 길게 누르기**, **누른 채로 35px 밀었다 떼기**로도 한 바퀴씩 돌리고, 선택지 A를 누른 채 C 위에서 떼면 아무것도 선택되지 않아야 한다는 반대 경우도 확인했습니다.
4. 10세션마다 Windows 프로세스 정보에서 GPU 프로세스와 렌더러 메모리를 기록하고, 50세션째에는 메인 화면에서 기다렸다가 자동 새로고침이 실제로 일어나는지 확인합니다.
5. 끝나면 저장된 기록 줄 수가 돌린 세션 수와 같은지, 캔버스가 정말 하나만 남아 있는지 확인합니다.

실제 참여 기록이 섞이면 안 되기 때문에, 테스트용 앱은 `--user-data-dir`로 **별도 데이터 폴더**를 쓰게 하고, 그 폴더가 제대로 쓰이는지 먼저 확인한 다음에만 테스트를 진행하도록 했습니다.

| 시점 | GPU 프로세스 | 렌더러 |
| --- | ---: | ---: |
| 시작 | 123MB | 49MB |
| 10세션 | 460MB | 107MB |
| 30세션 | 482MB | 115MB |
| 50세션 | 477MB | 121MB |
| 자동 새로고침 후 | 293MB | 138MB |

- **GPU 메모리** — 10세션 이후 420~480MB에서 더 늘지 않았습니다. 수정 전 방식이었다면 50세션 즈음 GB 단위였을 구간입니다.
- **터치** — 길게 누르기, 밀면서 누르기 모두 끝까지 정상 진행됐고, 다른 버튼 위에서 떼면 무시됐습니다.
- **자동 새로고침, 저장** — 50세션 뒤 메인 화면에서 새로고침이 일어났고, 이후 세션도 정상이었습니다. 53건 모두 빠짐없이 저장됐습니다.

#### 5. 이 테스트의 한계

- 테스트는 세션 사이 간격이 실제보다 훨씬 짧고, 터치도 실제 패널이 아니라 흉내 낸 터치 이벤트입니다. Windows가 길게 누르기를 우클릭으로 바꾸는 동작은 실기기에서만 나오기 때문에, 이 부분은 현장 기기에서 직접 눌러보며 확인해야 했습니다.
- 그래서 현장에서도 같은 걸 볼 수 있도록 아래 메모리 로그를 함께 넣었습니다. 테스트에서 본 숫자와 현장 로그의 숫자를 나란히 비교할 수 있습니다.

### 50명마다 조용히 새로고침

원인은 고쳤지만, 하루 종일 켜두는 동안 다른 곳에서 메모리가 조금씩 쌓일 가능성까지 없앨 수는 없었습니다. 그래서 안전장치로 **참여가 50건 끝날 때마다, 메인 화면에서 5초 동안 아무도 만지지 않으면 화면을 새로 불러오게** 했습니다.

- 그 5초 사이에 누가 화면을 만지면 이번에는 건너뛰고, 다음에 메인으로 돌아올 때 다시 시도합니다. 방문객이 쓰는 도중에 화면이 바뀌는 일은 없습니다.
- 저장 대기 중인 기록과 음량 설정은 `localStorage`에 있어서 새로고침해도 그대로 남습니다.

### 현장에서 무슨 일이 있었는지 나중에 알 수 있게

현장에서 "아까 좀 느렸다", "화면이 깜빡였다" 같은 이야기를 들어도, 행사가 끝난 뒤에는 원인을 다시 볼 방법이 없습니다. 그래서 앱이 스스로 기록을 남기게 했습니다.

- **5분마다 메모리 기록** — 프로세스별 메모리, 켜진 지 몇 분째인지, 지금까지 참여 몇 건째인지를 한 줄로 남깁니다. 로그만 보고 "몇 건째부터 메모리가 늘었는지"를 확인할 수 있습니다.
- **GPU 가속 상태** — GPU 프로세스가 여러 번 죽으면 Chromium이 소프트웨어 렌더링으로 내려가서 화면 전체가 느려집니다. 그 상태인지도 같이 기록합니다.
- **화면 오류도 같은 파일에** — 화면 쪽 오류는 원래 메인 프로세스 로그에 안 잡혀서, 콘솔 오류를 그대로 로그 파일에 옮겨 적었습니다. 앱 시작, 화면 새로고침, 응답 없음, 하위 프로세스 종료도 함께 남습니다.
- 로그는 날짜별 파일로 남고, 로그를 쓰다가 실패해도 앱 동작에는 영향이 없게 했습니다.

### 화면이 죽었을 때 스스로 살아나기

화면을 그리는 렌더러 프로세스가 죽으면 Electron 창은 흰 화면으로 멈춥니다. 스태프가 바로 알아채지 못하면 그 시간 동안 키오스크는 아무 쓸모가 없습니다. 그래서 **렌더러가 죽으면 기록을 남기고 바로 다시 불러오게** 했습니다. 다만 시작하자마자 계속 죽는 경우 무한 재시작에 빠지지 않도록, 1분에 3번까지만 시도합니다.

## 운영자 편의

현장 스태프는 개발자가 아니고, 키오스크 옆에 계속 붙어 있지도 않습니다. 그래서 필요한 기능은 앱 안에서 다 할 수 있게 했습니다.

- **숨겨둔 관리 버튼** — 메인 화면 하단에 작고 흐린 설정, 종료 버튼을 뒀습니다. 방문객 눈에는 잘 띄지 않고, 스태프는 손이 닿는 아래쪽이라 편하게 누를 수 있습니다. 설정은 숫자 비밀번호를 입력해야 열리고, 종료는 키오스크 모드라 OS 확인창 대신 직접 만든 확인창을 띄웁니다.
- **참여자 수 확인** — 오늘 참여자 수와 날짜별 참여자 수를 바로 볼 수 있습니다.
- **Excel 내보내기** — 참여 데이터, 일자별 통계(추천 제품별 수 포함), 전체 통계 세 개 시트로 나눠 저장합니다. 실패하면 "같은 이름의 파일이 열려 있습니다", "USB 연결을 확인하세요"처럼 스태프가 바로 알아들을 수 있는 말로 알려줍니다.
- **데이터 폴더 열기** — 참여 기록, 참여번호, 로그가 들어 있는 폴더를 탐색기로 바로 엽니다. 문제가 생겼을 때 스태프에게 폴더째 받아서 확인할 수 있습니다.
- **효과음, 상단바 설정** — 행사장 상황에 맞춰 음량과 음소거를 바꾸고, 점검할 때는 상단바를 켜서 창을 다룰 수 있습니다.

## 회고

디지털 패스와 같은 설문이라 처음에는 화면만 옮기면 될 거라고 생각했는데, 실제로는 **"한 대의 기기를 하루 종일, 여러 사람이 번갈아 쓴다"**는 조건 하나 때문에 고민할 거리가 완전히 달라졌습니다. 웹에서는 각자 새로고침 한 번이면 끝날 일이, 키오스크에서는 쌓이고 쌓여서 수십 번째 사람에게 문제로 돌아옵니다.

특히 컨페티 캔버스 문제는 한두 번 눌러보는 테스트로는 보이지 않았고, 결국 현장에서 처음 드러났습니다. 사람이 수십 번씩 직접 돌려보기는 어려운 문제라 AI에게 원인 후보를 먼저 정리하게 하고, 의심 가는 부분만 떼어낸 측정과 빌드된 앱 자동 반복 테스트로 숫자를 직접 확인한 다음 고쳤습니다. "아마 이것 때문일 것"에서 멈추지 않고 고치기 전과 후를 같은 조건으로 재본 덕분에, 수정이 맞았는지를 숫자로 확인할 수 있었습니다. 키오스크 앱에서는 이런 반복 테스트와 현장 기록(로그)이 기능만큼 중요하다는 걸 알게 됐습니다.

대형 터치 모니터의 누름 문제도 마우스로 개발할 때는 드러나지 않던 부분이었습니다. 실제 설치될 기기에서 손으로 직접 눌러보는 과정이 꼭 필요하다는 걸 느꼈습니다.
