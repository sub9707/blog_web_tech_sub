      브라우저가 MCP 서버가 된다는 건, 에이전트가 화면을 직접 열어 보고 DOM과 콘솔, 네트워크 요청을 읽을 수 있다는 뜻이다.
      결과를 사람이 스크린샷으로 찍어 전달하지 않아도 되니 확인과 수정 사이의 왕복이 줄어든다.


      대신 브라우저에는 로그인 상태와 개인 정보가 들어 있어서 권한 범위가 중요하다. Safari MCP 서버가 로컬에서만 돌고
      Safari의 개인 정보에 접근하지 않는다고 분명히 밝힌 이유도 그 때문이다.

이번 주 가장 두꺼운 소식은 Safari 27.0이다. WebKit 팀이 역대 가장 긴 릴리스 노트라고 적을 만큼 기능이 많이 들어왔는데, 정작 팀이 가장 큰 성과로 꼽은 건 새 기능이 아니라 844건의 버그 수정이었다. 여기에 코딩 에이전트가 브라우저를 직접 보고 고칠 수 있게 하는 <glossary-term term="mcp-server">MCP 서버</glossary-term>까지 붙었다.

나머지 소식도 결이 비슷하다. 지원율이 94%에 이르렀는데도 쓰는 사람이 절반이 안 되는 <glossary-term term="container-query">컨테이너 쿼리</glossary-term>를 왜 <glossary-term term="media-query">미디어 쿼리</glossary-term>처럼 쓰면 안 되는지 짚은 글, Vite가 하던 일을 Rust로 다시 짜서 메모리를 몇 분의 일로 줄인 개발 서버, 그리고 에이전트가 코드를 대신 써 주는 시대에 프레임워크가 여전히 의미가 있는지 묻는 긴 글이 함께 올라왔다.

WebKit 팀이 Safari 27.0에 들어간 변화를 정리했다. 6월 첫 베타에서 58개였던 기능이 80개까지 늘었고, 팀은 릴리스 노트가 이렇게 길었던 적이 없다고 적었다. 그런데 팀이 가장 큰 성과로 내세운 건 기능이 아니다. WWDC에서 525건의 수정을 발표한 뒤 60%를 더 얹어 844건까지 갔다는 사실이다.

수정의 결을 보면 어떤 작업이었는지 짐작이 간다. 문서 편집기에서 힌디어 입력이 깨지거나 예약 사이트에서 이미지가 사라지는 것처럼 특정 사이트에서만 나던 문제를 하나씩 추적했고, 토대를 아예 새로 쓴 것도 있다. ES 모듈 로더를 처음부터 다시 만들었고 CSS Zoom을 재구현했으며 인라인 레이아웃이 소수점 단위로 위치를 잡도록 바꿨다. SVG는 이번 릴리스에서만 66건을 고치면서 SMIL 애니메이션 엔진을 끝에서 끝까지 훑었다. 눈여겨볼 유형이 하나 더 있는데, 기능 둘이 각각은 멀쩡한데 함께 쓰면 어긋나던 경우다. 2010년에 들어온 `-webkit-line-clamp`와 2024년에 들어온 `text-wrap: balance`를 같은 요소에 주면 균형 잡기가 아예 동작하지 않았는데, 이번에 고쳐졌다.

새 기능 중 작업 방식을 바꿀 만한 건 Safari MCP 서버다. Claude Code나 Codex 같은 코딩 에이전트에게 브라우저 창의 제어권을 넘겨, 에이전트가 자기가 짠 코드가 실제로 어떻게 그려지는지 직접 보게 한다. DOM과 네트워크 요청, 스크린샷, 콘솔 출력에 접근할 수 있어서 폼이나 결제 흐름의 상태를 확인하고, 다른 브라우저와 계산된 스타일을 비교하고, 라벨 누락이나 잘못된 ARIA 속성 같은 접근성 문제를 점검하는 일까지 맡길 수 있다. 창을 오가며 스크린샷을 터미널에 붙여 넣는 과정이 줄어든다는 뜻이다. 서버는 전부 로컬에서 돌고 자체적으로 네트워크 요청을 하지 않으며, 수집한 데이터는 Apple이 아니라 쓰고 있는 에이전트로만 간다. 쓰려면 Safari 설정의 개발자 항목에서 원격 자동화와 외부 에이전트 허용을 켜고 에이전트에 `safaridriver --mcp`를 등록하면 된다.

화면에 바로 쓸 기능도 여럿이다. 오랫동안 손대기 어려웠던 `select` 요소를 완전히 다시 꾸밀 수 있는 <glossary-term term="customizable-select">커스터마이즈 가능한 select</glossary-term>가 들어왔고, 기본 스타일도 더 나은 출발점이 되도록 새로 다듬었다. 위쪽에서 무언가 늦게 로드돼 읽던 내용이 아래로 밀리는 현상을 막는 <glossary-term term="scroll-anchoring">스크롤 앵커링</glossary-term>도 포함됐다. 3D 모델을 HTML로 올릴 수 있는 <glossary-term term="model-element">model 요소</glossary-term>가 iOS와 iPadOS, macOS에 들어왔고, visionOS에서는 웹사이트가 몰입형 환경을 제공할 수 있게 됐다.

## 2. 컨테이너 쿼리를 미디어 쿼리처럼 쓰고 있다면

<figure>
<img src="https://files.smashing.media/articles/stop-treating-css-container-queries-traditional-media-queries/stop-treating-css-container-queries-traditional-media-queries.jpg" alt="컨테이너 쿼리와 미디어 쿼리의 차이를 다룬 Smashing Magazine 글의 대표 이미지" loading="lazy" referrerpolicy="no-referrer">
<figcaption>이미지 출처: <a href="https://smashingmagazine.com/2026/09/stop-treating-css-container-queries-traditional-media-queries/" target="_blank" rel="noopener noreferrer">smashingmagazine.com</a></figcaption>
</figure>

컨테이너 쿼리의 브라우저 지원율은 약 94%다. 그런데 State of CSS 설문을 보면 들어는 봤다는 사람이 86%인 데 비해 실제로 쓰는 사람은 41.4%에 그친다. 글쓴이는 이 격차의 원인을 문법이 미디어 쿼리와 너무 닮았다는 데서 찾는다. 겉모습이 비슷하니 하는 일도 비슷하겠거니 하고 넘어가게 된다는 것이다.

둘의 차이는 질문이 다르다는 데 있다. `@media (min-width: 1024px)`라고 쓸 때 브라우저에게 묻는 것은 지금 화면이 얼마나 넓냐는 것 하나다. 그래서 1920px짜리 데스크톱 화면이라면, 그 안의 카드가 300px짜리 격자 칸에 들어가 있어도 조건은 그대로 참이 된다. 카드는 가로로 펼쳐지려다 내용이 넘치거나 짓눌린다. 미디어 쿼리가 잘못한 건 없다. 묻지 않은 것을 알 수 없을 뿐이다.

컨테이너 쿼리는 질문을 바꾼다. 지금 이 자리에서 내게 주어진 공간이 얼마나 되느냐고 묻는다. 부모 요소에 `container-type: inline-size`를 주고 `@container` 안에 조건을 적으면, 그 컴포넌트는 화면 크기와 무관하게 자기를 감싼 영역의 가로 폭만 본다. 글쓴이는 이걸 거시 레이아웃과 미시 레이아웃으로 나눠 설명한다. 화면 전체를 가로지르는 헤더와 푸터, 전체 격자 구조, `prefers-color-scheme` 같은 시스템 설정과 기기 특성은 페이지 전체에 해당하는 이야기니 미디어 쿼리의 몫이다. 반면 카드, 위젯, 폼, 내비게이션처럼 그 안에 들어가 자리를 배정받는 것들은 컨테이너 쿼리의 몫이다. 같은 컴포넌트를 사이드바에도 넣고 본문에도 넣는 설계라면, 그 컴포넌트가 화면 너비를 보고 있는 이상 어느 한쪽에서는 반드시 어긋난다.

## 3. Vite를 Rust로 다시 쓴 개발 서버 OJ, 메모리를 몇 분의 일로

<figure>
<img src="https://assets.lovable.dev/content/news/covers/faster-previews-oj-tech-blog-2026-v2.png" alt="Rust로 만든 Vite 호환 개발 서버 OJ를 소개하는 글의 대표 이미지" loading="lazy" referrerpolicy="no-referrer">
<figcaption>이미지 출처: <a href="https://lovable.dev/blog/faster-previews-oj" target="_blank" rel="noopener noreferrer">lovable.dev</a></figcaption>
</figure>

Lovable은 미리보기 하나마다 실제 개발 서버를 띄운다. 정적인 결과물이 아니라 고치면 바로 반영되는 진짜 앱이어야 하기 때문이다. 그동안 그 엔진은 Vite였는데, 하루에 100만 개 가까운 샌드박스를 띄웠다 내리는 환경에서는 사정이 달라진다. Vite는 개발자 한 명이 노트북 한 대에서 쓰는 상황을 전제로 잘 만들어진 도구다. 다만 그 하나하나가 JavaScript 런타임을 들고 프로젝트에 도구 모음을 설치하며 메모리를 꽤 붙잡는다. 수천 개를 동시에 띄우면 그게 그대로 비용이 된다.

그래서 만든 것이 OJ다. Rust 바이너리 하나로 Vite가 하던 일을 한다. 기존 `vite.config.ts`를 그대로 읽고, 호환 계층을 통해 진짜 Vite 플러그인을 돌리며, <glossary-term term="fast-refresh">React Fast Refresh</glossary-term>나 TanStack Start처럼 앱이 의존하는 부분을 Rust로 다시 구현했다. 토대는 <glossary-term term="rolldown">Rolldown</glossary-term>과 Oxc로, Vite도 점점 받아들이고 있는 바로 그 Rust 기반이다. 차이는 어디까지 Rust로 가져가느냐다. Vite는 Rust 번들러를 부리는 Node.js 애플리케이션이지만, OJ는 파일 감시부터 웹소켓까지 전부 Rust이고 플러그인이나 서버 코드가 JavaScript를 실제로 필요로 할 때만 작은 Node 보조 프로세스를 띄운다.

설계 의도 중 눈에 띄는 대목은 에이전트를 전제로 잡았다는 점이다. 사람은 파일 하나를 저장하지만 에이전트는 한 번에 열 개를 몰아 쓴다. OJ는 파일 감시, 모듈 그래프, 컴파일, 갱신 전달이 하나의 파이프라인으로 묶여 있어서 몰아친 수정을 일관된 갱신 하나로 합친다. 중간의 반쯤 고쳐진 상태를 화면에 그리지 않고 한 번에 반영한다는 뜻이다. 숫자를 보면 컴포넌트 1만 개짜리 합성 앱에서 콜드 스타트가 4.9초에서 1.2초로 줄었고, 메모리는 1.5GB가 넘던 것이 약 115MB가 됐다. Excalidraw는 2.4GB에서 288MB, 모듈 1만 5천 개 규모의 CRM 앱 Twenty는 4.9GB에서 1.5GB였다. 글쓴이는 속도 수치가 완전히 같은 조건이 아니라는 점도 밝혀 뒀다. 비교 대상인 Vite 쪽에는 타입 오류를 띄우는 플러그인이 켜져 있었고 OJ는 아직 그 플러그인을 지원하지 않는다. 그래서 정작 중요하게 보는 숫자는 메모리라고 말한다. 미리보기를 동시에 몇 개나 띄울 수 있는지를 결정하는 건 결국 그쪽이기 때문이다. 실제 운영에서도 미리보기를 열고 앱을 쓸 수 있게 되기까지 걸린 시간이 중앙값 기준 17.4초에서 8.0초로 줄었다.

암호화 쪽 변화도 적지 않다. 메시지 인증 코드를 다루는 범용 API가 추가됐고, 사용할 수 있는 암호 알고리즘과 해시 목록을 OpenSSL 제공자에서 직접 찾아오도록 바뀌었다. 실험 단계지만 DTLS API도 들어왔다. 평소 쓰던 코드가 당장 바뀌지는 않지만, 성능 수치를 근거로 제시해야 하는 상황이라면 `node:bench`는 꺼내 볼 만하다.

## 6. 에이전트가 코드를 쓰는 시대에 프레임워크는 아직 중요한가

<figure>
<img src="https://brookslybrand.com/images/og/do-frameworks-matter-anymore.png" alt="프레임워크가 여전히 중요한지 묻는 글의 대표 이미지" loading="lazy" referrerpolicy="no-referrer">
<figcaption>이미지 출처: <a href="https://brookslybrand.com/posts/do-frameworks-matter-anymore/" target="_blank" rel="noopener noreferrer">brookslybrand.com</a></figcaption>
</figure>

오픈소스 프레임워크를 3년째 전업으로 만들어 온 글쓴이가 꺼낸 질문이다. 에이전트가 코드를 대신 쓰는 2026년에 어떤 웹 프레임워크를 쓰는지가 아직 중요한가. 더 나아가, 지금 새 프레임워크를 만드는 일에 의미가 있는가.

요즘 자주 들리는 주장은 이렇다. 모델이 쓸 만해진 뒤로는 코드 자체에 신경을 덜 쓰게 됐고, 특히 프론트엔드는 대부분 보여 주는 일이니 보기에 괜찮으면 괜찮은 것이다. React가 이미 가장 널리 쓰이고 학습 데이터도 많으니 모델도 React를 가장 잘 다룬다. 그러니 다른 걸 시도할 이유가 없다. 글쓴이는 이 주장을 반박하는 대신 논리의 앞뒤를 뒤집어 본다. 세부 구현을 아무도 신경 쓰지 않는 게 사실이라면, 왜 하필 React인가. 모델과 웹 사이에 추상 계층을 둘 이유 자체가 없어지는 것 아닌가. 지금이야말로 <glossary-term term="web-components">웹 컴포넌트</glossary-term>를 쓸 때가 아니냐는 것이다. 결국 둘 중 하나라고 정리한다. 프레임워크가 중요하지 않다면 React를 쓸 이유도 없고, React를 쓰는 게 유리하다면 프레임워크는 중요하다.

그다음 글은 프레임워크가 무엇을 주는 물건인지로 돌아간다. Flask와 jQuery와 React와 Next.js를 한 줄에 놓고 비교하기 어려우니, 이름 대신 역할로 정의하자고 제안한다. 프레임워크는 사이트를 만들 때 쓰는 추상, 구조, 제약을 제공한다는 것이다. 제약이 목록에 들어가 있다는 점이 핵심이다. 사람이 쓰든 에이전트가 쓰든, 할 수 있는 선택을 줄여 주는 쪽이 결과를 일정하게 만든다는 논의로 이어진다. 결론을 내리는 글이라기보다 질문을 제대로 세우는 글에 가깝고, 기술 선택을 설명해야 하는 자리에 서 본 적이 있다면 읽어 둘 만하다.

  출처: [React Activity: When a Render No Longer Guarantees an Effect](https://hackernoon.com/react-activity-when-a-render-no-longer-guarantees-an-effect) · React Status · 2026.09.18
- **Astryx 0.6, 반응형 테마가 들어간 Meta의 React 디자인 시스템** 테마가 화면 크기와 포인터 종류, 대비 설정에 따라 CSS 수준에서 달라질 수 있게 됐다. 6월에 공개된 Meta의 React 디자인 시스템이다.
  출처: [Astryx 0.6: Meta's React Design System Gets Responsive Themes](https://astryx.atmeta.com/blog/astryx-v0-6-0) · React Status · 2026.09.18
- **React Konva, 복잡한 2D 그래픽용 컴포넌트** 화이트보드나 다이어그램, 디자인 편집기를 만들 때 쓰는 Konva 캔버스 라이브러리의 React 바인딩이다. 이제 React 19.3이 필요하다.
  출처: [React Konva: Canvas Components for Complex 2D Graphics](https://konvajs.org/docs/react/index.html) · React Status · 2026.09.18
- **React Simple Maps 5.0** `d3-geo`와 topojson을 바탕으로 SVG 지도를 선언적으로 그리는 라이브러리의 새 버전이다. 문서가 특히 잘 정리돼 있다.
  출처: [React Simple Maps 5.0: Composable SVG Maps for React Apps](https://www.react-simple-maps.io/) · React Status · 2026.09.18
