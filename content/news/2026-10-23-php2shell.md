description: >-
  PHP 엔진 자체에서 인증 없는 원격 코드 실행이 가능한 취약점 두 건이 공개됐다. 무엇이 문제였는지, 공개 첫날 공격이 얼마나 쏟아졌는지,
  그리고 화면 코드를 짜는 입장에서 무엇을 챙겨야 하는지까지 풀어썼다.

glossary:
  - id: runtime
    term: 런타임(Runtime)
    description: |-
      작성한 코드를 실제로 읽고 실행해 주는 프로그램이다. 자바스크립트에 Node.js나 브라우저가 있듯이, PHP 코드에는 PHP 엔진(인터프리터)이 런타임 역할을 한다.

      우리가 짠 코드가 아무리 깔끔해도 그걸 돌리는 런타임에 구멍이 있으면 코드와 상관없이 위험해진다. 이번 PHP2Shell이 무서운 이유가 바로 이 지점이다. 워드프레스 플러그인 하나의 문제가 아니라, 그 밑에서 모든 PHP 코드를 돌리는 엔진의 문제였다.
  - id: cve
    term: CVE / 보안 권고(GHSA)
    description: |-
      CVE(Common Vulnerabilities and Exposures)는 공개된 보안 취약점마다 붙이는 전 세계 공통 식별 번호다. CVE-2026-109618처럼 연도와 일련번호로 이뤄져 있어서, 서로 다른 회사와 기사가 같은 취약점을 가리키고 있는지 번호 하나로 맞춰볼 수 있다.

      GHSA는 GitHub Security Advisory의 줄임말로, 프로젝트가 GitHub 저장소에 직접 올리는 공식 보안 권고문이다. 영향 버전, 수정 버전, 임시 대응책이 가장 정확하게 적혀 있어서 뉴스 기사보다 먼저 확인해야 하는 1차 자료다.

  - id: cvss
    term: CVSS 점수
    description: |-
      취약점이 얼마나 심각한지를 0점부터 10점까지로 매기는 표준 채점 방식이다. 원격에서 공격 가능한지, 로그인이 필요한지, 성공하면 기밀성·무결성·가용성이 얼마나 무너지는지 같은 항목을 조합해 점수를 낸다.

      9.0 이상이면 가장 높은 Critical 등급이다. 이번 두 취약점은 모두 CVSS v4.0 기준 9.2점을 받았다. 네트워크로 공격 가능하고 인증이 필요 없지만, 공격 조건이 다소 까다롭다는 점(AC:H)이 반영돼 10점까지 가지는 않았다.
  - id: rce
    term: 원격 코드 실행(RCE)
    description: |-
      Remote Code Execution. 공격자가 서버 앞에 앉아 있지 않아도, 네트워크로 요청 몇 개를 보내는 것만으로 서버에서 자기가 원하는 코드를 실행시킬 수 있는 상태를 말한다.

      코드를 실행할 수 있으면 그 서버 프로세스가 할 수 있는 일은 전부 할 수 있다. 설정 파일 읽기, DB 접속 정보 빼가기, 웹페이지 변조, 다른 서버로 넘어가기 같은 일이 모두 가능해지기 때문에 보안 취약점 중에서도 가장 심각하게 다뤄진다. 앞에 붙는 '인증 없는(Pre-auth)'은 로그인조차 필요 없다는 뜻이라 더 위험하다.
  - id: oom
    term: OOM(Out Of Memory)
    description: |-
      프로그램이 쓸 수 있는 메모리를 다 써버려서 더 이상 할당을 받지 못하는 상황이다. PHP는 요청 하나가 쓸 수 있는 메모리 상한(memory_limit)을 두고, 이걸 넘으면 'Allowed memory size exhausted' 같은 치명적 오류를 내고 그 요청을 강제로 끝낸다.

      문제는 이 '강제 종료'가 하던 일을 중간에 툭 끊고 빠져나오는 방식이었다는 것이다. 정리가 덜 된 상태로 빠져나오다 보니 내부 데이터가 반쯤 만들어진 채 남았고, 이게 이번 취약점의 출발점이 됐다.
  - id: uaf
    term: Use-After-Free(UAF)
    description: |-
      이미 반납(해제)한 메모리를 여전히 내 것인 줄 알고 다시 쓰는 버그다. 이사 나간 집 주소를 아직 수첩에 적어두고, 새 세입자가 들어온 그 집에 내 물건이 그대로 있을 거라 믿고 문을 여는 상황과 비슷하다.

      공격자가 그 빈자리에 자기가 원하는 데이터를 미리 채워 넣을 수 있다면, 프로그램은 공격자가 깔아둔 데이터를 정상 데이터로 착각하고 읽거나 실행 흐름에 쓰게 된다. C나 C++처럼 메모리를 직접 관리하는 언어에서 자주 나오는 대표적인 메모리 안전성 문제이고, PHP 엔진도 C로 작성돼 있다.
  - id: worker
    term: 워커(Worker) 프로세스
    description: |-
      웹 서버가 요청을 처리하려고 미리 띄워두는 일꾼 프로세스다. PHP-FPM이나 Apache는 요청이 올 때마다 프로그램을 새로 켜는 대신, 워커 여러 개를 띄워두고 요청을 하나씩 나눠 맡긴다. 한 워커는 요청 하나를 끝내면 같은 프로세스 그대로 다음 요청을 받는다.

      이 재사용 구조가 성능에는 좋지만, 이번처럼 이전 요청의 흔적이 깨끗이 지워지지 않으면 다음 요청이 그 흔적을 밟게 된다. 패치 후에 '모든 워커를 재시작하라'는 말이 반복되는 것도, 이미 떠 있는 워커는 예전 코드를 계속 돌리고 있기 때문이다.
  - id: sapi
    term: SAPI (mod_php, PHP-FPM)
    description: |-
      Server API의 줄임말로, PHP가 웹 서버와 어떤 방식으로 붙어서 동작하는지를 가리킨다. 대표적으로 Apache 안에 PHP를 모듈로 직접 넣는 mod_php, 웹 서버와 별도 프로세스로 떨어져서 요청을 주고받는 PHP-FPM이 있고, 그 외에 FrankenPHP, LiteSpeed 등이 있다.

      같은 PHP 버전이라도 어떤 SAPI를 쓰는지에 따라 이번 취약점이 터지는 조건이 달랐다. PHP 팀은 mod_php가 가장 위험하다고 봤는데, 애플리케이션 코드가 한 줄도 실행되기 전 단계에서 공격이 성립하는 게 확인됐기 때문이다.
  - id: multipart
    term: multipart 요청
    description: |-
      HTML 폼으로 파일을 올릴 때 쓰는 요청 형식(multipart/form-data)이다. 본문을 여러 조각(part)으로 나누고 조각마다 자기 헤더와 내용을 갖는다. 프론트엔드에서 FormData에 파일을 담아 fetch로 보내면 바로 이 형식으로 나간다.

      PHP는 이 요청을 애플리케이션 코드보다 먼저, 요청 시작 단계에서 자동으로 해석한다. 이번 취약점은 조각 수나 헤더 수를 비정상적으로 부풀려서 PHP가 해석하는 도중에 메모리를 다 쓰게 만드는 방식으로 시작된다.
  - id: memory-disclosure
    term: 메모리 노출(Memory Disclosure)
    description: |-
      서버 프로세스의 메모리 일부가 응답에 섞여서 바깥으로 새어 나가는 문제다. 그 메모리에는 다른 사용자의 요청 데이터, 비밀번호, 인증 토큰, API 키 같은 것이 들어 있을 수 있다.

      2014년 OpenSSL의 하트블리드(Heartbleed)가 대표적인 사례라서 'Heartbleed식'이라는 표현이 붙곤 한다. 이번에는 PHP가 해제된 메모리 내용을 세션 쿠키(PHPSESSID) 값에 담아 돌려보내는 경로가 확인됐는데, 앱이 세션을 아예 쓰지 않아도 발생했다.
  - id: embargo
    term: 조율된 공개와 엠바고
    description: |-
      취약점을 찾은 사람이 곧바로 세상에 알리지 않고, 먼저 개발팀에 비공개로 제보해 패치를 만들 시간을 주는 관행을 조율된 공개(Coordinated Disclosure)라고 한다. 그동안 정해둔 공개 시점까지 내용을 밖에 내지 않기로 하는 약속이 엠바고다.

      엠바고 기간에는 리눅스 배포판이나 클라우드, 보안 업체처럼 대응이 필요한 곳에만 미리 정보를 공유해서, 공개되는 순간 패치와 방어 규칙이 동시에 준비돼 있도록 한다. 이번에는 8월 말 제보부터 10월 21일 공개까지 약 두 달이 걸렸다.
  - id: honeypot
    term: 허니팟(Honeypot)
    description: |-
      일부러 공격받기 좋아 보이게 꾸며 놓은 미끼 서버다. 실제 서비스가 아니라서 정상 사용자는 들어올 일이 없고, 여기에 들어오는 요청은 거의 다 공격이나 스캔이라고 볼 수 있다.

      AWS는 MadPot이라는 대규모 허니팟 네트워크를 운영하고 있는데, 바로 여기에 공식 공개 4일 전인 10월 17일 PHP2Shell 공격 시도가 찍혔다. 덕분에 '공개일보다 먼저 공격이 있었다'는 사실이 드러났다.
  - id: poc
    term: PoC(Proof of Concept)
    description: |-
      취약점이 실제로 악용 가능하다는 걸 보여주는 개념 증명용 공격 코드다. 원래는 연구자가 '정말 위험하다'는 걸 입증하려고 만들지만, 공개되는 순간 누구나 가져다 쓸 수 있는 공격 도구가 된다.

      과거에는 실력 있는 소수가 PoC를 만들 때까지 다른 공격자들이 기다리는 구조였는데, AWS는 AI 덕분에 권고문이나 패치 차이(diff)만 보고도 동작하는 공격 코드를 만드는 비용이 크게 떨어졌다고 진단했다.
  - id: browser-impersonator
    term: 브라우저 위장 클라이언트
    description: |-
      실제로는 자동화 스크립트인데, 요청 헤더나 동작을 크롬·사파리 같은 일반 브라우저처럼 꾸며서 보내는 클라이언트다. 정상 사용자 트래픽에 섞여서 탐지를 피하려는 목적이 크다.

      Imperva 관측에서는 공개 첫날 PHP2Shell 관련 트래픽의 43%가 이런 위장 클라이언트였고, 33.3%는 알려진 봇, 20.5%는 Go 언어의 HTTP 라이브러리였다. 대부분이 사람 손이 아니라 도구로 뿌려진 요청이었다는 뜻이다.

  - id: waf
    term: WAF(Web Application Firewall)
    description: |-
      웹 서버 앞단에서 들어오는 HTTP 요청을 검사해, 알려진 공격 패턴과 맞는 요청을 서버에 닿기 전에 막아주는 방화벽이다. Cloudflare, AWS, Google Cloud Armor, Imperva 같은 곳이 서비스 형태로 제공한다.

      서버를 바로 패치할 수 없을 때 시간을 벌어주는 용도로 아주 유용하다. 다만 공격자가 요청 모양을 조금씩 바꿔 규칙을 피해 가는 경우가 있어서, 어디까지나 '추가 방어선'이지 패치를 대신하지는 못한다.
  - id: full-transaction
    term: Full Transaction Detection
    description: |-
      Cloudflare가 이번에 처음 실전 투입한 WAF 기능으로, 요청만 보는 게 아니라 같은 HTTP 거래에서 서버가 돌려준 응답까지 함께 보고 공격 여부를 판단한다.

      요청만으로는 정상 업로드와 공격을 구분하기 애매한 경우가 있는데, 응답에 이상한 신호(예: 비정상적으로 큰 쿠키 값)가 실려 나오면 그 응답을 사용자에게 보내기 전에 막을 수 있다. 오탐은 줄이고, 메모리 노출 같은 피해가 바깥으로 새는 것도 막는 구조다.

  - id: backport
    term: 백포트(Backport)
    description: |-
      최신 버전에서 만든 수정 사항을 예전 버전에도 옮겨 적용하는 작업이다. 우분투나 RHEL 같은 리눅스 배포판은 안정성 때문에 PHP 버전 번호는 그대로 두고 보안 패치만 백포트하는 경우가 많다.

      그래서 php -v에 찍힌 버전이 '취약 버전'처럼 보여도 실제로는 패치가 들어가 있을 수 있고, 반대로 버전만 보고 안심할 수도 없다. 배포판 패키지라면 패키지 변경 이력(changelog)에 CVE 번호가 있는지까지 확인해야 정확하다.
  - id: eol
    term: EOL(End-of-Life)
    description: |-
      공식 지원이 끝나서 더 이상 보안 패치가 나오지 않는 버전 상태다. PHP 8.1 이하가 여기에 해당한다.

      이번처럼 심각한 취약점이 나와도 EOL 버전에는 공식 수정판이 나오지 않는다. PHP 팀이 예외적으로 7.4, 8.0, 8.1용 최소한의 소스 패치를 공개하긴 했지만, 직접 빌드하는 경우를 위한 응급 처치에 가깝고 정답은 지원되는 버전으로 옮기는 것이다.
  - id: next-public
    term: NEXT_PUBLIC_ 환경변수
    description: |-
      Next.js에서 환경변수 이름 앞에 NEXT_PUBLIC_을 붙이면, 빌드할 때 그 값이 브라우저로 내려가는 자바스크립트 번들 안에 그대로 박힌다. 누구나 개발자 도구나 번들 파일에서 볼 수 있는 공개 값이 되는 것이다.

      접두사가 없는 변수는 서버에서만 읽을 수 있다. 그렇다고 서버 변수가 완벽히 안전한 건 아니다. 이번처럼 서버 프로세스가 뚫리거나 메모리가 노출되면, 그 프로세스가 들고 있던 비밀값도 함께 새어 나갈 수 있다.

주간 소식을 기다리기엔 급한 이슈라 따로 정리한다. 지난주 다룬 Next.js 보안 패치보다 판이 훨씬 크다.

10월 21일, PHP 개발팀이 PHP 엔진 자체에서 발견된 취약점 두 건(CVE-2026-109618, CVE-2026-109619)을 공개하고 같은 날 수정 버전을 배포했다. 이름은 **PHP2Shell**. PHP로 돌아가는 서버에서 로그인 없이 원하는 코드를 실행할 수 있다는 뜻이 이름에 그대로 담겨 있다.

"PHP면 백엔드 얘기 아닌가?" 싶을 수 있다. 맞다. 그런데 이번 사건은 화면 코드를 짜는 입장에서도 그냥 넘기기 어려운 질문을 던진다. **내 코드가 멀쩡해도, 그 코드를 돌리는 바닥이 뚫리면 서비스는 뚫린다.**

어떤 문제였는지, 공개 첫날 무슨 일이 벌어졌는지, 그리고 프론트엔드 개발자로서 무엇을 가져가면 좋을지 차례로 정리해보자.

## 1. 한눈에 보는 PHP2Shell

먼저 육하원칙으로 사건을 정리하면 이렇다.

- **누가** Wiz Research가 Calif, OpenAI 등과 함께 발견해 PHP 보안팀에 제보했고, PHP 개발팀이 수정했다. Cloudflare, AWS, Google, Imperva 같은 업체가 공개 전부터 방어 규칙을 준비했다.
- **언제** 8월 19일 첫 취약점 발견, 8월 24일 PHP 팀에 제보, 10월 21일 패치와 함께 공개됐다.
- **어디서** HTTP 요청을 처리하는 모든 PHP 서버. PHP-FPM, Apache mod_php, FrankenPHP, LiteSpeed 등이 대상이다.
- **무엇을** PHP <glossary-term term="runtime">런타임</glossary-term> 내부의 메모리 안전성 버그 두 건. 인증 없는 <glossary-term term="rce">원격 코드 실행(RCE)</glossary-term>과 서버 메모리 노출이 가능하다.
- **왜** 요청 처리 중 메모리가 바닥나 강제 종료될 때, 내부 상태를 깨끗하게 정리하지 못하고 흔적이 남았다.
- **어떻게** 특수하게 만든 HTTP 요청 몇 개로 그 흔적을 일부러 만들고, 다음 요청에서 그걸 밟게 만든다.

규모가 크다는 말을 실감하려면 숫자 두 개면 충분하다.

전 세계 웹사이트의 **약 70%가 PHP를 쓰고**, 워드프레스, 드루팔, 줌라, 위키백과의 MediaWiki가 전부 PHP 위에서 돈다. 그리고 영향을 받는 버전은 **PHP 5.4부터 8.5.11까지**, 사실상 지난 10여 년간 나온 거의 모든 버전이다.

두 취약점의 심각도는 <glossary-term term="cvss">CVSS</glossary-term> v4.0 기준 각각 **9.2점**, 가장 높은 Critical 등급이다.

## 2. 플러그인이 아니라 엔진이 뚫렸다

<img src="https://www.datocms-assets.com/75231/1792535785-image-5.png?fm=webp" alt="공격자가 특수하게 만든 POST 요청을 워드프레스, 드루팔, 줌라에 보내 메모리 압박을 일으키고 원격 코드 실행에 이르는 흐름도" loading="lazy" referrerpolicy="no-referrer">
<figcaption>이미지 출처: <a href="https://www.wiz.io/blog/php2shell-php-rce" target="_blank" rel="noopener noreferrer">Wiz Research</a></figcaption>

워드프레스 보안 사고는 보통 플러그인 하나, 테마 하나의 문제다. 그 플러그인을 안 쓰면 상관없고, 플러그인만 업데이트하면 끝난다.

PHP2Shell은 결이 다르다. 문제가 그 플러그인들을 **돌려주는 PHP 엔진**에 있다.

Wiz가 워드프레스, 드루팔, 줌라의 최신 공식 컨테이너 이미지를 대상으로 인증 없는 RCE를 시연했는데, 이건 대표 예시일 뿐이다. Wiz는 "**Hello World 한 줄짜리 앱도 취약한 PHP 버전 위에서 돌면 공격받을 수 있다**"라고 못 박았다.

애플리케이션 코드를 아무리 꼼꼼하게 짰어도 소용이 없다는 얘기다.

PHP 공식 공지는 특히 <glossary-term term="sapi">Apache mod_php</glossary-term> 환경을 가장 위험하다고 봤다. 애플리케이션 코드가 **한 줄도 실행되기 전에** 공격이 성립하는 게 확인됐기 때문이다. 로그인 검사, 입력값 검증, 권한 확인 같은 우리가 짠 방어 로직은 출발선에 서보지도 못하고 지나가 버린다.

## 3. 무엇이 잘못됐나: 메모리가 바닥났을 때의 뒷정리

두 취약점의 뿌리는 같다. **PHP가 요청을 처리하다 메모리가 바닥났을 때, 뒷정리를 제대로 못 한다.**

PHP는 요청 하나가 쓸 수 있는 메모리 상한을 두고, 이걸 넘으면 <glossary-term term="oom">OOM(Out Of Memory)</glossary-term> 오류를 내며 그 요청을 강제로 끝낸다. 여기까지는 정상이다. 문제는 강제로 끝내는 방식이 하던 일을 중간에 툭 끊고 빠져나오는 식이었다는 것이다.

요리하다 화재경보가 울려서 도마 위에 재료를 반쯤 썰어둔 채 뛰쳐나왔다고 생각해보자. 다음 사람이 주방에 들어와 그 도마를 '정리된 도마'인 줄 알고 그대로 쓰면 사고가 난다.

### CVE-2026-109618: 반쯤 만들어진 데이터를 진짜로 믿는다

<figure>
<img src="https://opengraph.githubassets.com/5d534b5750b6b09681c47e7343906fe921530060a139fab9925b31efa686ed3e/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w" alt="php-src GitHub 보안 권고 GHSA-w8hw-w9fx-j79w, RCE via OOM corruption" loading="lazy" referrerpolicy="no-referrer">
<figcaption>이미지 출처: <a href="https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w" target="_blank" rel="noopener noreferrer">GitHub php/php-src Security Advisory</a></figcaption>
</figure>

요청 내부 데이터가 아직 다 초기화되지 않은 순간에 OOM이 터지면, 요청을 마무리하는 정리 단계가 그 미완성 데이터를 정상 데이터처럼 읽고 판단에 써버린다.

공격자는 이 순간을 일부러 만든다. 파일 업로드에 쓰는 <glossary-term term="multipart">multipart 요청</glossary-term>에 조각 수나 헤더 수를 비정상적으로 부풀려 넣으면, 요청 크기 제한(post_max_size)은 통과하면서도 PHP가 이를 해석하는 과정에서 메모리를 다 써버리게 만들 수 있다. 공식 권고는 이 조건들을 조합하면 원격 코드 실행까지 이어진다고 설명한다.

### CVE-2026-109619: 이사 간 집 주소를 아직 들고 있다

요청이 끝나면 그 요청이 쓰던 메모리는 반납된다. 그런데 일부 전역 상태가 반납된 메모리를 **여전히 가리킨 채** 남아 있었다.

PHP는 <glossary-term term="worker">워커 프로세스</glossary-term> 하나가 요청을 끝내면 그대로 다음 요청을 받는다. 다음 요청이 초기화되기 전에 이 낡은 주소를 따라가면, 이미 다른 데이터로 채워진 메모리를 읽거나 고치게 된다. 공격자가 그 빈자리에 원하는 값을 미리 채워 넣을 수 있다면 실행 흐름까지 조작할 수 있다.

이런 종류의 버그를 <glossary-term term="uaf">Use-After-Free</glossary-term>라고 부른다.

Wiz의 기술 분석을 보면 이 경로로 **서버 메모리 일부를 세션 쿠키(PHPSESSID) 값에 실어 빼내는** 공격도 확인됐다. 앱이 세션을 아예 쓰지 않아도 동작했고, 그 메모리에는 다른 사용자 요청에 들어 있던 비밀번호, 토큰, API 키가 섞여 있을 수 있다. 2014년 하트블리드를 떠올리게 하는 <glossary-term term="memory-disclosure">메모리 노출</glossary-term>이다.

정리하면 핵심은 메모리가 부족하다는 사실 자체가 아니다. **오류가 났을 때 내부 상태를 안전하게 지키지 못했다**는 게 진짜 문제였다.

PHP 팀은 메모리가 바닥났을 때 중간에 툭 끊고 빠져나오는 방식을 아예 걷어내고, 안전한 지점까지 기다렸다가 정리하며 멈추는 방식으로 바꿨다.

## 4. 10년 묵은 버그를 꺼낸 건 AI였다

이번 사건에서 개인적으로 가장 오래 곱씹게 된 대목이다.

문제의 코드는 **10년 넘게** PHP 안에 있었다. 아무도 몰랐다기보다는, 실제 공격으로 엮어내기가 너무 어려웠다. 버그 여러 개를 사슬처럼 이어야 하고, 대상 서버마다 메모리 배치가 달라서 시도하고 디버깅하고 다시 맞추는 일을 끝없이 반복해야 한다. Wiz 표현으로는 "인간 연구자가 현실적으로 해낼 수 있는 한계선"에 있던 작업이다.

Wiz는 이번 연구 전반에 자체 도구인 Wiz Atlas와 Gemini 4 Argon, GPT-5.6 Sol을 썼다고 밝혔다. 결과적으로 **연구자 한 명이 일주일 만에, 예전 같으면 최고 수준의 팀이 몇 달 걸렸을 일을 끝냈다**고 한다. 실제로 8월 19일 첫 발견 다음 날 드루팔, 그다음 날 워드프레스 RCE까지 확인됐다.

Wiz는 2014년 하트블리드, 2021년 Log4Shell에 이어 PHP2Shell이 'AI 시대의 전환점'이 될 수 있다고 본다.

'복잡해서 현실적으로는 못 쓴다'는 말이 더 이상 안전의 근거가 되지 못한다는 것이다.

양날의 검이기도 하다. 같은 능력이 공격자 손에 들어가면 패치가 나오자마자 공격 코드가 만들어진다. 아래 5장에서 그 장면을 실제로 보게 된다.

## 5. 공개 4일 전부터 공격은 시작됐다

보통은 취약점이 공개되고, 패치가 나오고, 그다음에 공격이 시작된다고 생각한다. 이번엔 순서가 달랐다.

이번 취약점은 <glossary-term term="embargo">엠바고</glossary-term>를 걸고 약 두 달간 비공개로 패치를 준비했다. 그런데 AWS는 자사 <glossary-term term="honeypot">허니팟</glossary-term> 네트워크 MadPot에서 **공식 공개 4일 전인 10월 17일** 이미 PHP2Shell 공격 시도를 포착했다. 상업용 익명화 네트워크 IP에서 들어온 요청이었고, 공격자가 어떻게 미리 정보를 얻었는지는 아직 밝혀지지 않았다.

공개 당일에는 엠바고가 풀리기 열두 시간 전쯤부터 이미 <glossary-term term="poc">PoC</glossary-term> 공격 코드가 여러 개 돌아다녔고, 공개 직후 몇 시간 만에 PoC가 더 쏟아졌다. Cloudflare도 공식 공개 전에 취약점 정보가 유출됐고 실제 공격 트래픽을 목격했다고 밝혔다.

AWS가 이 사건에서 뽑은 교훈은 짧고 무겁다.

- 엠바고는 다른 누군가가 같은 버그를 찾기 전까지만 방어자를 지켜준다. **공개일을 공격 시작일로 착각하지 말 것.**
- 패치에서 실제 공격 코드가 나오기까지의 시간이 구조적으로 짧아지고 있다. 인터넷에 노출된 서버의 치명적 취약점이라면 **패치 기한을 '일'이 아니라 '시간' 단위로 잡을 것.**
- 침해 조사는 공개일이 아니라 가장 이른 공격 시점부터. 이번 건이라면 **최소 10월 17일부터** 로그를 봐야 한다.

## 6. 어떤 버전을 쓰고 있다면 위험한가

PHP 팀이 내놓은 수정 버전은 아래와 같다. 내 서버의 PHP가 왼쪽 범위에 있다면 바로 올려야 한다.

| PHP 계열 | 취약 버전 | 수정 버전 |
|---|---|---|
| PHP 8.5 | 8.5.11 이하 | 8.5.12 |
| PHP 8.4 | 8.4.26 이하 | 8.4.27 |
| PHP 8.3 | 8.3.35 이하 | 8.3.36 |
| PHP 8.2 | 8.2.34 이하 | 8.2.35 |
| PHP 8.1 이하 (5.4부터) | 전부 취약 | 공식 수정판 없음, 지원 버전으로 이전 권장 |

PHP 8.1 이하는 이미 <glossary-term term="eol">지원이 끝난(EOL)</glossary-term> 버전이라 공식 수정판이 나오지 않는다. 사안이 워낙 심각해서 PHP 팀이 7.4, 8.0, 8.1용 최소한의 소스 패치를 예외적으로 공개하긴 했지만, 직접 빌드하는 경우를 위한 응급 처치에 가깝다.

버전 번호만 보고 판단하면 안 되는 경우도 있다. 우분투, 데비안, RHEL 같은 리눅스 배포판은 버전 번호는 그대로 두고 보안 패치만 <glossary-term term="backport">백포트</glossary-term>하는 경우가 많다. PHP 팀도 배포판과 LTS 업체에는 패치를 미리 전달했다고 밝혔으니, 배포판 패키지를 쓴다면 패키지 변경 이력에 CVE 번호가 있는지 확인하는 게 정확하다.

클라우드 쪽도 상황이 제각각이다. Google Cloud를 예로 들면 App Engine 표준 환경(PHP 8.2 이상)은 자동으로 패치되지만, **직접 만든 컨테이너 이미지는 사용자 책임**이라 패치된 PHP로 다시 빌드하고 배포해야 한다. Dockerfile에 `php:8.3-apache` 같은 베이스 이미지를 박아 뒀다면, 이미지를 새로 받아서 다시 빌드하기 전까지는 예전 버전 그대로 돌고 있다는 뜻이다.

## 7. 지금 어떻게 막고 있나

### 첫 번째이자 유일한 완전한 해결책, 업데이트

PHP 공식 공지의 문장을 그대로 옮기면 이렇다. **"완전한 우회책은 없다. 업데이트만이 안전한 선택이다."**

업데이트할 때 놓치기 쉬운 게 하나 있다. **패키지만 올리고 끝내면 안 되고, 떠 있는 PHP 워커를 전부 재시작해야 한다.** 이미 떠 있는 프로세스는 메모리에 올라간 예전 코드를 계속 돌리고 있기 때문이다. PHP-FPM 풀, Apache, FrankenPHP 워커 모드 같은 것들을 하나도 빠짐없이 다시 띄워야 한다.

### 당장 못 올린다면, 시간을 버는 임시 대응

PHP 팀은 바로 업데이트할 수 없는 경우를 위해 노출을 줄이는 설정도 함께 안내했다. 어디까지나 특정 공격 경로를 막는 것이지 안전하게 만들어주는 건 아니라는 단서가 붙어 있다.

- 파일 업로드가 필요 없는 앱이면 post_max_size를 8M 정도로 낮추고, 업로드가 필요해도 32M 이하로 둔다.
- 업로드 진행률 기능(session.upload_progress.enabled)을 끈다.
- 웹 서버나 프록시 단에서 요청 크기, 입력 필드 수, multipart 조각 수, 헤더 수를 제한한다.
- multipart 업로드를 아예 안 쓰는 앱이라면 프록시 단에서 그런 요청 자체를 막는다.

### 앞단에서 막는 WAF

<figure>
<img src="https://blog.cloudflare.com/_emdash/api/media/file/01KXQSMGN3Z955B45GCJR4REK3.png" alt="Cloudflare 블로그의 php2shell 대응 글 대표 일러스트" loading="lazy" referrerpolicy="no-referrer">
<figcaption>이미지 출처: <a href="https://blog.cloudflare.com/php-vulnerabilities-waf-protection/" target="_blank" rel="noopener noreferrer">Cloudflare Blog</a></figcaption>
</figure>

서버 앞에 <glossary-term term="waf">WAF</glossary-term>가 있다면 패치할 시간을 벌 수 있다. Cloudflare는 공식 공개 약 9시간 전인 10월 21일 03:02(UTC)부터 **무료 플랜을 포함한 모든 WAF 사용자**에게 방어 규칙을 기본 적용했다. Google Cloud Armor, Imperva도 관리형 규칙으로 방어를 내놨다.

흥미로운 건 Cloudflare가 이번에 처음 실전에 투입한 <glossary-term term="full-transaction">Full Transaction Detection</glossary-term>이다. 요청만 봐서는 정상 업로드와 공격을 구분하기 애매한 경우가 있어서, 서버가 돌려준 응답까지 같이 보고 수상하면 응답 자체를 사용자에게 보내기 전에 막는다. 메모리가 쿠키에 실려 새어 나가는 이번 공격과 잘 맞는 방식이다.

그래도 Cloudflare 스스로 공격자가 요청 모양을 바꿔가며 규칙을 우회하려는 시도를 계속 관측했다고 밝혔다. WAF는 **패치를 대신하는 게 아니라, 패치하는 동안 버티는 추가 방어선**이다.

### 업데이트한 다음에 할 일

공격이 공개 전부터 있었으니, 패치를 했다고 끝난 게 아니다. 이미 뚫렸을 가능성까지 확인해야 한다.

1. 운영 서버에서 실제로 돌고 있는 PHP 버전과 실행 방식(FPM, mod_php, 컨테이너 등)을 전부 확인한다.
2. 패치 후 모든 워커를 재시작했는지 다시 확인한다.
3. 10월 17일 이후 로그에서 비정상적인 multipart 요청 직후 메모리 한도 초과 오류나 500 응답이 반복된 흔적이 있는지 본다.
4. 비정상적으로 크거나 이상한 PHPSESSID 쿠키 응답, 설명 안 되는 워커 재시작이 있었는지 본다.
5. 웹 루트에 처음 보는 파일(웹셸)이나 새 크론 작업이 생기진 않았는지 확인한다.
6. 침해가 의심되면 증거가 되는 로그를 먼저 보존하고, 노출 가능성이 있는 API 키와 DB 비밀번호를 교체한다.

## 8. 그래서 프론트엔드 개발자는 뭘 챙겨야 할까

PHP를 직접 만질 일이 없더라도, 이번 사건에서 프론트엔드 입장으로 가져갈 것들이 꽤 있다.

### 클라이언트 검증은 서버 보안을 대신하지 못한다

React에서 파일 크기를 검사하고, 폼 입력을 막고, 친절한 에러 메시지를 띄우는 건 당연히 필요하다. 하지만 그건 **정상 사용자를 위한 UX**지 방어선이 아니다.

공격자는 우리 화면을 거치지 않는다. curl이든 Go 스크립트든, 원하는 모양의 HTTP 요청을 서버에 직접 쏜다. 이번 공격 트래픽의 대부분이 자동화 도구였다는 Imperva 통계가 딱 그 장면이다. 게다가 이번 취약점은 서버 쪽 애플리케이션 코드보다도 앞 단계에서 터졌으니, 프론트 검증은 말할 것도 없다.

### 요청 한 번이 지나가는 길을 그려 볼 수 있어야 한다

```text
브라우저
  ↓
CDN / WAF / 리버스 프록시
  ↓
웹 서버
  ↓
런타임 (PHP, Node.js, Python ...)
  ↓
애플리케이션 코드
  ↓
데이터베이스, 외부 API
```

우리가 매일 보는 건 맨 위 한 칸이다. 이번 사건은 그 아래 '런타임' 칸에서 일어났고, 바로 위 'WAF' 칸이 막판 방어선 역할을 했다. 내 서비스가 이 중 어디를 어떤 도구로 채우고 있는지, 각 칸의 업데이트는 누가 책임지는지 한 번쯤 그려 볼 만하다.

### npm 패키지만이 의존성이 아니다

프론트엔드는 package.json과 lockfile을 관리하는 데 익숙하다. 그런데 그 코드를 실제로 돌리는 Node.js 버전, Docker 베이스 이미지, 서버 OS 패키지도 똑같이 보안 업데이트 대상이다.

공교롭게도 같은 날인 10월 21일은 지난주 FE News에서 다룬 Node.js 보안 릴리스가 예정된 날이기도 했다. 런타임 업데이트는 PHP만의 숙제가 아니다. 프론트와 백엔드가 따로 운영되는 팀이라면 '런타임은 누가 올리지?'를 확실히 정해 두는 게 좋다.

### 비밀값은 어디에 있든 노출될 수 있다고 가정한다

Next.js에서 <glossary-term term="next-public">NEXT_PUBLIC_</glossary-term>이 붙은 환경변수는 빌드할 때 브라우저 번들에 그대로 박힌다. API 키나 DB 접속 정보를 여기에 넣으면 누구나 개발자 도구로 볼 수 있다. 이건 기본 중의 기본이다.

한 걸음 더 나가 보면, 서버 전용 변수에 넣었다고 영원히 안전한 것도 아니다. 이번 PHP2Shell처럼 서버 프로세스의 메모리가 통째로 새어 나가면 그 프로세스가 들고 있던 비밀값도 같이 나간다. 그래서 키 권한은 꼭 필요한 만큼만 주고, 유출됐을 때 빠르게 교체할 수 있는 구조를 미리 만들어 두는 게 현실적인 대비다.

### 보안 뉴스를 읽는 습관

이번 글을 쓰면서 확인한 순서를 그대로 체크리스트로 남겨 둔다.

1. CVE 번호와 공식 보안 권고(<glossary-term term="cve">GHSA</glossary-term>)부터 찾는다.
2. 영향받는 버전과 수정 버전, 지원 종료 여부를 확인한다.
3. 내가 관리하는 서비스가 실제로 그걸 쓰고 있는지 확인한다.
4. 업데이트 후 제대로 반영됐는지 검증하는 방법까지 챙긴다.
5. '공격 시도 N만 건'과 '실제 피해'를 구분해서 읽는다.

## 마무리

PHP2Shell은 서비스의 보안을 '내가 짠 코드'만으로 판단할 수 없다는 걸 아주 크게 보여준 사건이다.

브라우저에 보이는 화면은 서비스의 맨 윗부분일 뿐이고, 요청은 그 아래 여러 겹을 지나간다. 어느 한 겹이라도 구멍이 나면 위에서 아무리 잘 짜도 소용이 없다. 거기에 AI가 '너무 복잡해서 못 쓰는 버그'를 '하루 만에 쓰는 버그'로 바꿔놓기 시작했으니, 패치를 미뤄도 되는 시간은 앞으로 더 짧아질 것이다.

모든 취약점을 직접 찾아낼 수는 없다. 대신 공식 권고를 찾아 읽고, 내 서비스가 해당되는지 판단하고, 올리고, 제대로 올라갔는지 확인하는 습관은 지금부터 들일 수 있다.

**클라이언트가 잘 돌아간다는 사실만으로 서비스 전체가 안전하다고 믿지 말자.** 이번 사건이 남긴 가장 단순하고 중요한 교훈이다.
