이번 주는 브라우저가 오랫동안 미뤄온 숙제를 끝낸 소식과, 플랫폼 자체가 갑자기 뒤틀리는 보안 소식이 동시에 몰렸다. Chrome은 `<canvas>` 안에 진짜 HTML을 심어 접근성과 성능을 동시에 잡는 HTML-in-Canvas를 정식 공개했고, Safari는 <glossary-term term="customizable-select">Customizable Select</glossary-term>와 CSS Grid Lanes를 한 뼘씩 더 다듬었다. 반대쪽에서는 Node.js가 원격 코드 실행까지 이어질 수 있는 Brotli 결함을 포함한 보안 패치를 냈고, Next.js는 내일 또 다른 보안 릴리스를 예고해뒀다.

도구 쪽도 조용하지 않았다. TanStack AI가 '벤더에 종속되지 않는다'는 약속을 지킨 채 1.0을 찍었고, Go로 다시 짠 TypeScript 7이 잃어버린 플러그인 자리를 '<glossary-term term="content-mapper">콘텐츠 매퍼</glossary-term>'로 메우기 시작했다. 거기에 <glossary-term term="webview">웹뷰</glossary-term> 없이 네이티브 창을 띄우는 Svelte 실험작과, `<table>`에 CSS Grid의 영혼을 이식하는 CSS 장난까지 더해져서, 어느 한 분야에 치우치지 않고 골고루 읽을거리가 쌓인 한 주였다.

## 1. Next.js, 11월 3일 보안 패치를 예고하다

Next.js 팀이 2026년 11월 3일에 예정된 보안 릴리스를 미리 공지했다. 이번 패치는 중간(medium) 등급 취약점 7개를 한꺼번에 처리하는데, 아직 구체적인 영향 범위나 버전대는 공개되지 않았고 릴리스와 함께 전체 권고문이 올라올 예정이다.

패치가 나오기 전에 "몇 개, 어느 등급인지"만 먼저 알려서 팀들이 배포 일정을 조율할 시간을 벌어주는 건 Next.js가 최근 꾸준히 지켜온 보안 공개 방식이다. 중간 등급이라고 가볍게 볼 건 아니고, 실제 영향은 조건에 따라 달라지므로 권고문이 올라오면 바로 확인하는 게 안전하다.

지금 당장 할 수 있는 건 많지 않다. 프로덕션에서 Next.js를 쓰고 있다면 11월 3일 이후 공식 권고문을 확인하고, 영향받는 버전대에 있다면 패치 버전으로 올리는 일정을 미리 잡아두는 정도가 최선이다. Vercel은 자체 오픈소스 버그바운티 프로그램으로 보안 연구자들과 계속 협업하고 있다는 점도 함께 언급했다.

## 2. Node.js, Brotli 디코더발 원격 코드 실행까지 포함한 보안 패치 공개

<figure>
<img src="https://nodejs.org/en/next-data/og/vulnerability/Node.js%20%E2%80%94%20Wednesday,%20October%2021,%202026%20Security%20Releases" alt="Node.js 2026년 10월 21일 보안 릴리스 공지 이미지" loading="lazy" referrerpolicy="no-referrer">
</figure>

10월 21일, Node.js 프로젝트가 26.x·24.x·22.x 라인에 걸쳐 보안 릴리스를 냈다. 가장 심각한 건 CVE-2026-111497로, 잘못된 형식의 Brotli 압축 데이터를 `node:zlib`로 풀 때 내부 디코더 버퍼 끝을 넘어서 메모리를 덮어쓸 수 있는 결함이다. 스트리밍 디코더가 "형식이 아예 틀렸다"는 신호를 "입력이 더 필요하다"는 신호로 잘못 처리하면서, 8바이트짜리 내부 버퍼에 입력을 계속 이어붙인 게 원인이다. 공격자가 보낸 압축 데이터를 그대로 풀어주는 서버라면 크래시는 물론 메모리 노출, 심하면 <glossary-term term="rce">원격 코드 실행(RCE)</glossary-term>까지 이어질 수 있다.

같이 묶인 패치 중에는 DNS와 TLS 쪽 결함도 있다. 호스트 이름에 NUL 바이트를 숨겨서 `dns.resolve*()`가 다른 이름을 조회하게 만드는 결함, IP 주소를 전각 숫자나 앞에 0을 붙인 비표준 표기로 써서 `tls.checkServerIdentity()`의 검증을 피해가는 결함 등이 포함됐다. 둘 다 과거에 고친 취약점의 틈을 다시 비집고 들어간 사례라, 같은 영역을 계속 괴롭히는 공격 패턴이라는 점도 눈여겨볼 만하다.

패치는 26.13.0과 24.22.2 <glossary-term term="lts">LTS</glossary-term>로 배포됐다. 중간 등급 취약점까지 포함해 한 번에 여러 건을 처리한 만큼, 운영 중인 서비스가 사용자 입력을 압축 해제하거나 DNS·TLS로 외부와 통신한다면 버전을 바로 올리는 게 맞다.

## 3. `<canvas>` 안에 진짜 DOM이 들어왔다 — HTML-in-Canvas 정식 출시

<figure>
<img src="https://developer.chrome.com/static/blog/html-in-canvas/image/thumbnail.png?hl=fr" alt="HTML-in-Canvas 기능을 소개하는 Chrome 공식 썸네일" loading="lazy" referrerpolicy="no-referrer">

그동안 `<canvas>`로 화려한 UI를 만들려면 두 가지 중 하나를 골라야 했다. 텍스트와 컨트롤을 `fillText()`로 픽셀째 직접 그리거나, HTML 엘리먼트를 캔버스 위에 떠 있는 레이어로 겹쳐 놓고 좌표를 매 프레임 JavaScript로 계산해 맞추는 식이다. 전자는 스크린 리더가 읽을 수 없고 페이지 내 검색(Ctrl/Cmd+F)도 안 되고, 후자는 스크롤이나 확대·축소 중에 레이어가 캔버스 그림과 살짝 어긋나는 찢어짐이 생기고 매 프레임 `style.transform`을 다시 계산해 써야 하는 비용도 쌓인다.

이 API는 <glossary-term term="origin-trial">오리진 트라이얼</glossary-term>을 거쳐 Chrome 157에서 정식 안정 버전으로 자리 잡았다. 캔버스 기반 에디터, 지도, 3D 시각화 도구처럼 빽빽한 UI를 다루던 곳이라면 지금 쓰던 레이어 동기화 코드를 걷어낼 여지가 생긴 셈이다.

<figure>

Safari 27.0에서 처음 나온 Customizable Select는 `<select>`의 선택된 옵션이 버튼 안에 어떻게 표시될지를 `<selectedcontent>` 엘리먼트로 직접 제어할 수 있게 해주는 기능이다. 27.2는 `<selectedcontent>`를 아예 쓰지 않아도 되는 길을 하나 더 열었다. 새 `::field-content` 가상 엘리먼트로 선택된 옵션 텍스트의 스타일만 건드릴 수 있게 됐고, 피커 아이콘 레이아웃이나 수직 정렬 같은 기본 스타일도 더 안정적으로 다듬었다. 큰 피커가 화면 밖으로 삐져나오던 문제도 safe 정렬을 적용해 고쳤는데, 이 변경은 absolute·fixed 위치 요소 전반에 적용되는 더 넓은 CSS 정렬 규칙 변경의 일부다.

작년 3월 Safari 26.4로 처음 나온 CSS Grid Lanes의 flow-tolerance 속성은 이름이 <glossary-term term="fit-tolerance">fit-tolerance</glossary-term>로 바뀌었다. 이 속성은 다음 항목을 어느 칸에 놓을지 고를 때 브라우저가 얼마나 '깐깐하게' 따질지를 정한다. 값을 0으로 두면 내용이 끝나는 높이가 조금만 짧은 칸을 매번 쫓아가느라 항목이 이 칸 저 칸으로 튀어 다니고, 포커스를 따라가는 키보드 사용자는 시선이 계속 좌우로 튄다. 기본값인 `fit-tolerance: 1em`보다 더 큰 값을 주면 높이가 비슷한 칸들을 '같다'고 보고 옆 칸에 계속 쌓아주기 때문에, 대부분은 이 값을 지금보다 크게 올려서 쓰는 게 낫다. 옛 이름은 당분간 더 동작하는 별칭으로 남지만 조만간 지워질 이름이니 지금 바꿔두는 게 좋다.

이 밖에도 접근성, 미디어, CSS, JavaScript 전반에 걸쳐 20건의 버그가 고쳐졌다. `aria-labelledby`로 참조된 목록·표·트리 콘텐츠가 접근 가능한 이름에서 빠지던 문제, `for await...of`가 교체된 `Promise.prototype.constructor`를 제대로 찾지 못하던 문제처럼 눈에 잘 안 띄지만 실제로 자주 부딮히는 종류의 수정이 많다.

## 6. TypeScript 7.1, 사라진 tsserver 플러그인 자리에 '콘텐츠 매퍼'를 두다

<figure>
<img src="https://www.jovidecroock.com/typescript-7-content-mappers.jpg" alt="TypeScript 7.1 콘텐츠 매퍼를 다룬 블로그 글의 대표 이미지" loading="lazy" referrerpolicy="no-referrer">
</figure>

TypeScript 7(이른바 <glossary-term term="tsgo">tsgo</glossary-term>, Go로 다시 짠 컴파일러)은 tsserver 플러그인을 로드하지 않는다. tsconfig.json에 플러그인을 적어놔도 그냥 무시된다. 당장 체감되는 피해는 `.graphql` 쿼리에 타입과 자동완성을 붙여주던 GraphQLSP 같은 플러그인이다. gql.tada로 만든 타입은 그냥 TypeScript라서 여전히 동작하지만, 에디터에서 뜨던 GraphQL 오류, 오타 난 필드 이름, 더 이상 쓰지 않는 필드 경고는 아무 말 없이 전부 사라진다.

TypeScript 7.1 베타가 그 구멍을 메우는 방법으로 내놓은 게 콘텐츠 매퍼다. 콘텐츠 매퍼는 TypeScript가 JSON-RPC로 띄우는 별도 프로세스로, 특정 확장자의 파일을 받아서 TypeScript 코드와 원본 위치로 되돌아가는 매핑, 진단 정보를 돌려준다. 컴파일러는 그 다음부터 원본 파일을 마치 그 TypeScript 코드인 것처럼 취급한다. CSS 모듈을 예로 들면 `typed-css-modules-mapper`가 `.module.css` 파일을 읽어서 클래스 이름마다 정확한 타입을 즉석에서 만들어주기 때문에, `declare module '*.module.css'`로 전부 string이라고 뭉개거나 watch 모드로 `.d.ts`를 계속 생성해 둘 필요가 없어진다.

다만 콘텐츠 매퍼에는 중요한 제약이 하나 있다. `.ts`나 `.tsx` 같은 내장 확장자는 매핑할 수 없다. 그래서 컴포넌트 파일 안에 그대로 쓰인 `graphql()` 호출문 자체는 매퍼가 들여다볼 수 없고, gql.tada는 대신 `.graphql` 파일을 매핑 대상으로 삼아 `# import` 주석으로 프래그먼트를 모듈처럼 가져오는 방식을 택했다. 콘텐츠 매퍼는 외부 코드를 실제로 실행하는 기능이라 `tsc --runExternalCode`와 에디터의 워크스페이스 신뢰 설정으로 명시적으로 켜야 동작한다는 점도 기억해 둘 부분이다.

## 7. gpuix-svelte, 웹뷰 없이 네이티브 데스크톱 창을 띄우는 Svelte

<figure>
<img src="https://gpuix-svelte.stanislav.garden/assets/wall/wall-mac.webp" alt="gpuix-svelte로 만든 네이티브 데스크톱 앱이 macOS에서 실행되는 모습" loading="lazy" referrerpolicy="no-referrer">
</figure>

Electron이나 Tauri 같은 데스크톱 프레임워크는 결국 웹뷰, 즉 브라우저 엔진 한 벌을 창 안에 넣어 HTML을 그린다. gpuix-svelte는 그 웹뷰를 아예 빼버린다. Svelte 컴파일러가 아직 공개되지 않은 커스텀 렌더러 API로 평소처럼 컴파일을 끝내면, 그 결과가 DOM이 아니라 <glossary-term term="gpui">GPUI</glossary-term>로 간다. GPUI는 Zed 에디터를 그리는 GPU 가속 UI 프레임워크로, macOS에서는 Metal, Windows에서는 DirectX, Linux에서는 Vulkan으로 레이아웃과 페인트를 직접 처리한다. `<div>`나 class 선택자를 쓴 `<style>` 블록까지 평소 Svelte 문법 그대로 쓰면서, 결과물은 DOM도 웹뷰도 없는 진짜 네이티브 창이 된다.

개발 경험 쪽은 웹 개발자에게 익숙한 것들을 그대로 옮겨왔다. 파일을 저장하면 열려 있는 창이 바로 갱신되는 핫 리로드가 있고, 테스트는 창을 띄우지 않고 헤드리스로 컴포넌트를 마운트해 실제 히트 테스트로 클릭을 흉내 낼 수 있다. 빌드하면 런타임과 GPUI까지 통째로 묶인 서명된 실행 파일 하나가 나오는데, 같은 앱을 GPUI의 WebAssembly 빌드로 브라우저에서도 돌릴 수 있다.

아직 기반이 되는 Svelte 커스텀 렌더러 API 자체가 공개 전이라 실험적인 프로젝트이지만, '웹 프레임워크 문법으로 네이티브 앱까지'라는 방향을 보여주는 사례로는 흥미롭다. Node 24나 Bun 1.4 이상만 있으면 `npm create gpuix-svelte@latest`로 바로 시작해볼 수 있다.

`<table>`과 `<th>`, `<td>`는 겉보기엔 투박해도 브라우저와 보조 기술이 공통으로 이해하는 의미를 갖고 있다. `<th>`를 보면 '이건 제목이고 뒤에 데이터가 따라온다'는 관계가 바로 전달되는데, 이건 `<div class="title">`이나 `<strong>`으로는 똑같이 흉내 내기 어려운 종류의 의미다. 그런데 레이아웃을 짜는 입장에서 보면 테이블의 기본 레이아웃 모델은 Flexbox나 CSS Grid만큼 유연하지 않다는 아쉬움이 늘 있었다.

이 글은 그 둘을 합치는 방법을 보여준다. 마크업은 `<table>`, `<tr>`, `<th>`, `<td>`로 그대로 쓰고, CSS에서 `table { display: grid }`로 테이블의 기본 렌더링을 완전히 걷어낸 다음, `tbody { display: contents }`로 레이아웃 트리에서 `tbody`를 건너뛰고, `tr`과 그 자식들에 `display: block`을 줘서 표 전용 스타일을 끊어버린다. 그 결과 신용카드 디자인 같은 걸 `grid-template-columns`와 `gap`으로 자유롭게 배치하면서도, 마크업을 읽을 때는 여전히 '제목과 값' 구조가 바로 보인다.

신기한 건 이렇게 뒤섞어도 역할(role)이나 접근성 쪽 동작은 실제 테이블 그대로 유지된다는 점이다. VoiceOver와 키보드 탐색이 진짜 표를 다루듯 동작한다. 다만 글쓴이도 인정하듯 이건 콘텐츠와 표현을 분리하라는 원칙을 아슬아슬하게 비껴가는 재주다. 데이터 표를 표로 보여주는 용도에는 그냥 테이블이 제일 깔끔하고, 이런 기법은 '레이아웃은 자유롭게 짜면서 의미는 표처럼 남기고 싶다'는 특수한 상황에서 꺼내볼 만한 도구로 받아들이는 게 맞다.
