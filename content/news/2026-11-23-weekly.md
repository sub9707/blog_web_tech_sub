이번 주 프론트엔드 소식을 관통하는 키워드 하나를 고르면 '경계를 다시 긋는다'는 말이 어울린다. Next.js는 AI 때문에 <glossary-term term="security-advisory">보안 권고</glossary-term>가 쏟아지는 상황을 받아들이고 오히려 AI로 그 경계를 지키는 쪽으로 방향을 틀었고, Resend는 Node.js와 Go 사이의 경계를 넘나들며 어디까지가 런타임의 한계이고 어디부터가 설계의 문제인지를 숫자로 보여줬다.

같은 흐름은 UI 레이어에서도 보인다. UI SDK는 컴포넌트와 그 안의 동작을 분리해 사람과 에이전트가 함께 쓸 수 있는 경계를 새로 그렸고, WebKit은 2D 평면에 머물던 CSS의 경계를 3D 공간까지 넓혀보는 실험을 시작했다. 그 사이사이에 npkill, Astrobook, <glossary-term term="semantic-html">시맨틱 HTML</glossary-term>로 그린 차트처럼 작업 환경을 가볍게 만들어주는 소식들도 나란히 놓여 있다.

## 1. 보안 권고는 왜 늘었나, 그리고 Next.js는 AI로 어떻게 맞서고 있나

<figure>
<img src="https://nextjs.org/_next/image?url=https%3A%2F%2Fh8DxKfmAPhn8O0p3.public.blob.vercel-storage.com%2Fstatic%2Fblog%2Fhow-were-using-ai-to-make-nextjs-more-secure%2Fsecurity-insight-light.png&amp;w=3840&amp;q=75" alt="Next.js DevTools가 보안 취약점이 있는 버전임을 감지하고 안전한 버전으로 업그레이드하라고 안내하는 화면" loading="lazy" referrerpolicy="no-referrer">
</figure>

Next.js의 보안 권고 건수는 2024년 6건에서 2025년 14건, 그리고 2026년 들어서는 51건으로 크게 늘었다. 숫자만 보면 프레임워크가 점점 위험해지는 것처럼 보이지만, Vercel은 오히려 지금이 가장 안전한 시점이라고 말한다. 늘어난 건 버그 자체가 아니라 버그를 찾아내는 속도이기 때문이다.

이 변화의 핵심은 AI다. 누구나 LLM으로 코드를 훑어보며 취약점을 찾을 수 있게 되면서, 예전에는 발견하기 어렵거나 공격할 가치가 없다고 여겨졌던 엣지 케이스 버그들이 돈이 되는 표적으로 바뀌었다. 실제로 올해 발견된 취약점의 70%는 1년 이상 된 코드에서 나왔고, 43%는 3년 이상 된 코드에서 나왔다. Next.js가 포함하는 이미지 최적화 같은 상위 의존성 라이브러리들도 함께 집중 공격을 받고 있다.

Vercel의 대응은 두 갈래다. 먼저 오래된 코드의 재고 버그를 찾기 위해 <glossary-term term="bug-bounty">버그 바운티 프로그램</glossary-term>을 운영하고, 신고와 재현, 심각도 판단을 돕는 내부 보안 봇을 만들었으며, 외부 보안 업체 Trail of Bits에 수동 감사를 맡겼다. 그리고 새 코드에 버그가 들어가는 것을 막기 위해 모든 pull request마다 공격자 관점으로 코드를 해킹해 보는 Vercel Agent의 보안 리뷰 기능을 붙였다. 이 리뷰는 코드 리뷰를 통과하고 CI가 초록불이었던 PR에서도 실제로 문제를 잡아낸 사례가 있다.

개발자 입장에서 당장 할 일은 간단하다. 보안 릴리스는 이제 한 달에 한 번 정도, 사전 공지와 함께 나오므로 업그레이드 일정을 미리 잡아두면 되고, `npm run dev` 실행 시 뜨는 보안 경고나 Next.js DevTools의 안내를 그냥 넘기지 않는 것이다.

## 2. 이메일 API를 Node에서 Go로 옮긴 Resend, 그 이유와 결과

<figure>
<img src="https://cdn.resend.com/posts/memory-per-task-go-vs-node.png" alt="태스크당 메모리 사용량을 비교한 그래프, Node는 1.3GB, Go는 180MB를 사용한다" loading="lazy" referrerpolicy="no-referrer">
</figure>

이메일 발송 API를 서비스하는 Resend는 7주, 약 140개의 pull request를 거쳐 핵심 이메일 API를 Node.js에서 Go로 옮겼다. 10월부터는 모든 이메일 API 트래픽이 Go로 처리되고 있다.

이들이 Node를 떠난 이유는 속도보다는 안정성이었다. 큰 요청 본문을 파싱하고 직렬화하는 작업은 CPU를 많이 쓰는 동기 작업인데, Node.js에서는 이 작업이 끝날 때까지 <glossary-term term="event-loop">이벤트 루프</glossary-term>를 막아버린다. 심지어 속도 제한에 걸려 거부될 요청조차 파싱 비용을 먼저 치르면서, 정작 처리돼야 할 다른 요청들까지 함께 멈춰버리는 문제가 있었다.

재구현 과정에서 가장 어려웠던 건 속도가 아니라 동일한 동작을 보장하는 일이었다. Node와 Go 양쪽에 같은 요청을 보내 응답, 에러, 저장된 데이터, 그리고 요청을 두 번 보내도 같은 결과를 보장하는 <glossary-term term="idempotency">멱등성(idempotency)</glossary-term>까지 비교하는 테스트 하네스를 따로 만들었을 정도다. HTML 메일을 텍스트로 바꿔주는 변환 로직처럼, 문서에는 없지만 기존 사용자가 의존하고 있는 동작까지 Go로 그대로 포팅했다.

결과는 50% 트래픽 전환 시점을 기준으로 뚜렷했다. 같은 태스크 크기에서 Go는 요청당 CPU를 약 62% 덜 쓰고, 메모리는 태스크당 약 1.3GB에서 180MB로 줄었다. POST /emails 요청의 중간값 지연 시간은 58ms에서 31ms로 절반 가까이 줄었다. 다만 이런 수치 개선과 별개로, 실제 운영에서는 태스크 크기를 두 차례 늘리고 Redis 연결 풀을 조정하는 등 롤아웃 과정의 세심한 튜닝이 여전히 필요했다.

## 3. 컴포넌트가 아니라 동작을 파는 라이브러리, UI SDK

<figure>
<img src="https://ui-sdk.dev/og/docs/core/changelog/introducing-ui-sdk/image.png" alt="UI SDK 소개 페이지의 카드 이미지" loading="lazy" referrerpolicy="no-referrer">
</figure>

그동안 Radix, React Aria, Base UI 같은 라이브러리들은 버튼이나 Select 같은 완성된 컴포넌트를 제공하면서, 그 내부에 키보드 탐색이나 포커스 관리, <glossary-term term="aria">ARIA 속성</glossary-term> 처리 같은 로직을 함께 담아왔다. UI SDK는 이 레이어를 완성된 컴포넌트가 아니라, 그대로 재사용할 수 있는 동작 단위로 떼어낸 <glossary-term term="headless-ui">헤드리스 UI</glossary-term> 라이브러리다. `createRovingFocus`는 방향키로 포커스를 옮기고, `createTypeahead`는 타이핑한 글자로 옵션을 찾고, `createPopup`은 버튼 옆에 팝업을 열고 Escape나 바깥 클릭으로 닫아준다.

이렇게 만든 50개 이상의 동작을 조합하면 원하는 컴포넌트를 직접 만들 수 있고, React, Vue, Svelte, Solid 같은 프레임워크마다 같은 동작을 입힌 50개 이상의 완성 컴포넌트 세트도 함께 제공한다. 스타일은 전혀 강요하지 않으므로, 디자인 시스템은 그대로 유지한 채 상호작용 로직만 가져다 쓸 수 있다.

흥미로운 지점은 에이전트를 위한 설계다. `createAgent`로 어떤 컴포넌트의 어떤 동작까지 허용할지 정해두면, 브라우저에 내장된 에이전트나 외부 에이전트가 페이지의 컴포넌트를 사람처럼 읽고 클릭하고 값을 입력할 수 있다. 이를 위한 표준 통신 방식이 <glossary-term term="webmcp">WebMCP</glossary-term>인데, 페이지가 `registerTools`로 자신의 기능을 에이전트에게 노출하는 구조다. 컴포넌트 라이브러리가 사람뿐 아니라 에이전트도 쓰는 대상으로 설계되는 흐름을 보여주는 사례다.

## 4. CSS로 3D 공간을 다루는 시대, spatial CSS 개발자 프리뷰

<img src="https://webkit.org/wp-content/uploads/webkids-puzzle-playground-slotted.png" alt="모양 맞추기 보드에 팔각형 블록이 정확히 끼워진 모습, spatial CSS로 두 3D 모델을 정렬한 예시" loading="lazy" referrerpolicy="no-referrer">
</figure>

지금까지 웹에서 3D 콘텐츠는 대체로 별도의 그래픽스 엔진이나 JavaScript 라이브러리의 몫이었다. WebKit은 visionOS 27.3에서 `<model>` 엘리먼트를 중심으로 한 spatial CSS의 개발자 프리뷰를 내놓으며, 3D 공간을 꾸미는 작업도 CSS의 문법으로 끌어왔다.

핵심은 <glossary-term term="portal">포털(portal)</glossary-term>이라는 개념이다. `spatial:portal`을 선언한 엘리먼트는 그 안에 들어간 여러 `<model>`들이 공간을 공유하게 만들고, 이 모델들은 익숙한 transform으로 옮기고 돌리고 크기를 바꿀 수 있다. 블록을 보드의 정확한 구멍에 맞춰 끼우는 것처럼 두 모델을 정밀하게 붙여야 할 때는, 2D에서 쓰던 position-anchor 개념을 그대로 가져와 한 모델의 특정 기준점에 다른 모델을 맞춘다.

이걸 CSS로 선언하는 이유는 단순하다. 미디어 쿼리로 화면 비율이나 다크 모드, 모션 감소 설정에 맞춰 3D 장면도 함께 반응하게 만들 수 있고, 숫자 값은 애니메이션과 트랜지션도 그대로 적용된다. JavaScript로 상태를 일일이 관리할 필요가 없어진다는 뜻이다. 아직은 Vision Pro와 visionOS 시뮬레이터에서 기능 플래그를 켜야 써볼 수 있는 developer preview 단계이지만, 3D 콘텐츠를 다루는 방식에 CSS가 들어오는 방향성을 미리 보여준다.

## 6. 라이브러리 없이, 시맨틱 HTML과 CSS만으로 차트 그리기

차트를 그리려면 보통 차트 라이브러리를 설치하지만, 이 가이드는 반대로 묻는다. `<table>`, `<meter>`, `<data>`처럼 원래 그 의미를 가진 시맨틱 HTML 엘리먼트에서 시작하면 라이브러리 없이도 차트를 그릴 수 있지 않을까 하는 질문이다. 스타일시트를 걷어내도 여전히 읽을 수 있는 표나 목록이 남는다는 게 핵심 전제다.

문제는 CSS가 텍스트를 숫자로 해석하지 못한다는 점이다. 그래서 값은 사람이 읽는 텍스트와, 레이아웃에 쓸 커스텀 프로퍼티로 두 번 적어준다. `<td style="--v:2480">2,480</td>` 처럼 적어두면, CSS는 `--v`를 이용해 막대의 높이나 너비를 계산한다. `<meter value>`처럼 이미 속성에 숫자가 들어있는 경우라면 타입이 있는 `attr(value number)`로 바로 읽어올 수 있다.

그 다음은 익숙한 CSS 도구들의 조합이다. 배경을 값에 맞춰 늘리면 막대그래프가 되고, `color-mix()`는 히트맵의 색을, `conic-gradient()`는 도넛이나 게이지의 조각을 그린다. 범위 안에서 값의 비율을 구하는 계산은 `calc()`가 맡고, `:hover`나 `:has()` 같은 선택자로 툴팁이나 범례 토글 같은 상호작용도 추가할 수 있다. 결과적으로 자바스크립트 없이도 접근성 있는 차트 하나를 완성할 수 있다는 걸 보여주는 좋은 레퍼런스다.

여러 프레임워크를 한 프로젝트에서 같이 쓰는 팀이거나, 이미 Astro로 사이트를 만들고 있어서 새 도구를 더 얹고 싶지 않은 팀에게 특히 맞는 선택이다. 기존 Astro 프로젝트에 `subpath` 옵션으로 얹어 쓸 수도 있어서, 별도 배포 없이 같은 서버에서 컴포넌트 카탈로그를 운영할 수 있다.

## 8. node_modules 청소부 npkill, 이제 모든 언어의 쓰레기를 치운다

<figure>
<img src="https://zaldih.com/media/posts/npkill-1.0.0/panel-help.png" alt="npkill help panel" loading="lazy" referrerpolicy="no-referrer">
<figcaption>이미지 출처: <a href="https://zaldih.com/en/post/npkill-1-0-0/" target="_blank" rel="noopener noreferrer">zaldih.com</a></figcaption>
</figure>

npkill은 2019년, 디스크 용량을 잡아먹는 `node_modules`를 찾아 지우려고 만든 200줄짜리 개인 스크립트에서 시작했다. 7년, 45개 버전을 거친 1.0에서는 더 이상 `node_modules` 하나만 보지 않는다는 근본적인 변화가 생겼다.

이번 버전의 핵심은 프로필이라는 개념이다. 기본 프로필인 `node`는 `node_modules`뿐 아니라 `.next`, `.nx`, `.angular`, `coverage` 같은 무겁고 언제든 지워도 되는 디렉터리를 묶어서 찾아준다. `python` 프로필을 켜면 `__pycache__`나 `.venv`처럼 파이썬 개발 환경이 남기는 흔적도 같이 찾아낸다. `target`이나 `build`처럼 이름만으로는 헷갈릴 수 있는 디렉터리는 근처에 `Cargo.toml`이나 `pom.xml`이 있는지까지 확인해서 잘못 지우는 일을 막는다.

이 밖에도 여러 결과를 한 번에 지우는 멀티 셀렉트, 경로나 이름으로 결과를 걸러내는 필터, 자주 쓰는 설정을 저장해두는 `.npkillrc` 같은 편의 기능이 함께 들어왔다. `npx npkill`만 쓰던 사람은 그대로 써도 되고, `-p all` 한 번으로 디스크 전체를 훑어보고 싶다면 그렇게 확장해서 쓸 수 있다.
