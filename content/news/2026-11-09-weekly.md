  - id: cache-components-use-cache
    term: Cache Components와 use cache
    description: >-
      Next.js에서 특정 함수나 컴포넌트의 결과를 캐시해 두고 다음 요청에서 다시 계산하지 않고 재사용하게 만드는 기능이다. 함수 위에

      문제는 이 캐시가 요청마다 다른 사용자나 테넌트를 구분하지 않고 같은 저장소를 공유한다는 점이다. 같은 캐시 창고를 여러 손님이 함께
      쓰는데, 창고 열쇠(캐시 키)를 만드는 과정에 실수가 있으면 한 손님의 물건이 다른 손님에게 전달될 수 있는 것과 비슷하다. 이번
      보안 패치는 바로 그 열쇠 생성 과정의 허점을 고친 것이다.
  - id: unstable-cache

      생긴 문제다. 두 가지 캐시 방식을 함께 쓰는 프로젝트일수록 영향을 받을 가능성이 크다.

이번 주는 보안과 재작성(rewrite)이라는 두 단어로 요약된다. Next.js가 캐시 교차 노출을 포함한 6건의 취약점을 패치하며 두 개 LTS 라인을 동시에 업데이트했고, 뒤이어 Node.js도 26.x부터 22.x까지 전 라인업에 HIGH 등급 보안 릴리스를 예고했다. 공교롭게도 서버 쪽 핵심 런타임 두 개가 같은 시기에 패치를 요구하고 있어, 지금 운영 중인 프로젝트의 버전부터 점검해 둘 필요가 있다.

한편 도구 생태계에서는 '자바스크립트로 쌓아 올린 레이어를 걷어내고 네이티브로 다시 짠다'는 흐름이 뚜렷하다. 번들러 Parcel은 핵심부를 통째로 러스트로 새로 썼고, 테스트용 가짜 브라우저 <glossary-term term="jsdom-term">jsdom은</glossary-term> 자체 CSS 엔진을 갖췄다. <glossary-term term="safari-technology-preview">Safari Technology Preview는</glossary-term> 그리드와 line-clamp 버그를 대거 정리했고, Vitest는 변경된 코드의 테스트만 골라 돌리는 기능으로 AI 코딩 에이전트 시대에 맞춘 실험을 시작했다.

## 1. Next.js, 캐시 교차 노출 등 보안 취약점 6건 긴급 패치

지난주 예고됐던 Next.js 보안 업데이트가 이번 주 v16.4.5(<glossary-term term="active-lts">Active LTS</glossary-term>)와 v15.5.29(Maintenance LTS)로 공개됐다. Next.js를 운영 중이라면 패치 내용을 읽기 전에 일단 `npm install next@16.4.5` 또는 `next@15.5.29`부터 실행해 두는 게 안전하다.

가장 심각도가 높은 문제(High)는 Cache Components 기능과 함께 쓰이는 <glossary-term term="cache-components-use-cache">use cache 디렉티브</glossary-term>와, 더 오래된 <glossary-term term="unstable-cache">unstable_cache API</glossary-term>가 같은 함수를 동시에 호출할 때 벌어지는 캐시 교차 노출이다. <glossary-term term="tenant">테넌트</glossary-term> 식별자 같은 값을 읽는 캐시 함수가 콜드 캐시 상태에서 unstable_cache를 통해 동시에 호출되면, 한 요청의 결과가 테넌트 구분 없이 캐시에 저장돼 다른 고객사(테넌트)에게 그대로 노출될 수 있다. 이 밖에도 중첩된 use cache 함수가 느린 값을 기다리지 않고 먼저 저장되는 문제, 이진 인자를 쓰는 캐시 키가 서로 다른 사용자인데 같은 식별자로 묶이는 문제, Partial Prefetching을 끈 self-hosted 환경에서 페이지 셸이 오염되는 문제, HTTP/1.1 파이프라이닝 환경에서 압축 응답 프레이밍이 어긋나 다른 클라이언트의 응답이 뒤바뀌는 문제, `NextResponse.cookies.set()`으로 설정한 쿠키 값이 내부 `x-middleware-set-cookie` 헤더를 통해 <glossary-term term="httponly-cookie">HttpOnly</glossary-term> 설정에도 불구하고 같은 출처의 자바스크립트에 노출되는 문제, 그리고 SVG 이미지가 AVIF로 오인식돼 `images.dangerouslyAllowSVG: false` 설정을 우회하는 문제까지 총 6건이 공개됐다.

멀티테넌트 SaaS를 운영하거나 Cache Components·use cache를 쓰는 프로젝트라면 영향이 직접적이므로 업그레이드 우선순위를 높여야 한다. Edge Route Handler에서 민감한 쿠키를 다루거나, self-hosted 환경에서 `next start`로 직접 서빙하고 있다면 해당 항목도 한 번씩 짚어보는 게 좋다.

Next.js에 이어 Node.js 프로젝트도 11월 11일(수) 전후로 보안 릴리스를 낸다고 예고했다. 눈에 띄는 점은 이번에는 한 버전만의 문제가 아니라 26.x, 24.x, 22.x 세 릴리스 라인 모두에서 가장 심각한 이슈의 등급이 HIGH로 표시돼 있다는 점이다. 즉 어떤 메이저 버전을 쓰고 있든 영향권 안에 있다는 뜻이다.

공지 시점에는 구체적인 CVE 내용이 공개되지 않았는데, 이는 Node.js 보안 릴리스의 일반적인 절차다. 사전 공지로 날짜만 알리고, 실제 패치 버전이 나오는 시점에 상세 내용이 함께 공개된다. 또 하나 눈여겨볼 점은 '지원 종료(End-of-Life) 버전은 보안 릴리스가 나올 때 항상 영향을 받는다'는 안내다. 22 이전 버전처럼 이미 지원이 끝난 라인을 쓰고 있다면 패치를 받을 수 없으므로, 이번 기회에 지원 중인 메이저 버전으로 올리는 것을 고려할 만하다.

지금 할 수 있는 일은 많지 않다. 공지된 날짜 전후로 각자 쓰는 메이저 라인(26, 24, 22)의 새 버전이 올라오는지 확인하고, 올라오는 즉시 업데이트하면 된다. `nodejs-sec` 메일링 리스트를 구독해 두면 공지를 놓치지 않을 수 있다.

## 3. Safari Technology Preview 256, 그리드·line-clamp 버그 대거 정리

<figure>
<img src="https://webkit.org/wp-content/themes/webkit/images/preview-card.jpg" alt="Safari Technology Preview 공식 카드 이미지" loading="lazy" referrerpolicy="no-referrer">

Safari Technology Preview는 WebKit이 새 기능을 정식 Safari에 넣기 전에 먼저 시험해 보는 베타 채널이다. 아직 안정 버전에 없는 CSS·자바스크립트 기능을 미리 써 보고 싶을 때, 혹은 자신의 사이트가 다음 Safari에서 어떻게 보일지 미리 확인하고 싶을 때 쓰는 용도다. 이번 256 버전은 신규 기능보다 기존 버그 수정이 유난히 많았다.

특히 눈에 띄는 건 그리드 레이아웃 관련 수정이다. `repeat(auto-fit)`로 만든 빈 트랙과 그 거터(gutter)가 제대로 접히지 않던 문제, 선호 종횡비(aspect-ratio)를 가진 그리드 아이템의 크기 계산 문제 등이 고쳐졌다. 카드형 레이아웃에 auto-fit 그리드를 많이 쓴다면 반가운 소식이다. 텍스트를 몇 줄로 자르는 `line-clamp`도 여러 건 손봤는데, 블록 끝 마진을 무시하고 자르는 지점을 찾던 문제, 중첩 스크롤 컨테이너 안에서 레이아웃이 갱신되지 않던 문제, 절단 지점 이후의 요소가 계속 보이던 문제 등이 포함된다. 이 밖에 색 글꼴 팔레트를 섞는 `font-palette-mix()`가 새로 지원되고, 세로쓰기 모드에서 `aspect-ratio` 보간이 뒤집혀 있던 버그도 수정됐다.

당장 실무에 영향을 준다기보다는, 그리드나 line-clamp로 텍스트 자르기를 자주 쓰는 프로젝트라면 이번 수정 내역을 보고 '내가 겪었던 그 버그가 이거였구나' 하고 짚이는 게 있을 수 있다. 이런 수정들은 보통 몇 달 안에 정식 Safari로 넘어간다.

## 4. Parcel 3 알파, 번들러 핵심부를 통째로 러스트(Rust)로 다시 썼다

Parcel은 여러 JavaScript·CSS·이미지 파일을 모아서 브라우저가 바로 읽을 수 있는 결과물로 묶어주는 <glossary-term term="bundler">번들러다</glossary-term>. webpack이나 Vite와 같은 역할을 한다. Parcel 2에서는 JavaScript 컴파일러나 Lightning CSS 같은 개별 조각을 이미 러스트로 옮겼지만, 전체를 조율하는 핵심부는 여전히 자바스크립트였다. 문제는 워커 간 메모리를 공유할 수 없고, 가비지 컬렉션 비용이 들고, 언어 사이에 값을 직렬화해 주고받는 비용까지 더해져 성능에 한계가 있었다는 점이다.

Parcel 3는 CLI, 개발 서버, 트랜스포머, 번들러까지 전부 Node 의존성 없는 순수 러스트 바이너리로 다시 지었다. 그 결과 React Spectrum 같은 대형 TypeScript 모노레포를 기준으로 콜드 개발 빌드가 최대 100배 빨라졌고, 바이너리 용량도 Parcel 2의 의존성 포함 설치 용량(약 120MB)보다 4배 작은 30MB 미만으로 줄었다. 캐싱에 공들이는 대신, 애초에 콜드 빌드 자체를 빠르게 만들어서 캐시 무효화 버그라는 골치 아픈 문제 자체를 줄이는 쪽을 택한 점도 눈에 띈다.

기능 측면에서는 PostCSS 없이 바로 쓰는 Tailwind 지원, React Compiler, MDX, SVG를 JSX로 바꿔주는 변환이 기본 내장됐다. 새로 생긴 `parcel run` 명령은 Node 서버를 핫 리로드와 함께 띄워주는데, <glossary-term term="rsc">React Server Components</glossary-term>를 개발하기에 특히 잘 맞는다. 러스트·Go·Swift 등으로 네이티브 플러그인을 작성할 수 있는 안정적인 C ABI도 공개됐다. 아직 알파 단계라 당장 프로덕션에 쓸 수는 없지만, 번들러 성능 경쟁의 기준점이 한 단계 올라갔다는 점은 지켜볼 만하다.

## 5. Vitest 5.1, '방금 바뀐 파일의 테스트만' 돌리는 --since-last-run

<figure>
<img src="https://vitest.dev/og-vitest-5-1.jpg" alt="Vitest 5.1 릴리스 공지 카드 이미지" loading="lazy" referrerpolicy="no-referrer">

Vitest는 Vite 생태계에 맞춰 만들어진 테스트 러너로, Jest와 비슷한 역할을 한다. 기존에 쓰던 `--changed` 플래그는 Git 기준으로 바뀐 파일을 비교하는데, 저장소가 있어야 하고 커밋을 하는 순간 '바뀐 파일'에서 빠진다는 한계가 있었다.

새로 실험적으로 추가된 `--since-last-run`은 Git 대신 각 테스트가 마지막으로 실행됐을 때 로드한 파일들의 <glossary-term term="mtime">수정 시간</glossary-term>을 비교한다. 동적 import, 모킹, 설정 파일, 스냅샷 파일까지 추적 대상에 포함되며, 그 이후 수정되거나 삭제된 파일에 연결된 테스트만 다시 돌린다. Git 저장소가 아닌 임시 디렉터리나 컨테이너에서도 똑같이 동작하기 때문에, 코드를 수정할 때마다 테스트를 돌리는 AI 코딩 에이전트의 워크플로에 특히 잘 맞는다.

```sh
vitest run --since-last-run
```

이 외에도 스냅샷이 여러 개 틀어졌을 때 한꺼번에 업데이트하는 대신 하나씩 보면서 수락·거부할 수 있는 대화형 스냅샷 리뷰가 추가됐고, 5.0에서 실험 기능이던 Trace View가 'failure-only' 모드로 기본 활성화돼 안정화됐다. 통과한 테스트는 추적 비용이 전혀 들지 않고, 실패한 브라우저 테스트만 실패 시점까지의 단계별 기록(클릭, 입력, 어설션 등)을 남겨 디버깅 시간을 줄여준다.

## 6. jsdom 31, 테스트용 가짜 브라우저가 자체 CSS 엔진을 갖췄다

<figure>
<img src="https://opengraph.githubassets.com/32f450ad3dac46022da72e35a91bad8ec30a138c40de3a85973885fb71194f98/jsdom/jsdom/releases/tag/v31.0.0" alt="jsdom v31.0.0 GitHub 릴리스 페이지 카드 이미지" loading="lazy" referrerpolicy="no-referrer">

</figure>

jsdom은 Node.js 환경에서 브라우저의 DOM과 CSSOM을 흉내 내는 라이브러리다. 실제 브라우저를 띄우지 않고도 컴포넌트를 테스트할 수 있게 해줘서, 많은 테스트 러너가 내부적으로 jsdom을 기본 환경으로 깔고 간다.

이번 31.0의 가장 큰 변화는 CSS 파싱, 셀렉터 매칭, computed style 계산을 완전히 새로 통합된 구현으로 교체한 것이다. cascade layer, nesting, `@scope`, `@property`를 통한 커스텀 프로퍼티 등록, 조건부 `if()`, 그리고 `:host`, `::slotted()`, `::part()` 같은 <glossary-term term="shadow-dom-styling">shadow DOM 스타일링</glossary-term>과 constructable stylesheet까지 지원 범위가 크게 넓어졌고, 셀렉터 조회와 반복적인 스타일 읽기 속도도 빨라졌다. 다만 이 때문에 CSS 직렬화 결과나 computed value가 이전 버전과 달라질 수 있다.

또 하나의 큰 변화는 선택적 캔버스·이미지 디코딩 백엔드가 기존 `canvas` 패키지에서 `@napi-rs/canvas`로 바뀐 것이다. 플랫폼별로 미리 빌드된 Skia 바이너리를 쓰기 때문에 렌더링 결과와 인코딩된 이미지 바이트가 달라질 수 있어, 네이티브 캔버스 객체나 커스텀 폰트 등록을 쓰던 프로젝트는 마이그레이션 가이드를 확인해야 한다. HTML·XML 파싱이 블로킹 스크립트가 끝날 때까지 기다리도록 바뀐 점도 있어, `DOMContentLoaded`나 `load` 이벤트에 의존하던 테스트 코드라면 한 번 점검해 보는 게 좋다. 업그레이드 전에 테스트 스위트를 통째로 돌려서 스냅샷이 깨지는 곳이 없는지 확인하는 게 안전하다.

## 7. webframe, 웹페이지를 터미널 프로그램처럼 실행하기

webframe은 URL이나 HTML 파일을 인자로 주면, 운영체제에 이미 내장된 웹뷰(macOS·Linux의 WebKit 계열, Windows의 WebView2)에 그 페이지를 숨겨서 띄우고 터미널에 연결해 주는 도구다. 페이지 안에서 찍는 `console.log()`는 그대로 표준 출력(stdout)으로, 예외는 표준 에러(stderr)로 흘러나온다. Playwright나 Puppeteer처럼 브라우저를 따로 내려받아 번들로 들고 다닐 필요가 없다는 점이 특징이다.

이런 구조 덕분에 웹페이지를 셸 파이프라인 안에서 평범한 커맨드라인 프로그램처럼 다룰 수 있다. 페이지 안으로 스크립트를 주입해 테스트를 돌리거나, 비밀값을 전달하거나, 페이지가 종료 코드를 직접 정하게 만드는 식의 간단한 스크립팅·자동화 작업에 적합하다. 무거운 브라우저 자동화 도구 없이 가볍게 페이지 동작을 확인하고 싶을 때 선택지가 될 만하다.
