  - id: ua-sniffing

      손가락이 아니라 목소리로 조작되는 정사각형 화면 기기를 아이폰으로 착각해 버린다. 그래서 이 기기가 무엇인지보다 이 기능을 쓸 수
      있는지를 직접 확인하는 방식이 더 안전하다.

이번 주는 유난히 '기초를 다시 보게 하는' 소식이 많았다. Node.js는 HTTP/2와 TLS 처리 과정에 숨어 있던 고위험 보안 취약점 다섯 건을 한꺼번에 패치했고, Safari는 애플의 새 스마트 홈 디바이스인 HomeView에 올라타면서 '웹은 어떤 화면에서도 돌아가야 한다'는 원칙을 다시 시험대에 올렸다. 둘 다 결론은 비슷하다. 표준을 지키고 버전을 올려두면, 새로운 변화가 와도 크게 당황할 일이 없다.

프레임워크와 도구 쪽도 조용하지 않았다. X는 세 개로 쪼개져 있던 서버를 React·Vite·Fastify 기반의 스트리밍 아키텍처 하나로 다시 지었고, e18e는 메타 프레임워크의 성능을 더 이상 '느낌'이 아니라 공개된 숫자로 비교할 수 있는 벤치마크 프로젝트를 내놓았다. Next.js는 조용한 백포트 패치로 <glossary-term term="turbopack">Turbopack</glossary-term> 메모리 누수를 정리했고, Chrome은 탭 화면을 네이티브로 MP4에 바로 뽑아내는 API를 들고 왔다. 차트 라이브러리와 CSS 프레임워크까지 챙기다 보면, 이번 주는 기본을 얼마나 잘 지키고 있는지 점검하기 좋은 한 주다.

## 1. Node.js, 고위험 보안 취약점 다섯 건을 한꺼번에 막았다

<figcaption>이미지 출처: <a href="https://nodejs.org/en/next-data/og/vulnerability/Node.js%20%E2%80%94%20Wednesday,%20November%2011,%202026%20Security%20Releases" target="_blank" rel="noopener noreferrer">nodejs.org</a></figcaption>
</figure>

이번 주 Node.js 프로젝트는 22.x, 24.x, 26.x 세 개의 활성 <glossary-term term="lts">LTS 라인</glossary-term>에 동시에 보안 패치를 내놓았다. 숫자부터 심상치 않다. HTTP/2와 HTTPS, TLS 핸드셰이크 처리 과정에서 찾아낸 고위험(high) 등급 취약점 다섯 건이 한꺼번에 고쳐졌는데, 다섯 건 모두 인증 없이 요청만 보내도 공격이 성립한다는 공통점이 있다.

구체적으로 보면 HTTP/2 세션을 정리하는 코드에 남아 있던 메모리 계산 버그(<glossary-term term="cve">CVE-2026-123863</glossary-term>)는 평범한 요청만으로 서버 프로세스를 그대로 죽일 수 있다. 더 심각한 CVE-2026-123864는 HTTPS 요청 처리 중 TLS 계층이 잘못된 시점에 재진입하면서 <glossary-term term="use-after-free">use-after-free</glossary-term>가 발생하는 결함으로, 공격자가 다른 사용자의 요청 바디는 물론 TLS 개인 키 같은 민감한 메모리를 응답에 섞어 받아볼 수 있다. 나머지 세 건도 HTTP/2 세션이 영원히 정리되지 않아 메모리와 파일 디스크립터가 계속 새는 문제, 응답 버퍼를 다 쓰기 전에 스트림이 정리되면서 남의 응답 데이터가 전송되는 문제, TLS 핸드셰이크 콜백이 소켓이 끊긴 뒤에 실행되며 서버가 통째로 죽는 문제다.

이런 종류의 취약점은 패치 노트를 읽는다고 막히지 않는다. 할 일은 하나, 지금 쓰는 Node 버전을 이번에 함께 나온 26.13.1, 24.22.3, 22.23.5로 올리는 것이다. 운영 중인 서비스가 HTTP/2나 HTTPS 서버를 직접 띄우고 있다면 우선순위를 가장 앞에 둘 만한 업데이트다.

## 2. Safari, 애플 홈뷰라는 새 플랫폼에 올라탔다

<img src="https://webkit.org/wp-content/uploads/Apple-HomeView_cooking.png" alt="Safari의 HomeView 요리 모드 화면, 버터넛 스쿼시 수프 사진과 재료·조리 시작 버튼" loading="lazy" referrerpolicy="no-referrer">
<figcaption>이미지 출처: <a href="https://webkit.org/wp-content/uploads/Apple-HomeView_cooking.png" target="_blank" rel="noopener noreferrer">webkit.org</a></figcaption>

애플의 새 스마트 홈 디바이스인 <glossary-term term="apple-homeview">Apple HomeView</glossary-term>에도 이제 Safari가 들어간다. macOS, iOS, iPadOS, visionOS에 이어 다섯 번째 플랫폼인데, 이 기기는 사각형 7인치 화면을 탭으로 쓰거나 방 건너편에서 목소리로 말을 걸어 쓰는 게 기본 사용 방식이라는 점에서 기존 브라우저 환경과 다르다. 흥미로운 지점은 공식 블로그가 반복해서 강조하는 문장이다. 대부분의 경우 아무것도 하지 않아도 된다. 웹은 애초에 어떤 화면과 입력 방식에도 맞춰 동작하도록 설계됐기 때문이다.

다만 몇 가지를 챙기면 HomeView에서 사이트가 더 빛난다. HomeView의 요리 모드는 레시피 페이지를 인식해 단계별 안내 화면을 따로 보여주는데, 이 인식은 schema.org의 Recipe 타입을 <glossary-term term="json-ld">JSON-LD</glossary-term>로 적어둔 데이터를 기준으로 한다. 레시피 콘텐츠가 있다면 `<script type="application/ld+json">` 블록에 재료와 조리 단계를 구조화해 넣어두는 것이 먼저다. 영상 자막도 `<video>` 안에 WebVTT 파일을 가리키는 `<track>` 엘리먼트로 넣어야 HomeView의 재생 경험에서 제대로 뜬다.

더 중요한 건 하지 말아야 할 일이다. iOS 기기라고 해서 전부 아이폰은 아니다. HomeView도 iOS User Agent를 보내기 때문에, User Agent만 보고 iPhone이라 단정하는 <glossary-term term="ua-sniffing">UA 스니핑</glossary-term>은 예상 못한 오작동으로 이어질 수 있다. API 지원 여부는 UA 대신 <glossary-term term="feature-detection">기능 감지</glossary-term>로 직접 테스트하는 편이 안전하다. 화면이 항상 세로나 가로일 거라는 가정도 깨진다. HomeView는 정사각형에 가까운 짧은 화면이라, 고정 헤더·푸터가 콘텐츠 영역을 다 잡아먹거나 뉴스레터 모달이 화면보다 커서 닫을 방법이 없어지는 문제가 생길 수 있다. `max-height: 90vh; overflow-y: auto;` 정도의 방어적인 CSS 한 줄이 이런 사고를 막아준다.

## 4. 프레임워크 성능 비교, 이제는 감이 아니라 공개된 숫자로

<figure>
<img src="https://e18e.dev/og/launching-the-framework-performance-project.png" alt="e18e Framework Performance 프로젝트 출범 공지 이미지" loading="lazy" referrerpolicy="no-referrer">
<figcaption>이미지 출처: <a href="https://e18e.dev/og/launching-the-framework-performance-project.png" target="_blank" rel="noopener noreferrer">e18e.dev</a></figcaption>
</figure>

Next.js, Nuxt, SvelteKit, Astro, Solid Start, TanStack Start, React Router 같은 메타 프레임워크를 두고 '뭐가 더 빠르다'는 이야기는 늘 나오지만, 정작 같은 기준으로 잰 비교는 드물다. 어떤 팀은 <glossary-term term="ssr-csr">서버 렌더링(SSR)</glossary-term>에 집중하고 어떤 팀은 클라이언트 렌더링(CSR)에 집중하다 보니, 비교 자체가 사과와 우주선을 나란히 놓는 꼴이 되기 쉽다. e18e 커뮤니티가 시작한 Framework Performance 프로젝트는 이 문제를 정면으로 겨냥한다.

측정 항목은 두 갈래다. DevTime은 의존성 개수, node_modules 용량, 빌드·설치 시간, 개발 서버 구동 속도, 최소 Node 버전처럼 개발하는 동안 드는 비용을 잰다. RunTime은 각 프레임워크의 기본 설정이 아니라 똑같은 앱을 똑같이 만들어, Lighthouse 기준 초기 로딩, SSR 처리량, 부하 상태에서의 응답 지연 같은 실제로 돌아갈 때 드는 비용을 잰다. 여기에 더해 HTTP Archive의 실제 웹사이트 데이터를 끌어와 Core Web Vitals 수치까지 함께 보여준다.

이 프로젝트가 의미 있는 이유는 수치 하나를 뽑아 순위를 매기는 데 있지 않다. 공개된 벤치마크는 벌써 프레임워크 팀들의 실제 개선으로 이어지고 있다. Nuxt는 이 벤치마크를 손보는 과정에서 프레임워크 전용 링크 컴포넌트가 SSR 성능에 영향을 준다는 걸 발견해 수정했고, Solid 팀은 2.0 버전을 준비하며 SSR 처리량을 다지는 데 이 트래커를 계속 참고하고 있다고 밝혔다. 특정 프레임워크를 고를 때, 이제는 마케팅 문구보다 이 데이터를 먼저 열어보는 게 합리적이다.

## 6. Chrome 153, 탭 화면을 바로 MP4로 뽑아내는 네이티브 녹화 기능을 얹었다

<figure>
<img src="https://camo.githubusercontent.com/0663daa6cb290fa2bf52e00007208e2c6d2c59c8952b375aec6c5744cfa25e11/68747470733a2f2f696d672e736869656c64732e696f2f6e706d2f762f6368726f6d652d636170747572652e737667" alt="npm version" loading="lazy" referrerpolicy="no-referrer">
<figcaption>이미지 출처: <a href="https://github.com/paulirish/chrome-capture" target="_blank" rel="noopener noreferrer">github.com</a></figcaption>

브라우저 자동화 테스트에서 화면을 녹화해본 적이 있다면 익숙한 방식이 있다. `Page.startScreencast`라는, 2013년에 USB로 연결한 Android 기기를 DevTools에서 미리 보기 위해 만들어진 오래된 API다. Playwright의 `recordVideo`나 Puppeteer의 `page.screencast()`도 전부 이 위에서 동작한다. Chrome이 프레임을 JPEG로 압축해 base64로 바꾼 뒤 <glossary-term term="cdp">CDP</glossary-term>를 통해 JSON으로 보내고, 그걸 받아 ffmpeg로 영상을 만드는 식이라 느릴 수밖에 없는 구조다.

지난 9월 Chrome에 `Page.startScreenRecording`이라는 새 API가 들어오면서 이 흐름이 통째로 바뀌었다. 프레임이 합성(compositor) 단계에서 바로 공유 메모리를 통해 별도 프로세스의 인코더로 넘어가고, Chrome이 <glossary-term term="av1">AV1</glossary-term>로 인코딩해 그 자리에서 mp4 파일에 써 넣는다. ffmpeg 단계가 빠지니 멈추는 즉시 파일이 완성되고, 탭 오디오도 함께 담을 수 있다. 오픈소스 CLI 겸 라이브러리인 chrome-capture가 이 API를 Playwright Page, Puppeteer Page, 원시 CDP 세션 어디에든 붙일 수 있도록 감싸놓았다.

실제로 테스트를 자동화하는 입장에서 체감되는 변화는 녹화 종료가 더는 느린 작업이 아니라는 점이다. 녹화를 멈춘 뒤 파일을 마무리하는 데 걸리던 몇 초의 지연이 거의 사라져, 녹화가 걸린 테스트 전체가 눈에 띄게 빨라진다. Puppeteer는 이미 v25.10에서 실험적인 `page.record()`로 이를 받아들였고, Playwright 쪽도 같은 API를 끌어오는 PR이 올라와 있다.

## 7. Britecharts 3.0, 접근성을 기본값으로 둔 D3 차트 라이브러리

<figure>
<img src="https://britecharts.github.io/britecharts/assets/images/treemap-c0f8adc06778ee8cda29553af99f1ce6.png" alt="가계 예산을 보여주는 Britecharts 트리맵 차트 예시" loading="lazy" referrerpolicy="no-referrer">
<figcaption>이미지 출처: <a href="https://britecharts.github.io/britecharts/assets/images/treemap-c0f8adc06778ee8cda29553af99f1ce6.png" target="_blank" rel="noopener noreferrer">britecharts.github.io</a></figcaption>
</figure>

D3는 시각화를 만들기 위한 저수준 도구 모음이지 완성된 차트가 아니다. 축을 어디에 그릴지, 툴팁을 어떻게 띄울지까지 전부 직접 짜야 한다는 뜻이다. Britecharts는 그 위에 막대, 선, 도넛, 누적 영역, 산점도, 히트맵 같은 완성된 차트를 올려두고, 데이터만 넘기면 바로 쓸 수 있게 만든 라이브러리다. 3.0은 여기에 새 트리맵 차트를 더하고, 반응형과 로딩 상태를 전체 차트에 기본으로 넣었다.

이번 버전에서 가장 크게 바뀐 지점은 접근성이다. 모든 차트는 화면에는 보이지 않지만 스크린 리더가 셀 단위로 읽을 수 있는 데이터 테이블을 함께 렌더링하고, 막대·도넛·히트맵·선·산점도 같은 주요 차트는 키보드만으로 탭 이동과 방향키 탐색이 가능하다. `prefers-reduced-motion`을 설정해두면 애니메이션 없이 그려주고, 색맹 사용자를 위한 Okabe-Ito 팔레트도 기본 제공한다. 차트 색상은 `--bc-*` CSS 커스텀 속성으로 노출돼 있어 디자인 토큰만 바꿔도 전체 차트의 색이 따라간다.

실무에서 바로 체감할 변화는 내보내기와 테마다. `exportChart()` 한 줄로 SVG나 PNG를 내려받을 수 있어 보고서나 발표 자료에 차트를 바로 붙여넣을 수 있고, 페이지의 `color-scheme`을 따라 라이트·다크 테마가 자동으로 맞춰진다. 패키지는 `@britecharts/core`, `@britecharts/wrappers`, `@britecharts/react`로 나뉘어 있어 바닐라 JS든 React든 필요한 부분만 가져다 쓸 수 있다. 다만 메이저 버전업이라 호환되지 않는 변경이 적지 않으니, 기존에 Britecharts 2.x를 쓰고 있다면 마이그레이션 가이드를 먼저 펴보는 게 안전하다.
