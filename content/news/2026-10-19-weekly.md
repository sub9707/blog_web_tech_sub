  - id: rce
    term: 원격 코드 실행(RCE)
    description: >-
      공격자가 인증이나 권한 없이도 서버에서 자신이 원하는 코드를 그대로 실행시킬 수 있게 되는 취약점이다. 비유하면 현관문 자물쇠가 아예
      없는데 누군가 그 사실을 알아채고 마음대로 집에 들어와 가구를 옮기고 물건을 가져가는 것과 비슷하다.


      웹 서버에서 RCE가 가능해지면 데이터베이스 접근, 서버 내 파일 조작, 다른 시스템으로의 추가 공격까지 이어질 수 있어 보안 취약점
      중에서도 가장 심각한 등급으로 분류된다. 이번 주 Next.js 보안 패치가 긴급하게 나온 이유도 바로 이 등급의 취약점이 두 개나
      포함돼 있었기 때문이다.
  - id: lts
    term: LTS(Active LTS / Maintenance LTS)
    description: >-
      LTS는 Long-Term Support의 줄임말로, 새 기능 추가보다 안정성과 보안 유지에 초점을 맞춰 오래 지원하는 버전 라인을
      뜻한다. Next.js나 Node.js 같은 프로젝트는 보통 가장 최신 라인을 Active LTS로, 그 이전 라인을
      Maintenance LTS로 구분해 관리한다.

      지원이 끝나는 단계로 넘어간다. 그래서 운영 중인 서비스가 어느 LTS 라인에 있는지 파악해 두는 게 보안 업데이트를 놓치지 않는
      첫걸음이다.

      반환하는 데이터의 형태에 따라 예상치 못한 보안 취약점이 생길 수도 있어 프레임워크가 내부적으로 더 꼼꼼히 다뤄야 하는 영역이다.

      19.3.1이 손본 전송 프로토콜이 바로 이 포맷을 다루는 부분이다.

이번 주는 보안 패치 두 건이 거의 동시에 터진 주다. Next.js가 지난주 예고했던 임시 보안 업데이트를 실제로 공개했고, 거의 같은 시점에 Node.js도 다음 주 보안 릴리스를 예고했다. 두 소식 모두 당장 버전을 올려야 하는 실무형 뉴스라 가장 먼저 챙겨 볼 만하다.

그 외에는 프레임워크와 런타임이 저마다 웹 표준 쪽으로 몸을 기울이는 모습이 눈에 띈다. UnJS의 H3는 Node.js 전용 API를 버리고 Request와 Response 위에서 다시 지어졌고, CSS는 마스크와 <glossary-term term="style-query">스타일 쿼리</glossary-term> 같은 이미 자리잡은 기능으로 아이콘 문제를 깔끔하게 풀어내는 패턴이 소개됐다. HTML 쪽에서는 자바스크립트 없이 순서를 뒤바꿔 콘텐츠를 스트리밍하는 실험적 제안까지 나와, 프레임워크가 하던 일을 플랫폼이 조금씩 가져가는 흐름을 확인할 수 있다.

## 1. Next.js, 예고했던 보안 패치를 전격 공개하다

지난주 Next.js 팀이 예고했던 임시 보안 업데이트가 이번 주 실제로 나왔다. 원래 9월 보안 릴리스에 포함됐어야 했지만 업스트림 의존성 문제로 미뤄졌던 두 건의 취약점까지 한꺼번에 처리한 긴급 패치다. <glossary-term term="lts">Active LTS</glossary-term>인 v16.4.1과 Maintenance LTS인 v15.5.28에서 수정됐다.

가장 심각한 건 치명적(Critical) 등급의 <glossary-term term="rce">원격 코드 실행(RCE)</glossary-term> 취약점 두 가지다. 하나는 App Router에서 Cache Components를 쓸 때 <glossary-term term="use-cache">use cache</glossary-term> 함수가 타입이 지정된 배열(typed array)을 여러 개 반환하면 인증 없이도 서버에서 임의 코드가 실행될 수 있는 문제이고, 알려진 우회 방법이 없어 해당 패턴을 안 쓰더라도 무조건 업그레이드가 권장된다. 다른 하나는 SVG를 다루는 Image Optimization API에서 glibc 기반 리눅스 환경의 이미지 처리 라이브러리인 sharp의 메모리 취약점으로 인한 RCE로, sharp를 0.35.5 이상으로 올리는 것이 임시 우회책이지만 Next.js 자체를 올리면 패키지 매니저가 자동으로 안전한 sharp를 받아온다.

세 번째는 심각도 High의 <glossary-term term="dos">서비스 거부(DoS)</glossary-term> 취약점으로, Server Action을 쓰는 App Router 애플리케이션에 조작된 요청을 보내면 CPU를 과도하게 소모시켜 같은 프로세스의 다른 요청 처리까지 막아버린다. Pages Router만 쓰거나 Server Action을 전혀 쓰지 않는다면 영향이 없다. 지금 당장 해야 할 일은 명확하다. `npm install next@15.5.28` 또는 `npm install next@16.4.1`로 올리고, 이후 나온 버그 수정판 v16.4.2까지 반영해 두는 것이 안전하다.

## 2. React 19.3.1, RSC 전송 프로토콜을 다듬다

<glossary-term term="rsc">React Server Components(RSC)</glossary-term>는 서버에서 렌더링한 결과를 JSON과 비슷한 전용 와이어 포맷으로 클라이언트에 흘려보내는 방식으로 동작한다. 이번 19.3.1 패치는 바로 이 전송 프로토콜(transport protocol)을 개선하는 데 집중한 조용한 릴리스다.

변경 내용 자체는 한 줄로 짧게 적혀 있지만, 공개 시점이 Next.js의 긴급 보안 패치와 같은 주이고 Next.js 보안 공지가 타입이 지정된 배열을 여러 개 반환하는 use cache 함수의 RCE를 업스트림 React 권고와 연결 짓고 있다는 점을 보면, RSC 페이로드가 타입이 지정된 배열 같은 데이터를 다루는 방식과 무관하지 않아 보인다. React를 직접 올리지 않고 Next.js만 패치해도 상위 버전이 함께 올라오지만, React를 단독으로 쓰는 프레임워크라면 19.3.1로 직접 올려 두는 편이 안전하다.

기능 추가가 아니라 프로토콜 안정화에 가까운 릴리스이므로 애플리케이션 코드를 바꿀 일은 거의 없다. package.json의 react, react-dom 버전을 확인하고 패치 버전만 끌어올리면 끝이다.

## 4. UnJS의 H3, 웹 표준 위에서 새로 태어난 v2

<figure>
<img src="https://h3.dev/_og/blog/v2.png" alt="H3 v2 릴리스를 소개하는 공식 이미지" loading="lazy" referrerpolicy="no-referrer">
</figure>

H3는 Nitro, Nuxt 같은 UnJS 생태계가 내부적으로 쓰는 가벼운 HTTP 서버 프레임워크다. v1은 Node.js 고유의 요청/응답 객체에 맞춰 만들어졌는데, v2는 이를 통째로 걷어내고 Request, Response, URL, Headers 같은 웹 표준 API 위에 처음부터 다시 쌓았다.

핸들러는 표준 Request 그대로인 event.req와 event.url을 받고, 응답은 event.res.headers로 다룬다. 문자열이든 객체든 스트림이든 뭘 반환해도 H3가 알아서 Response로 바꿔준다. 덕분에 똑같은 코드가 Node.js뿐 아니라 Bun, Deno, Cloudflare Workers, 심지어 Service Worker와 브라우저에서도 그대로 돌아간다. 이걸 가능하게 하는 게 범용 서버 레이어인 srvx이고, 런타임마다 다른 세부 기능이 필요하면 event.req.runtime으로 접근할 수 있다.

라우팅은 URLPattern과 비슷한 문법을 쓰는 rou3 v1이 맡는다. 정규식 제약, 옵션 파라미터, 반복 파라미터 같은 걸 세그먼트 트리 구조로 빠르게 매칭한다. v1의 유틸리티 대부분은 그대로 동작하고 예전 이름도 계속 export되므로, 당장 전면 재작성을 할 필요 없이 점진적으로 마이그레이션 가이드를 따라가면 된다. 다만 Node.js에서 돌릴 때는 Node.js 20.19 이상이 필요하다.

## 5. Bun 1.4.3, tsc 없이도 타입 체크가 되는 시대

<figure>
<img src="https://bun.com/images/bun-check-1.4.3.webp" alt="bun check이 tsc 7보다 훨씬 빠르고 메모리를 적게 쓰는 것을 보여주는 벤치마크 차트" loading="lazy" referrerpolicy="no-referrer">
</figure>

지금까지 TypeScript 코드를 검사하려면 결국 마이크로소프트의 tsc를 돌려야 했다. Bun 1.4.3에 새로 들어간 bun check은 TypeScript 7.0.2의 conformance 테스트를 100% 통과하는, Bun 안에 내장된 독자 <glossary-term term="type-checker">타입 체커</glossary-term>다. 내부적으로는 마이크로소프트가 만들고 있는 Go 기반 차세대 컴파일러 typescript-go를 그대로 포팅한 것이다.

tsconfig.json을 그대로 읽어 tsc와 똑같은 에러를 내놓지만 멀티코어를 전부 활용해서, 공개된 벤치마크 기준으로 VS Code나 Next.js 같은 대형 저장소에서 tsc 7.0.2보다 3배에서 6배 넘게 빠르고 메모리도 2배에서 5배 적게 쓴다. 타입 체크만 하고 JS나 .d.ts를 만들지는 않기 때문에 에디터의 자동완성이나 '선언으로 이동' 같은 기능은 여전히 기존 TypeScript 패키지가 담당한다.

`bun run --check`처럼 기존 명령에 --check 플래그를 붙이면 타입 에러가 있을 때 아예 실행이나 번들링을 막아준다. `bun test --check`, `bun build --check`도 마찬가지다. typescript 패키지를 설치하지 않고도 쓸 수 있다는 점까지 더해지면, 작은 스크립트나 CI 파이프라인에서 '일단 타입부터 빠르게 거르는' 용도로 적당해 보인다. 다만 아직 에디터 통합이나 선언 파일 생성은 못 하므로, 본격적인 타입 선언 작업에는 여전히 tsc가 필요하다.

## 7. `<?marker>`, 자바스크립트 없이 순서를 거스르는 HTML 스트리밍

지금까지 서버가 먼저 끝난 데이터부터 화면에 보여주려면 보통 자바스크립트 프레임워크의 스트리밍 SSR이나 클라이언트 쪽 로직이 필요했다. 크로미움에서 플래그를 켜고 테스트할 수 있는 새 제안 <glossary-term term="declarative-partial-updates">Declarative Partial Updates</glossary-term>는 이걸 순수 HTML로 풀어낸다. `<?marker name="post-abc123">`같은 처리 지시를 자리표시자로 미리 심어두고, 응답이 끝에 가서 `<template for="post-abc123">`로 내용을 보내면 그 템플릿이 자동으로 마커 자리에 끼워진다.

`<slot>`과 비슷해 보이지만 차이가 있다. 마커는 한 번 채워지면 그 카드를 다시 쓸 수 없고, 서버 연결을 끊지 않은 채로 계속 HTML을 흘려보내면서 같은 이름의 마커를 반복해 채워 넣는 식으로 피드 같은 콘텐츠도 만들 수 있다. 글쓴이가 드는 예로는 답글이 겹겹이 달리는 게시판 스레드나, 응답 속도가 제각각인 LLM 챗봇의 스트리밍 출력을 들 수 있다.

재귀 함수로 트리 구조를 순회해 HTML을 만들던 복잡한 서버 코드 대신, 평평한 목록을 먼저 보내고 각 조각이 준비되는 대로 마커에 꽂아 넣는 쪽으로 사고방식을 바꿀 수 있다는 게 핵심 제안이다. 다만 아직 초기 단계 제안이라 FOUC(스타일 없는 콘텐츠가 잠깐 보이는 현상)나 레이아웃이 계속 흔들리는 문제를 어떻게 다룰지는 더 정리가 필요하고, 지금 당장 프로덕션에 쓸 수 있는 기능은 아니다. 다만 프레임워크 없이도 서버에서 비동기로 도착하는 콘텐츠를 다루는 방법이 늘어난다는 점은 눈여겨볼 만하다.
