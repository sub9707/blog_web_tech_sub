이번 주는 보안이 모든 대화를 집어삼킨 한 주다. Next.js가 App Router와 Image Optimization API를 겨냥한 두 개의 치명적 RCE와 한 개의 고위험 DoS를 한꺼번에 패치했고, 공교롭게도 Node.js도 26.x·24.x·22.x 세 릴리스 라인에 동시에 HIGH 등급 보안 업데이트를 예고했다. 당장 패치 버전을 올리는 것이 이번 주 가장 중요한 할 일이다.

그 사이에도 플랫폼과 생태계는 계속 움직였다. 크로미움에서는 서버 연결을 끊지 않고 HTML을 계속 흘려보내는 `<?marker>` 기반 선언적 부분 업데이트가 실험되고 있고, Bun은 tsc보다 몇 배 빠른 내장 타입 체커 `bun check`를 선보였다. UnJS의 H3는 웹 표준 위에서 완전히 다시 쓰인 v2로 안정화됐고, CSS 쪽에서는 마스크와 스타일 쿼리를 조합한 아이콘 패턴이 눈길을 끌었다. 보안 패치부터 챙기고, 나머지는 여유를 갖고 읽어도 늦지 않다.

## 1. Next.js 비정기 보안 패치, v16.4.1·v15.5.28 지금 바로 올려야 하는 이유

<bookmark url="https://nextjs.org/blog/nextjs-security-update-october-14-2026"></bookmark>

지난주 예고됐던 Next.js의 비정기 보안 업데이트가 v16.4.1(Active LTS)과 v15.5.28(Maintenance LTS)로 공개됐다. 9월 보안 릴리스에서 업스트림 의존성 문제로 미뤄졌던 수정 사항까지 포함된 패치다. 가장 심각한 건은 App Router에서 Cache Components를 사용하는 `use cache` 함수가 타입 배열(typed array)을 여러 개 반환할 때 인증 없이 원격 코드 실행(RCE)으로 이어지는 Critical 취약점이다. 알려진 우회 방법이 없어서, 해당 패턴을 쓰지 않는 애플리케이션도 일단 업그레이드가 권장된다.

두 번째 Critical 이슈는 Image Optimization API에서 SVG를 처리할 때 발생한다. 이미지 최적화에 쓰이는 업스트림 라이브러리의 메모리 관련 결함으로, glibc 기반 리눅스에서 Next.js를 돌릴 경우 RCE로 이어질 수 있다. 임시 우회책은 `sharp`를 0.35.5 이상으로 맞추는 것이지만, Next.js를 패치 버전으로 올리면 패키지 매니저가 알아서 안전한 `sharp` 버전을 가져온다.

마지막으로 High 등급의 DoS 이슈는 App Router에서 Server Action을 하나 이상 쓰는 애플리케이션을 겨냥한다. 조작된 요청이 과도한 CPU 사용을 유발해 같은 프로세스의 다른 요청 처리까지 막아버린다. Pages Router만 쓰거나 Server Action을 전혀 사용하지 않는다면 이 건에는 해당하지 않는다. 세 건 모두 `npm install next@15.5.28` 또는 `next@16.4.1`로 바로 해결되니, 운영 중인 프로젝트라면 이번 주 가장 먼저 처리할 일이다.

## 2. Node.js 26.x·24.x·22.x 동시 보안 릴리스, 세 라인 모두 HIGH

<bookmark url="https://nodejs.org/en/blog/vulnerability/october-2026-security-releases"></bookmark>

Node.js 프로젝트가 26.x, 24.x, 22.x 세 릴리스 라인에 대해 2026년 10월 21일 또는 그 직후 보안 업데이트를 내놓겠다고 예고했다. 공지에 따르면 세 라인 모두에서 수정되는 이슈 중 가장 심각한 등급이 HIGH다. 특정 기능 하나를 찝어 설명하기보다 라인별로 동시에 패치가 나가는 구조라, 어느 버전을 쓰든 예외 없이 업데이트가 필요하다.

실제로 LTS 라인에서는 24.22.0이, Current 라인에서는 26.12.0이 뒤따라 공개됐다. Node.js 팀은 공지에서 End-of-Life 버전은 보안 릴리스가 나올 때마다 항상 영향을 받는다고 못박았다. 22.x를 포함해 지원 종료가 가까운 버전을 쓰고 있다면 이번 기회에 LTS 라인 이동을 검토할 만하다. 배포 파이프라인에서 Node 버전을 고정해 둔 팀은 릴리스 스케줄을 다시 확인하고 패치 버전을 반영하는 작업을 챙겨야 한다.

## 3. <?marker>로 그리는 선언적 부분 업데이트, 재귀 없이 끝없는 스트리밍

<bookmark url="https://daverupert.com/2026/10/html-recursion/"></bookmark>

크로미움에 Declarative Partial Updates라는 이름의 실험적 기능이 플라이팅되고 있다. 핵심은 `<?marker name="">` 라는 새 요소다. 초기 응답에 플레이스홀더로 마커를 심어두고, 같은 연결을 끊지 않은 채 뒤늦게 `<template for="">`로 실제 콘텐츠를 흘려보내면 브라우저가 알아서 마커 위치에 그 내용을 끼워 넣는다. `<slot>`과 달리 한 번 채워지면 다시 쓸 수 없지만, 같은 이름의 마커를 반복하면 피드처럼 항목을 계속 이어 붙일 수 있다.

이 패턴이 흥미로운 지점은 서버가 데이터를 트리 구조로 조립해 내려보내는 상황, 예를 들어 중첩 댓글 스레드나 리뷰어 프로필이 달린 리뷰 목록 같은 전형적인 관계형 데이터를 다룰 때다. 지금까지는 중첩 for 루프나 재귀로 전체 트리를 다 만든 뒤에야 HTML을 내려보냈지만, `<?marker>`를 쓰면 가장 중요한 콘텐츠를 먼저 보여주고 나머지는 뒤에서 순서 없이 채워 넣는 식으로 구조를 단순화할 수 있다. LLM 챗봇이 답변을 생성 속도에 맞춰 스트리밍하는 상황도 같은 패턴으로 설명된다.

다만 이 기능은 아직 크로미움에서 실험 중인 플래그 단계이고, FOUC나 LCP 측면의 부작용도 별도로 관리가 필요하다고 원문은 언급한다. 지금 당장 프로덕션에 쓸 기능은 아니지만, 프레임워크 없이 서버 스트리밍 UI를 구성하는 방향을 미리 봐 둘 가치는 있다.

## 4. Bun 1.4.3의 bun check, tsc보다 최대 6배 빠른 내장 타입 체커

<bookmark url="https://bun.com/blog/bun-v1.4.3"></bookmark>

Bun 1.4.3에 `bun check`라는 내장 TypeScript 타입 체커가 추가됐다. `typescript-go`를 포트한 구현으로, TypeScript 7.0.2의 conformance 테스트 스위트를 100% 통과한다고 밝혔다. 프로젝트에 설치된 `typescript` 패키지 없이도 `tsconfig.json`을 읽어 같은 에러를 같은 형식으로 보고하며, 모든 CPU 코어를 활용한다. 다만 JavaScript나 `.d.ts`를 따로 출력하지 않고 언어 서버 기능도 없어서, 에디터의 타입스크립트 경험은 그대로 유지된다.

벤치마크로 공개된 수치에 따르면 VS Code, Next.js, Storybook, Nuxt, Playwright 같은 대형 프로젝트에서 `tsc` 7.0.2 대비 3배에서 6.4배 빠르고, 메모리도 2.2배에서 4.9배 적게 쓴다. `bun run --check`, `bun test --check`, `bun build --check`처럼 기존 명령에 플래그 하나만 붙이면 실행·테스트·빌드 전에 타입 체크를 끼워 넣을 수 있고, 타입 에러가 있으면 해당 단계 자체가 막힌다.

신뢰도를 보여주기 위해 Bun 팀은 72개의 실제 오픈소스 저장소를 의도적으로 설정이 어긋난 상태로 두고 `bun check`와 `tsc`의 출력을 파일·줄·열·에러 코드 단위로 비교했는데, 모든 프로젝트에서 결과가 일치했다고 밝혔다. CI에서 타입 체크가 느려서 고민이던 팀이라면 가장 먼저 시험해 볼 만한 변화다.

## 5. H3 v2 stable, 웹 표준 위에서 다시 쓴 UnJS HTTP 프레임워크

<bookmark url="https://h3.dev/blog/v2"></bookmark>

UnJS 생태계의 HTTP 프레임워크 H3가 v2로 안정화됐다. 이번 버전은 `Request`, `Response`, `URL`, `Headers` 같은 웹 표준 위에 완전히 새로 쓰였다. 핸들러는 표준 `Request`인 `event.req`와 `event.url`을 받고, 문자열이든 객체든 `Response`든 그대로 반환하면 H3가 알맞은 `Response`로 변환해 준다. v1의 대부분 유틸리티는 이름이 그대로 남아 있어 마이그레이션 부담이 크지 않다.

같은 앱 코드가 Node.js, Bun, Deno, Cloudflare Workers, 서비스 워커, 브라우저까지 동일하게 동작하도록 설계된 점도 눈에 띈다. `srvx`가 범용 서버 레이어 역할을 하고, 런타임별 세부 정보가 필요하면 `event.req.runtime`으로 접근할 수 있다. 라우팅은 `URLPattern`과 비슷한 문법을 지원하는 `rou3` v1을 쓰면서도 세그먼트 단위 트리 매칭으로 속도를 유지했고, 미들웨어·플러그인 시스템, 헤더·리다이렉트·CORS·캐싱을 그룹 단위로 선언하는 라우트 룰 엔진(`h3/rules`)도 새로 들어갔다.

H3는 Nitro를 비롯한 많은 UnJS 기반 프로젝트의 기초가 되는 패키지라, 이번 재작성은 Nuxt를 포함한 생태계 전반에 영향을 준다. Node.js 20.19 이상이 필요하다는 점만 확인하면, 기존 v1 유틸리티를 그대로 쓰면서 점진적으로 올려 볼 수 있다.

## 6. 마스크와 커스텀 프로퍼티로 완성하는 현대적 아이콘 시스템

<bookmark url="https://lea.verou.me/blog/2026/icons/"></bookmark>

아이콘 폰트나 스프라이트 대신, 빈 가상 요소에 `mask`를 걸어 아이콘을 그리는 패턴이 다시 정리됐다. 핵심은 `::before`나 `::after`를 1em 정사각형으로 만들고 `background: currentColor`를 채운 뒤, `mask`로 아이콘 모양만큼 잘라내는 방식이다. 어떤 아이콘을 쓸지는 `--icon-start`, `--icon-end` 같은 커스텀 프로퍼티로 지정하기 때문에, 인라인 스타일을 포함해 선언을 받을 수 있는 어디서든 아이콘을 바꿀 수 있다. flex 아이템은 기본적으로 늘어나기 때문에 `aspect-ratio` 대신 `width`와 `height`를 둘 다 명시해야 한다는 실무 팁도 함께 짚었다.

이 패턴을 모든 요소가 아니라 실제로 아이콘이 필요한 요소에만 적용하려면 스타일 쿼리 `@container style(--icon-start)`를 쓰면 된다. 이때 `@property`로 `--icon-start`를 `inherits: false`로 등록해야, 아이콘이 있는 컨테이너의 모든 자손에게 의도치 않게 아이콘이 번지는 일을 막을 수 있다. 가상 요소 안에서는 다시 `--icon-start: inherit`로 명시적으로 상속시켜 준다.

스타일 쿼리는 Baseline 2026으로 분류되어 최신처럼 보이지만, 실제 글로벌 사용자 기준으로는 약 93%에서 이미 동작한다. 크롬은 2023년에, 파이어폭스만 2026년 5월에야 뒤따라 지원을 추가했다. 아이콘이 없어도 UI가 크게 깨지지 않는 상황이라면 점진적 향상으로 받아들이고 넘어갈 만하지만, 아이콘 전용 컨트롤처럼 아이콘이 필수인 경우에는 `.icon` 같은 클래스를 함께 선언해 구형 브라우저에서도 동작하도록 이중으로 깔아두는 전략이 안전하다.

## 7. React 19.3.1, RSC 전송 프로토콜을 다듬은 조용한 패치

<bookmark url="https://github.com/react/react/releases/tag/v19.3.1"></bookmark>

React 19.3.1이 공개됐다. 변경 내역은 React Server Components의 전송 프로토콜을 개선한 한 건이 전부다. 새 기능 추가가 아니라 RSC 페이로드를 주고받는 방식을 다듬은 패치라서, 눈에 보이는 API 변화는 없다.

화려한 릴리스는 아니지만 RSC를 쓰는 프레임워크 입장에서는 전송 레이어의 안정성과 직결되는 변경이라 가볍게 넘길 사안은 아니다. App Router나 Server Components를 적극적으로 쓰는 프로젝트라면, 다른 큰 업그레이드 작업과 묶지 않고 이번 패치만 먼저 반영해 두는 편이 리스크를 줄이는 길이다.
